# v2.6.0 — Workspace buckets and moving originals

In this release, each Workspace can keep its original documents in its own S3-compatible bucket ([#100](https://github.com/AlexWhitehouse/local-document-extraction/pull/100), closes [#99](https://github.com/AlexWhitehouse/local-document-extraction/issues/99)). Owners and admins can also move existing originals from earlier locations into the current one ([#102](https://github.com/AlexWhitehouse/local-document-extraction/pull/102), closes [#101](https://github.com/AlexWhitehouse/local-document-extraction/issues/101)).

## Workspace buckets

- **Where:** **Workspaces → Original document storage**, for Workspace owners and admins. Members don't see it.
- **What it covers:** a saved bucket takes the Workspace's new uploads, document packets and Evaluation library saves in place of installation storage. It works even when the installation has no storage (`SOURCE_STORAGE_PROVIDER=none`).
- **Saving:** the app first writes, reads back and deletes a small test file. If any step fails, nothing is saved, and the message names the step. **Test** runs the same check without saving. You must confirm that the bucket uses neither object versioning nor Object Lock, because the app can't check this.
- **Changing it:** a new endpoint, bucket, prefix or addressing style applies to new uploads only. Existing originals stay readable where they are until they're moved or deleted. Changing only the access keys keeps the location. **Use default storage** sends new uploads back to installation storage.
- **Retention:** a Workspace bucket keeps new originals unless the Workspace turns off **Retain original documents**. `SOURCE_ORIGINAL_RETENTION_ENABLED` now applies to installation storage only.
- **Deletion:** deleting a Document or Workspace deletes its originals from whichever bucket holds them. A bucket's settings, including its keys, are kept until everything stored there is deleted, even after the Workspace is gone.
- **Access keys:** they're encrypted with `secrets/model-gateway.key` and never shown again. Only the last four characters of the access key ID are displayed.
- **Endpoints:** link-local and cloud metadata addresses, such as `169.254.169.254`, are refused, in every IPv4 and IPv6 spelling. Private network addresses are allowed.
- **Isolation:** a slow or unavailable Workspace bucket doesn't hold up other Workspaces' uploads, downloads or cleanup.

## Moving originals

- **Where originals are stored:** the same panel lists each location with its count and size: the local data folder, the installation bucket, earlier Workspace buckets and the current location.
- **Move to current location:** copies every retained original into the Workspace bucket, or into the installation bucket when the Workspace has none. This covers Documents, packets, packet children and Evaluation library entries. The confirmation says how much data will be copied and that providers may charge egress for data leaving the old bucket.
- **Safety:** each original is copied through the server, read back and compared by size and SHA-256. Only then is its Document pointed at the new copy. The old copy is deleted about 10 minutes later, so downloads already under way can finish. A restart at any point finishes or rolls back each original.
- **While it runs:** uploads, downloads and deletion keep working. The panel shows progress, and the move can be cancelled.
- **Busy or unreachable originals:** Documents still processing, and originals whose bucket can't be reached, are retried automatically. If the new location can't be reached, the move pauses and resumes. When the move ends, the panel lists originals that couldn't be moved, with the reason.
- **Afterwards:** emptied earlier Workspace buckets disappear from the list automatically, along with their saved keys.
- **Leaving an installation bucket:** once no original depends on the installation bucket, you can change or remove `SOURCE_STORAGE_S3_*` without the startup refusal.

## API

All new routes use a browser session and are limited to Workspace owners and admins. MCP clients don't get them.

- **Bucket settings:** `GET`, `PUT` and `DELETE` on `/v1/workspaces/{id}/source-storage`.
  - Changes need `If-Match`, or `If-None-Match: *` when creating a bucket.
  - New error codes include `invalid_source_storage`, `source_storage_test_failed` (with a `stage` field), `source_storage_endpoint_blocked` and `source_storage_overrides_disabled`.
- **Bucket test:** `POST /v1/workspaces/{id}/source-storage/test` tests a bucket without saving it.
- **Moves:**
  - `GET /v1/workspaces/{id}/source-storage/move` reports locations and the latest move.
  - `POST` on the same route starts a move. `DELETE` cancels it.
  - New error codes `source_storage_move_unavailable`, `source_storage_move_running`, `source_storage_move_nothing_to_move` and `source_storage_move_not_running`.
- **Retention settings:** the `source-retention` response gains `storage_location` (`"installation"` or `"workspace"`).

## Upgrading and compatibility

The release workflow checks **Ubuntu 24.04 x64 and arm64, and macOS 15 arm64**. Intel macOS binaries are bundled but not qualified by the CI matrix.

Stop the application. Back up its configuration and state. Then run:

```bash
document-extraction update v2.6.0
```

- **Control database:** on first start it adds tables for Workspace buckets and moves. Existing entries in the retained-object record are assigned to the installation's storage. The record also gains a size column, which is filled for new uploads and moved copies. All changes are additive.
- **Workspace databases:** no migrations.
- **New setting:** `SOURCE_STORAGE_WORKSPACE_OVERRIDES_ENABLED`, default `true`. Set it to `false` to turn Workspace buckets off. Saved buckets then take no new originals but keep serving existing ones.
- **Changed setting:** `SOURCE_ORIGINAL_RETENTION_ENABLED` no longer affects Workspace buckets.
- **Backups:** S3 originals, including those in Workspace buckets, are not part of application backups. Back up each bucket with the provider's tools. Keep `secrets/model-gateway.key` with your backup, or saved bucket keys can't be read after a restore.
- **Trust:** Workspace owners and admins can make the server send signed requests to private network hosts they choose. Give these roles only to people you trust, as with the Model gateway.

## Known limits

- Originals can't be moved into the local data folder, only into a bucket.
- There's no installation-wide command to move every Workspace off the installation bucket. Each Workspace starts its own move.
- Originals stored before this release show "size unknown" until they're moved. Local originals always do.
- Moves copy data through the server, at most four originals at once and two per bucket.
- Uploads to Workspace buckets still share the installation's submission limits (`SUBMISSION_MAX_CONCURRENCY` and `SUBMISSION_MAX_RESERVED_BYTES`). There is no per-bucket upload limit yet.
- A bucket with versioning or Object Lock keeps old versions after deletion and after moves. The app can't detect this.
