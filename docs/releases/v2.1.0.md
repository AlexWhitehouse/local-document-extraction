# v2.1.0 — PDFium rendering

This release raises throughput for documents sent to models that do not accept PDFs natively. The Go processor now renders pages with PDFium instead of PDF.js and makes fewer callbacks into the Bun runtime. Frontend and public API behavior are unchanged.

## Processing changes

- Pages are rendered by isolated `document-extraction-pdf` processes using PDFium. Each process has a deadline, recycles after 128 operations or 384 MiB peak memory, and stops at 1 GiB, so a hostile PDF affects only its own process.
- Rendered pages are lossless PNG: grayscale when the whole page is gray, otherwise RGB. Annotations and filled form fields are drawn. Page encoding overlaps the next page's rendering, and documents longer than eight pages render in parallel chunks.
- Page images use up to 144 DPI with each edge capped at **2000 px**, down from 2048 px. Some providers reject larger edges in requests with more than 20 images, which split assessments of long packets could produce.
- Each processing stage needs fewer round trips to the Bun runtime, and an extraction claim records its model in the same database commit.
- Workspaces with sequential model calls now serialize only the model calls, not page rendering.
- Model responses without a declared length no longer reserve the full 32 MiB response allowance before reading.

Upload validation is unchanged: the guarded PDF inspector still rejects malformed and hostile PDFs at upload.

## Performance evidence

On the development host (six vCPUs), matched runs against v2.0.0 with a near-instant simulated provider and image-only model input measured:

| Workload | v2.0.0 | v2.1.0 |
| --- | ---: | ---: |
| Two-page PDF, explicit Template | 17.60 Documents/s | 44.90 Documents/s |
| Two-page PDF, smart splitting + automatic Template | 27.93 | 56.43 |
| Scanned two-page PDF, explicit Template | 2.42 | 16.88 |
| Scanned two-page PDF, smart splitting + automatic Template | 2.13 | 26.46 |

Peak process-tree memory fell from about 2.3 GiB to 1.4–1.6 GiB. These are single runs; the v2.0.0 baseline measured 9–15% below the figures published with v2.0.0. Results depend on document content, machine resources, concurrency settings and provider behavior, and are not a production throughput guarantee. No paid model calls were used.

Rendered images are not pixel-identical to v2.0.0: anti-aliasing and glyph edges differ slightly (under 0.6% of pixels noticeably on the test fixtures). Page geometry, order, annotations and form values match. Check extraction accuracy on representative documents if you depend on exact results.

## Upgrading and runtime requirements

Stop the application and back up its configuration and state, then run:

```bash
document-extraction update v2.1.0
```

Release archives bundle the processor, the PDFium renderer and the PDFium library, with its third-party licenses, for Linux and macOS on x64 and arm64. Installed releases need neither a Go compiler nor network access to PDFium. Source builds download a pinned, checksum-verified PDFium library once during `bun run build`.

`GO_PDF_OVERLAP` and `GO_PDF_PNG_ENCODER` are removed. `GO_PDF_WORKER_BINARY` and `PDFIUM_LIBRARY` can override the renderer and library paths. No database migration is introduced, and state remains compatible with v2.0.0.

## Known limits

- Model context, request-size and rate limits still apply.
- Intel macOS binaries are bundled but not qualified by the CI matrix.
- Simulated model tests do not qualify live model routes, Google sign-in or Cloudflare email delivery.
