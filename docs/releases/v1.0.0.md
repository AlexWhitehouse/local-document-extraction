# v1.0.0 — Automatic template selection and smart splitting

Template tags now let the application select a suitable Template for an uploaded document. Smart splitting can divide a PDF into separate extraction jobs. Each job has its own results and original-page references.

## Automatic document processing

- The frontend can create, rename, assign, and delete shared Template tags. Names use lowercase. Templates can have multiple tags.
- Supply `template_tags` without `template_id` for automatic selection. Templates that match **any** supplied tag form the candidate pool. Classification uses candidate names and descriptions. Each document in a split PDF is classified independently.
- An explicit `template_id` fixes that Template version and skips automatic selection. Enabled Smart splitting still applies. Every resulting document uses the fixed Template.
- Workspace owners and admins can enable Smart splitting under **Document processing**, below Model gateway. Optional blank-page exclusion is in the same section. Both settings default to off. Blank removal requires Smart splitting. Nonblank cover pages remain.
- Ambiguous decisions get bounded reassessment before user review. Unresolved boundaries and Template choices keep their source for review. Restart resumes durable processing without duplicate children.
- Multi-document uploads show an overview and separate document tabs. A one-page upload or accepted one-document plan opens as a normal Document. Verified exclusions remain recorded.
- The upload dialog accepts a specific Template or automatic selection by tags. Workspace toggles give immediate feedback and save notifications.
- Original-page previews remain stable during polling and rendering. This prevents duplicate preview requests.

## API integration

Submit multipart requests to `POST /v1/extract`. Include `template_id` or a nonempty `template_tags` JSON array. Requests with neither value are rejected. Existing explicit-template integrations keep their behavior when Smart splitting is disabled.

With Smart splitting enabled, PDF submissions return a packet with `202`, `Location: /v1/packets/{packet_id}`, and `Retry-After: 2`. Poll that packet. For each `children[].job_id`, read `GET /v1/jobs/{job_id}` to get extraction results. Child `source_pages` refer to physical pages in the original PDF.

A one-child packet keeps this API response type, even when the frontend displays an ordinary Document. Handle `awaiting_review` packets and `awaiting_template` jobs explicitly. An all-blank PDF can complete with `outcome: "no_documents"` and no children.

See the [API reference and request-chain example](https://github.com/AlexWhitehouse/local-document-extraction/blob/v1.0.0/mkdocs/docs/api/overview.md#follow-the-packet-and-child-request-chain) and [Postman collection](https://github.com/AlexWhitehouse/local-document-extraction/blob/v1.0.0/postman/local-api.postman_collection.json).

## Also included since v0.2.0

- The Template assistant explains extraction results and field guidance. It proposes edits for review before application.
- Model gateway roles support separate models for extraction, Template assistance, and document classification and splitting. Unset optional roles use the extraction model.
- The Evaluation library stores reusable documents and Expected answers. Browser Batch Evaluations compare candidates across documents. They include result caching, field mapping, and answer verification.
- Evaluation navigation, day-first date scoring, preview dividers, and shared interface styling have improvements.

## Upgrading and compatibility

Bun remains pinned to **1.4.2**. Automated qualification covers **Ubuntu 24.04 x64 and arm64, and macOS 15 arm64**. The installer recognizes Intel macOS. This release's CI does not qualify Intel macOS or older operating systems.

Stop the application. Back up its configuration and state. Then run:

```bash
document-extraction update v1.0.0
```

The installer keeps configuration, accounts, documents, and generated secrets. It backs up local state before migration. Back up S3 buckets separately.

Database initialization adds Template-tag, model-role, Evaluation-library, and document-processing state required since v0.2.0. Existing Templates and extraction results remain available. Smart splitting and blank exclusion remain disabled until enabled in each Workspace. Automatic processing requires no new environment variables. Downgrade requires restoration of the backup from before the upgrade.

Custom `SUBMISSION_MAX_RESERVED_BYTES` limits must permit `MAX_SOURCE_FILE_BYTES` plus **40,960 bytes** of multipart overhead. The previous overhead was 32,768 bytes. Default settings already meet this requirement.

## Known limits

- Select a classification/splitting model with the required document capabilities. Provider image-count, PDF, context, and request-size limits still apply. Rendered pages are not automatically grouped into smaller requests to avoid provider limits. A connection test does not verify these capabilities.
- Automatic processing can increase time and model use. Unresolved decisions and provider failures can require user review.
- API clients poll for progress. Completed packets do not contain full child results. Failed packets can still have children that require polling.
- S3 buckets must not use object versioning or Object Lock. Local backups exclude S3 originals. Source downloads do not support byte ranges.

The release workflow validates the exact tagged commit before publishing `install.sh`, `document-extraction.tar.gz`, and its SHA256 checksum. Automated checks do not verify live Google sign-in, Cloudflare email delivery, or every third-party model route.
