Stop using Workspace API keys as the SPA's own authentication mode. Frontend workspace-scoped UI requests use the signed-in user session plus accepted Workspace context, while Workspace API keys remain backend credentials for external product-route clients.

## Agent Brief

**Category:** enhancement
**Summary:** Stop using Workspace API keys as the SPA's active authentication mode.

**Current behavior:**
The SPA can persist and use Workspace API key material as its active credential for normal UI requests. The frontend request layer prefers a stored API key when one is available, and local workspace state can include a synthetic fallback Workspace ID. This mixes browser session behavior with external-client credential behavior and can let UI requests bypass the intended signed-in session plus accepted Workspace context model.

**Desired behavior:**
Normal SPA requests should use the signed-in user session and a backend-confirmed accepted Workspace context. The SPA should not send Workspace API keys as its active authentication credential for UI requests, should not use synthetic fallback Workspace IDs, and should route unauthenticated users to login rather than presenting Workspace context. Workspace API keys should remain backend credentials for external clients on workspace-scoped product routes, but must not authenticate user/session-only routes or the SPA shell.

**Key interfaces:**
- Frontend request adapter — should send session requests with `credentials: include` and, for workspace-scoped UI requests, the backend-confirmed accepted Workspace ID in `x-workspace-id` rather than a bearer Workspace API key.
- Frontend Workspace context selection — should only provide accepted Workspace IDs received from backend Workspace listing or accepted Workspace actions, never synthetic fallback IDs.
- Backend authentication boundary — should continue accepting valid Workspace API keys for workspace-scoped product routes while requiring a session for profile, Workspace membership, invitations, Workspace deletion, API key generation, and SPA shell access.
- Unauthenticated SPA state — should present login without Workspace context or API-key-backed UI access.

**Acceptance criteria:**
- [x] Normal SPA UI requests do not send Workspace API keys as `Authorization: Bearer ...` credentials.
- [x] Workspace-scoped UI requests made by a signed-in user include a backend-confirmed accepted Workspace ID and never a synthetic fallback Workspace ID.
- [x] Unauthenticated users accessing the SPA are taken to login and are not given Workspace context.
- [x] Workspace API keys still authenticate external clients for workspace-scoped product routes such as Templates, Extraction jobs, and Document submission.
- [x] Workspace API keys do not authenticate user/session-only routes or the SPA shell.
- [x] Relevant frontend/backend checks cover session requests, API-key product-route compatibility, and rejection of API keys on session-only routes.

**Out of scope:**
- Changing current Workspace API key access parity on workspace-scoped product routes.
- Scoped Workspace API keys or separate read/write/delete permissions.
- Workspace API key display flow, one-time visibility, clipboard behavior, or role-gated generate/rotate controls.
- Browser persistence cleanup beyond what is necessary to stop active SPA API-key authentication.
