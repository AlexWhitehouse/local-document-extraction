# Frontend Workspace Context Transitions

Category: enhancement
Status: completed

## Parent

.scratch/workspace-resolution-and-api-keys/PRD.md

## What to build

Make user-driven Workspace context changes consistently select, clear, preserve, and refresh the right state. Create, delete, rename, accept invitation, decline invitation, leave, Workspace switch, selected Document disappearance, and access-loss transitions should follow the accepted Workspace context rules.

## Acceptance criteria

- [x] Accepting a Workspace invitation moves into the newly accepted Workspace context and removes the invited entry.
- [x] Declining a Workspace invitation returns to an accepted Workspace context without granting access to the declined Workspace.
- [x] Creating a Workspace selects the new accepted Workspace context without generating Workspace API key material.
- [x] Deleting the current Workspace clears workspace-scoped state, refreshes Workspaces, and selects the first remaining accepted Workspace.
- [x] Switching accepted Workspace immediately clears visible workspace-scoped data from the previous Workspace before loading the new Workspace data.
- [x] Renaming the current Workspace updates display and stored preference without clearing workspace-scoped data.
- [x] If the selected Document is no longer available after backend refresh, the frontend selects the first available Document or shows the empty state.

## Agent Brief

**Category:** enhancement
**Summary:** Make user-driven Workspace context transitions preserve, clear, or refresh frontend state according to accepted Workspace context rules.

**Current behavior:**
Frontend Workspace resolution now starts from backend-confirmed accepted Workspaces, but the follow-on user actions still need a durable transition contract. Workspace creation, deletion, renaming, Workspace invitation decisions, leaving a Workspace, switching accepted Workspaces, selected Document disappearance, and selected Workspace access loss can each affect the selected accepted Workspace, the visible Workspace selection view, and workspace-scoped UI data.

**Desired behavior:**
Every user-driven Workspace context transition should leave the SPA in a valid accepted Workspace context or a non-access invitation state. Accepting an invitation moves into the newly accepted Workspace. Declining an invitation removes that invited entry and returns to accepted Workspace context. Creating a Workspace selects the new accepted Workspace without exposing Workspace API key material. Deleting, leaving, or losing access to the current Workspace clears workspace-scoped data, refreshes the backend Workspace list, and selects another accepted Workspace when one is available. Renaming the current Workspace updates display and Stored workspace preference without clearing workspace-scoped data. Switching accepted Workspaces clears visible workspace-scoped data immediately before loading the new Workspace data. If the selected Document disappears after a backend refresh, the document view selects the first available Document or shows the empty state.

**Key interfaces:**
- Workspace transition decision logic - should express create, delete, rename, leave, switch, invitation accept/decline, forbidden-access recovery, and selected-Document disappearance as explicit decisions/effects.
- Workspace context update adapter - should apply selected accepted Workspace ID/name, selected invitation state, and Stored workspace preference consistently.
- Workspace-scoped frontend data - Templates, selected upload Template, visible Documents, queued jobs, selected Document, Workspace users, Workspace invitations, and any completed Document cache should be cleared when accepted Workspace context changes, but preserved for non-context-changing rename.
- Action toast behavior - should report user-visible Workspace transitions such as access changes, invitation decisions, creation, deletion, leave, and rename without surfacing silent backend invariant repair as a user action.

**Acceptance criteria:**
- [x] Accepting a Workspace invitation moves into the newly accepted Workspace context and removes the invited entry.
- [x] Declining a Workspace invitation returns to an accepted Workspace context without granting access to the declined Workspace.
- [x] Creating a Workspace selects the new accepted Workspace context without generating or showing Workspace API key material.
- [x] Deleting or leaving the current Workspace clears workspace-scoped state, refreshes Workspaces, and selects the first available accepted Workspace returned by the backend.
- [x] Switching accepted Workspace immediately clears visible workspace-scoped data from the previous Workspace before loading data for the new Workspace.
- [x] Renaming the current Workspace updates display and Stored workspace preference without clearing workspace-scoped data.
- [x] Forbidden access for the selected accepted Workspace refreshes Workspaces, moves to another accepted Workspace when available, and reports the access change with an Action toast.
- [x] If the selected Document is no longer available after backend refresh, the frontend selects the first available Document or shows the empty state.
- [x] Relevant frontend checks cover the transition decisions and at least one App-level seam for clearing or preserving data.
- [x] Verification includes the frontend production build; include backend typecheck only if backend interfaces are touched.

**Out of scope:**
- Backend accepted Workspace invariant repair and API key existence state.
- Initial startup Workspace resolution from backend lists.
- Workspace API key display, generation, rotation, clipboard behavior, or role-gated controls.
- Long-term completed Document cache retention rules beyond clearing on accepted Workspace context changes.
