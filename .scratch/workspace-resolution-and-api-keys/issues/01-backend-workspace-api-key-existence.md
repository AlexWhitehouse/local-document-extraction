# Backend Workspace API Key Existence

Category: enhancement
Status: completed

## Parent

.scratch/workspace-resolution-and-api-keys/PRD.md

## What to build

Make external-client Workspace API keys explicit backend state. Workspaces can exist without a Workspace API key, workspace responses expose whether one exists, and issuing a new key remains a one-time secret flow that replaces any existing hash. Existing silently generated key hashes are treated as no external-client Workspace API key, per the accepted ADR.

## Acceptance criteria

- [x] New and bootstrapped Workspaces start with no external-client Workspace API key and report `has_api_key: false`.
- [x] Workspace listing, Workspace creation, and Replacement personal Workspace responses expose non-secret API key existence state and never expose existing key material.
- [x] `POST /v1/workspaces/:id/api-key` remains owner/admin-only, replaces any existing key hash, returns one-time key material, and reports `has_api_key: true`.
- [x] Existing silently generated key hashes are migrated/reset so they are not treated as external-client Workspace API keys.
- [x] Workspace API key format remains opaque to callers beyond being usable as a bearer token.

## Agent Brief

**Category:** enhancement
**Summary:** Make external-client Workspace API key existence explicit in backend Workspace policy and API responses.

**Current behavior:**
Workspaces are created and bootstrapped with generated Workspace API key material and a required stored hash. Workspace creation and bootstrap responses can return the generated secret, and workspace listing does not expose a non-secret `has_api_key` state. Existing stored key hashes may have been silently generated rather than explicitly issued for external clients.

**Desired behavior:**
New and bootstrapped Workspaces should start without an external-client Workspace API key. Backend responses should expose non-secret API key existence state with `has_api_key`, never existing key material. `POST /v1/workspaces/:id/api-key` should be the explicit owner/admin action that issues or reissues a one-time Workspace API key secret, replaces any existing hash, and returns `has_api_key: true`. Existing silently generated hashes should be migrated/reset so they are not treated as external-client Workspace API keys, in line with the accepted ADR.

**Key interfaces:**
- `Workspace` persistence shape — must represent absence of an external-client Workspace API key.
- Workspace listing response entries — should include whether each accepted Workspace has an external-client Workspace API key.
- Workspace creation response — should return the new accepted Workspace context with `has_api_key: false` and no `api_key` secret.
- Replacement personal Workspace response shape — should include `has_api_key: false` and no `api_key` secret.
- Workspace API key issue/reissue response — should return the one-time `api_key` secret and `has_api_key: true`.
- Workspace API key authentication — should continue accepting valid issued Workspace API keys for workspace-scoped product routes.

**Acceptance criteria:**
- [x] New and bootstrapped Workspaces start with no external-client Workspace API key and report `has_api_key: false`.
- [x] Workspace listing, Workspace creation, and Replacement personal Workspace responses expose non-secret API key existence state and never expose existing key material.
- [x] `POST /v1/workspaces/:id/api-key` remains owner/admin-only, replaces any existing key hash, returns one-time key material, and reports `has_api_key: true`.
- [x] Existing silently generated key hashes are migrated/reset so they are not treated as external-client Workspace API keys.
- [x] Workspace API key format remains opaque to callers beyond being usable as a bearer token.
- [x] Relevant backend policy/API tests cover creation, bootstrap, listing, issue/reissue, authorization, migration/reset behavior, and API-key authentication.

**Out of scope:**
- Frontend API key display changes.
- Frontend Workspace resolution and local storage cleanup.
- Scoped Workspace API keys or changes to current API-key product-route access parity.
- Changing Workspace API key prefix or making key format a user-facing contract.
