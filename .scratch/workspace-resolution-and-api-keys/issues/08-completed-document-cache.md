# Completed Document Cache

Category: enhancement
Status: completed

## Parent

.scratch/workspace-resolution-and-api-keys/PRD.md

## What to build

Add a bounded Completed document cache for opened completed Extraction job details. The cache improves revisit performance for the same accepted Workspace after refresh while staying bounded, non-secret beyond extraction results, and tightly cleared on Workspace changes, sign-out, deletion, and not-found responses.

## Acceptance criteria

- [ ] Completed document cache stores a completed Extraction job only after the user opens that Document and details load.
- [ ] Cache entries contain backend-returned completed job metadata and Extraction results, not source file contents, File objects, blob URLs, or source preview URLs.
- [ ] Cache keeps at most 50 completed Documents for the current accepted Workspace.
- [ ] Cache may survive page refresh for the same resolved accepted Workspace.
- [ ] Cache clears on accepted Workspace change and sign-out.
- [ ] Queued, processing, and failed Extraction jobs are not stored as durable completed-cache entries.
- [ ] Cache entries are removed on explicit delete and when a job detail request returns not found.
- [ ] Filtered job-list absence does not remove cache entries; unfiltered job-list evidence prunes conservatively.

## Agent Brief

**Category:** enhancement
**Summary:** Add a bounded browser-local Completed document cache for opened completed Extraction job details.

**Current behavior:**
The frontend loads Extraction job lists and job details from the backend into in-memory document state. Stored workspace preference has been narrowed to accepted Workspace ID and display name, and user/session-specific Workspace data is cleared on sign-out and Workspace context changes. Completed Extraction job details are not yet governed by a durable cache contract that can survive refresh for the same accepted Workspace while staying bounded and tightly scoped.

**Desired behavior:**
The frontend should maintain a **Completed document cache** for completed **Extraction job** details that the user has explicitly opened. The cache should be scoped to the resolved accepted **Workspace** and job ID, may survive page refresh for the same accepted Workspace, and should render cached completed details while the backend remains the source of truth. It must store only backend-returned completed job metadata and **Extraction results**. It must not store Source file contents, browser `File` objects, blob URLs, or source preview URLs. Queued, processing, and failed Extraction jobs should continue to be fetched from the backend rather than stored as durable completed-cache entries.

Cache lifecycle rules should be conservative and privacy-preserving. Keep at most 50 completed Documents for the current accepted Workspace. Clear the cache on accepted Workspace context changes and sign-out. Remove entries when the user deletes a Document, when a job detail request returns not found, and when an unfiltered backend job-list refresh provides conservative evidence that the job no longer exists. Do not remove entries merely because a filtered job list does not include them.

**Key interfaces:**
- Completed document cache module - should own cache insert, lookup, retention, pruning, and clearing decisions behind a small interface keyed by accepted Workspace context and job ID.
- Job detail loading flow - should insert into the cache only after the user opens a completed Document and the completed details load from the backend.
- Job list refresh flow - should distinguish filtered from unfiltered list evidence so filtered absence does not prune cached completed Documents.
- Document deletion and not-found handling - should remove matching completed cache entries along with visible document state.
- Workspace transition and sign-out cleanup - should clear completed cache data when accepted Workspace context changes or the user signs out.
- Browser storage adapter - may persist completed cache entries for refresh survival, but must exclude Source file contents, `File` objects, blob URLs, and source preview URLs.

**Acceptance criteria:**
- [ ] Completed document cache stores a completed Extraction job only after the user opens that Document and details load.
- [ ] Cache entries contain backend-returned completed job metadata and Extraction results, not Source file contents, `File` objects, blob URLs, or source preview URLs.
- [ ] Cache keeps at most 50 completed Documents for the current accepted Workspace.
- [ ] Cache may survive page refresh for the same resolved accepted Workspace.
- [ ] Cache clears on accepted Workspace change and sign-out.
- [ ] Queued, processing, and failed Extraction jobs are not stored as durable completed-cache entries.
- [ ] Cache entries are removed on explicit delete and when a job detail request returns not found.
- [ ] Filtered job-list absence does not remove cache entries; unfiltered job-list evidence prunes conservatively.
- [ ] Relevant frontend checks cover insertion, lookup, retention, same-Workspace refresh survival, Workspace-change clearing, sign-out clearing, delete/not-found removal, filtered-list non-pruning, unfiltered conservative pruning, and exclusion of source preview data.
- [ ] Verification includes the frontend production build.

**Out of scope:**
- Persisting Source files, Source file preview URLs, browser `File` objects, or blob URLs.
- Offline-first Document review or long-term local storage of Extraction results beyond the bounded Completed document cache.
- Persisting Active page, selected Document, selected upload Template, Templates, or general job history as user preferences.
- Backend Extraction job API changes unless the existing response contract cannot distinguish completed details safely.
- Workspace API key generation, rotation, one-time visibility, or SPA authentication behavior.
