# Workspace API Key Display Flow

Category: enhancement
Status: completed

## Parent

.scratch/workspace-resolution-and-api-keys/PRD.md

## What to build

Implement the owner/admin Workspace API key display flow around explicit external-client credential generation. The UI uses backend `has_api_key` state to label actions, confirms rotation, always shows one-time key material, attempts clipboard copy, supports manual copy retry, and keeps members in the current non-actionable role-gated state.

## Acceptance criteria

- [x] The API key section remains visible to members, but only owners/admins can generate or rotate Workspace API keys.
- [x] The action is labelled "Generate API Key" when no Workspace API key exists and "Rotate API Key" when replacing an existing key.
- [x] Rotating an existing Workspace API key requires confirmation; first generation does not.
- [x] When no key exists, the display says "Generate an API key to view"; when a hidden key exists, it says "Rotate API key to view again".
- [x] Generated or rotated key material is always shown once and is never persisted as SPA auth state.
- [x] Clipboard success reports generated-and-copied or rotated-and-copied Action toast copy.
- [x] Clipboard failure or unavailable Clipboard API leaves the key visible and reports manual-copy Action toast copy.
- [x] Visible key material includes a compact icon-only Copy button with an accessible label.
- [x] The UI does not promise a Workspace API key prefix or length.

## Agent Brief

**Category:** enhancement
**Summary:** Implement Workspace API key display as an explicit owner/admin external-client credential flow.

**Current behavior:**
The frontend has a rotate/refresh API key action and can keep returned Workspace API key material in SPA state. The UI does not yet model backend `has_api_key` as non-secret existence state, first generation versus rotation copy, one-time visible key lifecycle, clipboard success/failure outcomes, confirmation for rotation only, or the member-facing non-actionable display state.

**Desired behavior:**
The **Workspace API key display** should treat Workspace API keys as external-client credentials, not SPA auth state. Accepted Workspace entries include non-secret `has_api_key` state from the backend. Owners/admins can explicitly generate the first key or rotate an existing key. First generation does not require confirmation; rotation requires confirmation because existing external clients will stop working. Newly generated or rotated key material is always shown once, even when clipboard copy fails or is unavailable. Clipboard success and failure use distinct Action toast copy for generated versus rotated keys. Visible key material includes a compact icon-only Copy button with an accessible label. Members can see the API key section in its role-gated non-actionable state but cannot generate or rotate keys. The UI must not promise a Workspace API key prefix or length, and key material must not be persisted as SPA auth state.

**Key interfaces:**
- Workspace API key display decision logic - should derive action label, empty/hidden display copy, confirmation requirement, role-gated action availability, and one-time visibility from Workspace role, `has_api_key`, and current visible key material.
- Workspace API key issue/reissue request adapter - should call the existing backend endpoint and treat returned `api_key` as one-time key material plus `has_api_key: true` state.
- Clipboard adapter - should attempt automatic copy when key material is issued, report success/failure without hiding the key on failure, and support manual copy retry from the visible key field.
- Action toast behavior - should distinguish generated-and-copied, rotated-and-copied, generated-manual-copy, and rotated-manual-copy outcomes without including key material in toast text.
- Persistence boundary - should keep one-time key material in ephemeral UI state only and clear it on dismiss, accepted Workspace change, sign-out, refresh, or navigation away.

**Acceptance criteria:**
- [x] The API key section remains visible to members, but only owners/admins can generate or rotate Workspace API keys.
- [x] The action is labelled "Generate API Key" when `has_api_key` is false and "Rotate API Key" when `has_api_key` is true.
- [x] Rotating an existing Workspace API key requires confirmation; first generation does not.
- [x] When no key exists, the display says "Generate an API key to view"; when a hidden key exists, it says "Rotate API key to view again".
- [x] Generated or rotated key material is always shown once and is never persisted as SPA auth state.
- [x] Clipboard success reports generated-and-copied or rotated-and-copied Action toast copy.
- [x] Clipboard failure or unavailable Clipboard API leaves the key visible and reports manual-copy Action toast copy.
- [x] Visible key material includes a compact icon-only Copy button with an accessible label.
- [x] Visible key material clears on dismiss, accepted Workspace change, sign-out, refresh, or navigation away.
- [x] The UI does not promise a Workspace API key prefix or length.
- [x] Relevant frontend checks cover owner/admin/member state, generate versus rotate labels, confirmation rules, one-time visibility lifecycle, clipboard outcomes, manual copy retry, and no key material in persistence or toast text.
- [x] Verification includes the frontend production build; include backend typecheck only if backend interfaces are touched.

**Out of scope:**
- Backend API key existence state and issue/reissue behavior, already covered by the completed backend issue.
- Changing current Workspace API key access parity on workspace-scoped product routes.
- Scoped Workspace API keys or separate read/write/delete permissions.
- Changing Workspace API key format, prefix, or length.
