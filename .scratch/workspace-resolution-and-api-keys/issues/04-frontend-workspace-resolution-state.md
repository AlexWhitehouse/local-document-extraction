# Frontend Workspace Resolution State

Category: enhancement
Status: completed

## Parent

.scratch/workspace-resolution-and-api-keys/PRD.md

## What to build

Resolve accepted Workspace context from the backend workspace list instead of local fallback state. The frontend validates stored workspace preference against backend-confirmed accepted Workspaces, shows Loading workspace context while resolving, enters Workspace resolution error on failure, avoids auto-selecting invited entries, and recovers from forbidden access by refreshing Workspaces.

## Acceptance criteria

- [x] Startup Workspace resolution never invents or uses a synthetic default Workspace ID.
- [x] Loading workspace context uses generic loading display and keeps workspace-scoped UI actions unavailable.
- [x] Stored workspace preference is used only when the accepted Workspace still appears in the backend workspace list.
- [x] Missing or stale stored preference selects the first accepted Workspace returned by the backend.
- [x] Pending Workspace invitations are shown but not auto-selected when accepted Workspaces exist.
- [x] Workspace list failures enter a retryable Workspace resolution error rather than falling back to stored state.
- [x] Forbidden access for the selected accepted Workspace refreshes Workspaces, moves to another accepted Workspace when available, and shows an Action toast that access changed.

## Agent Brief

**Category:** enhancement
**Summary:** Resolve frontend Workspace context only from backend-confirmed accepted Workspaces.

**Current behavior:**
The frontend can still initialize and display Workspace context from local fallback state. It can use a synthetic default Workspace ID, read broad legacy Workspace persistence, show fallback Workspace names while context is unresolved, and treat Workspace list failures as an empty list rather than a retryable resolution failure. This conflicts with the domain rule that accepted Workspace IDs are backend-owned and clients must not invent default or fallback Workspace access.

**Desired behavior:**
Signed-in startup should enter **Loading workspace context** until the frontend has fetched the backend Workspace list and resolved an accepted **Workspace context**. Stored workspace preference is only a hint: it may restore a Workspace only when that accepted Workspace still appears in the backend list. If the stored preference is missing or stale, select the first accepted Workspace returned by the backend. Pending **Workspace invitations** may be shown as invited entries, but they must not be auto-selected while accepted Workspaces exist and must not enable workspace API access. Workspace listing failures should enter a retryable **Workspace resolution error** with workspace-scoped UI actions unavailable. If the selected accepted Workspace starts returning forbidden access, refresh Workspaces, move to another accepted Workspace when available, and show an **Action toast** explaining that access changed.

**Key interfaces:**
- Stored workspace preference — should contain only accepted Workspace ID and display name under the Document Extraction storage key, and should not read the legacy Image Extraction storage key.
- Workspace resolution logic — should select only backend-confirmed accepted Workspaces, reject stale stored preferences, avoid synthetic fallback IDs, and return loading/error decisions that keep workspace-scoped actions unavailable.
- Workspace selection view — should distinguish accepted Workspace entries from invited Workspace entries and avoid auto-selecting invitations when accepted Workspaces exist.
- Frontend request adapter — should send workspace-scoped UI requests only after accepted Workspace context is resolved and should recover from forbidden selected-Workspace access by refreshing Workspace context.
- Action toast behavior — should notify when unexpected access changes force the UI to move away from the selected accepted Workspace.

- [x] Startup Workspace resolution never invents or uses a synthetic default Workspace ID.

- [x] Stored workspace preference is used only when the accepted Workspace still appears in the backend workspace list.
- [x] Missing or stale stored preference selects the first accepted Workspace returned by the backend.

- [x] Verification includes the frontend production build; include backend typecheck only if backend interfaces are touched.
