## Agent Brief

**Category:** enhancement
**Summary:** Repair broken zero-accepted-Workspace states from the backend workspace listing boundary.

**Current behavior:**
The backend can create personal Workspaces during first-login bootstrap and can create a Replacement personal Workspace when a user leaves their last accepted Workspace. However, a signed-in user whose accepted Workspace membership set has already become empty is not repaired by `GET /v1/workspaces`; the endpoint can return an empty accepted Workspace list even though the domain invariant says a signed-in user should have at least one accepted Workspace after sign-up or first login.

**Desired behavior:**
`GET /v1/workspaces` should be the backend repair point for the accepted Workspace invariant. When a signed-in user has zero accepted Workspaces, listing Workspaces should create a personal accepted Workspace using the same starter-template bootstrap semantics as first login, then return the repaired accepted Workspace list. Pending Workspace invitations must not count as accepted Workspace access. Removing another user from a Workspace should not create that user's replacement Workspace immediately; the repair should occur when that removed user next lists their Workspaces. Self-service Leave Workspace should continue creating a Replacement personal Workspace immediately when leaving the user's last accepted Workspace.

**Key interfaces:**
- Workspace listing API response — should return at least one accepted Workspace after repair for a signed-in user in a zero-accepted-Workspace state.
- Workspace policy bootstrap behavior — should reuse the same personal Workspace and starter-template creation semantics as first login.
- Pending Workspace invitation listing — should remain separate from accepted Workspace membership and must not satisfy the accepted Workspace invariant.
- Workspace member action behavior — should allow owner/admin removal of another user without immediately repairing the removed user's private accepted Workspace invariant.
- Leave Workspace behavior — should preserve immediate Replacement personal Workspace creation for self-service last-Workspace leave.

**Acceptance criteria:**
- [ ] `GET /v1/workspaces` repairs a signed-in user's zero-accepted-Workspace state and returns at least one accepted Workspace.
- [ ] The repair path uses the same personal Workspace naming, membership, and starter-template bootstrap semantics as first login.
- [ ] Pending Workspace invitations do not prevent repair when the user has no accepted Workspace memberships.
- [ ] Owner/admin removal of another user's last accepted Workspace membership does not immediately create a replacement personal Workspace for that removed user.
- [ ] Self-service Leave Workspace still creates a Replacement personal Workspace immediately when leaving the user's last accepted Workspace.
- [ ] Backend policy/API coverage verifies the repair path and the non-regression cases above.

**Out of scope:**
- Frontend Workspace resolution state changes.
- SPA authentication mode changes.
- Workspace API key display or generation UI changes.
- Treating pending Workspace invitations as workspace access.
