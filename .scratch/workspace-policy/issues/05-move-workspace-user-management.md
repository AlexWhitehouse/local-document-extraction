## Agent Brief

**Category:** enhancement
**Summary:** Move workspace user listing, member removal, admin promotion, and owner transfer behind Workspace policy.

**Current behavior:**
Workspace user management is still handled at the API route layer. The current route-level code checks actor membership roles, lists workspace users, removes target memberships, promotes members to admin, and coordinates owner transfer writes directly. This leaves membership role rules and owner transfer consistency outside the intended Workspace policy module.

**Desired behavior:**
Workspace user management should route through the Workspace policy interface by intent. Workspace policy should own the durable D1 reads and writes for listing workspace users, removing workspace users, promoting members to admin, and transferring workspace ownership. Public route response shapes, HTTP status codes, error codes, and role behavior should remain compatible with current behavior. Owner transfer should leave exactly one owner in the workspace and demote the previous owner to admin.

**Key interfaces:**
- `Workspace policy` module/interface - should expose intent-shaped operations for listing workspace users, removing a workspace user, promoting a workspace member to admin, and transferring workspace ownership.
- Workspace user listing result - should preserve the current users response data, including user id, name, email, role, and membership creation timestamp ordered by owner, admin, then member.
- Workspace role capability checks - should preserve owner/admin/member behavior without API callers loading membership rows and reimplementing role checks.
- Owner transfer operation - should consistently demote the previous owner, promote the target member to owner, and update the workspace owner reference so the workspace has exactly one owner afterward.
- Workspace policy errors - should be typed or distinguishable enough for callers to preserve current HTTP semantics for non-members, forbidden management attempts, missing target users, invalid actions, and owner-removal conflicts.

- [x] Workspace users can be listed through Workspace policy with the same response shape and ordering as before.

- [x] Admins can remove member users but cannot remove owners or admins.
- [x] Owners can promote members to admin.

- [x] Owners can transfer ownership to an existing workspace member.
- [x] Owner transfer leaves the workspace with exactly one owner and demotes the previous owner to admin.

- [x] Public route response contracts and error semantics for workspace user management remain compatible with current behavior.

**Out of scope:**
