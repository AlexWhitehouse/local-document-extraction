## Agent Brief

**Category:** enhancement
**Summary:** Move workspace settings updates and workspace API key rotation behind Workspace policy.

**Current behavior:**
Workspace settings updates and workspace API key rotation are handled directly by API callers. Those callers perform membership role checks themselves, update workspace rows directly, and participate in workspace API key hashing. This leaves owner/admin/member capability rules and API key rotation behaviour outside the intended Workspace policy module.

**Desired behavior:**
Workspace settings updates and workspace API key rotation should route through the Workspace policy interface by intent. Owners and admins should retain permission to update workspace settings and rotate workspace API keys. Members should be rejected from both mutations with the same public HTTP semantics as current behaviour. API key rotation should generate a new plaintext key, persist only its hash, and return the plaintext key only in the rotation response.

**Key interfaces:**
- `Workspace policy` module/interface - should own durable D1 reads and writes for the workspace settings update and workspace API key rotation decisions.
- Workspace role capability checks - should allow owners/admins and reject members for these mutations without callers loading membership rows and reimplementing role checks.
- Workspace API key hashing/rotation contract - should centralize key hash persistence and preserve one-time plaintext return on rotation.
- Workspace policy errors - should map cleanly at the caller edge to the current HTTP status codes, error codes, and messages for forbidden access and validation failures.

**Acceptance criteria:**
- [ ] Owners and admins can update workspace settings through Workspace policy.
- [ ] Members cannot update workspace settings.
- [ ] Owners and admins can rotate a workspace API key through Workspace policy.
- [ ] Workspace API key rotation stores only the hash and returns the plaintext key once in the rotation response.
- [ ] API callers no longer load workspace membership rows directly for these two mutations.
- [ ] Public route response contracts and error semantics for these mutations remain compatible with current behaviour.
- [ ] Backend typecheck succeeds.

**Out of scope:**
- Moving invitations, workspace user management, owner transfer, workspace deletion, invitation acceptance, or new-user bootstrap behind Workspace policy.
- Changing database schema.
- Changing public API response contracts beyond preserving the current settings update and API key rotation responses.
- Replacing existing auth routing, Better Auth configuration, or cascade deletion behaviour.
