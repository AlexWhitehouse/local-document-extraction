## Agent Brief

**Category:** enhancement
**Summary:** Move workspace listing and workspace creation behind the Workspace policy module.

**Current behavior:**
Workspace listing and creation are still owned by route-level callers. Listing directly joins workspace membership rows to return a user's workspaces. Creation validates the request, creates the workspace row, creates the owner membership, generates the workspace API key, hashes it, persists the hash, and returns the plaintext key from the caller. This keeps membership and workspace API key hashing rules duplicated outside the intended Workspace policy module.

**Desired behavior:**
Workspace listing and creation should route through the Workspace policy interface. Listing should preserve the existing response shape for a user's workspaces. Creation should preserve the existing behavior: create the workspace, create the owner membership, generate a workspace API key, persist only the key hash, and return the plaintext key once in the response. Route handlers should adapt HTTP request and response data but should not own membership write rules or workspace API key hashing rules.

**Key interfaces:**
- `Workspace policy` module/interface - should expose intent-shaped operations for listing a user's workspaces and creating a workspace for a user.
- Workspace creation result - should include the workspace id, workspace name, owner role, created timestamp, and one-time plaintext workspace API key needed to preserve the current API contract.
- Workspace listing result - should preserve the current list response data, including workspace identifiers, names, creation timestamps, image byte limits, and the user's role.
- Workspace API key hashing - should be owned by Workspace policy so create, rotate, and authenticate paths share the same hashing behavior over time.

**Acceptance criteria:**
- [x] A user can list their workspaces with the same response shape as before.
- [x] A user can create a workspace and receives the workspace id, name, owner role, created timestamp, and plaintext workspace API key.
- [x] Workspace API key hashing for workspace creation is owned by Workspace policy rather than duplicated by the caller.
- [x] Workspace creation owner membership writes are owned by Workspace policy rather than duplicated by the caller.
- [x] Route handlers adapt request and response data without owning membership or key hashing rules.
- [x] Backend typecheck succeeds.

**Out of scope:**
- Moving workspace settings, workspace API key rotation, invitations, user management, deletion eligibility, or new-user bootstrap behind Workspace policy.
- Changing public workspace route response contracts.
- Changing the database schema.
- Introducing a generic persistence layer or generic D1 store abstraction.
