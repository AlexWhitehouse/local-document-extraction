## Agent Brief

**Category:** enhancement
**Summary:** Move workspace deletion eligibility behind Workspace policy while preserving existing cascade cleanup behavior.

**Current behavior:**
Workspace deletion eligibility is still owned by the API route layer. The current deletion path checks whether the caller is a workspace member, verifies the caller is the owner, checks whether the owner has at least one other workspace, then calls the existing cascade deletion mechanism. This leaves deletion role rules and last-workspace protection outside the intended Workspace policy module.

**Desired behavior:**
Workspace deletion should route through the Workspace policy interface by intent. Workspace policy should approve deletion only when the acting user is the workspace owner and has at least one other workspace. Admins, members, non-members, and owners deleting their only workspace should receive the same public error semantics as before. Once Workspace policy approves deletion, the existing cascade deletion behavior should remain responsible for removing workspace data.

**Key interfaces:**
- `Workspace policy` module/interface - should expose an intent-shaped operation for approving or performing workspace deletion eligibility checks.
- Workspace deletion response contract - should preserve the current successful response shape that confirms the workspace id was deleted.
- Workspace policy errors - should be distinguishable enough for callers to preserve current HTTP semantics for non-members, non-owner callers, and last-workspace rejection.
- Existing cascade deletion mechanism - should remain the cleanup path after Workspace policy approves deletion.

**Acceptance criteria:**
- [x] Only owners can delete a workspace.
- [x] Admins and members cannot delete a workspace.
- [x] Non-members cannot delete a workspace.
- [x] Owners cannot delete their only workspace.
- [x] Approved deletion still removes workspace data through the existing cascade deletion behavior.
- [x] Route handlers no longer load workspace membership rows or count user workspaces for deletion eligibility decisions.
- [x] Public route response contracts and error semantics for workspace deletion remain compatible with current behavior.
- [x] Backend typecheck succeeds.

**Out of scope:**
- Replacing or redesigning the cascade deletion mechanism.
- Changing public workspace deletion route paths, request bodies, response bodies, HTTP status codes, or error codes except where required to preserve existing behavior through Workspace policy.
- Changing database schema.
- Moving new-user workspace bootstrap, template behavior, extraction behavior, or profile behavior behind Workspace policy.
- Introducing a generic persistence layer or generic D1 store abstraction.
