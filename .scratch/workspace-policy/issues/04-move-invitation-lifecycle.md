## Agent Brief

**Category:** enhancement
**Summary:** Move invitation creation, listing, and acceptance behind Workspace policy while preserving current invitation behavior.

**Current behavior:**
Invitation lifecycle behavior is implemented at the API route layer. Invitation creation checks the inviter membership role, normalizes email, rejects duplicate pending invitations, creates pending invitation rows, and returns the existing response shape. Invitation listing reads pending invitations for the signed-in user's normalized email. Invitation acceptance validates pending status, matching email, and expiry, durably marks expired invitations, creates or updates the membership, marks the invitation accepted, and returns the current response shape.

**Desired behavior:**
Workspace policy should own the durable D1 reads and writes for invitation creation, invitation listing, and invitation acceptance. Callers should pass intent to Workspace policy and map Workspace policy outcomes or errors to the existing HTTP status codes, error codes, messages, and response contracts. Email normalization, duplicate pending invitation detection, wrong-email rejection, expiry marking, accepted membership creation/update, and accepted invitation status changes should remain behaviorally compatible.

**Key interfaces:**
- `Workspace policy` module/interface - should expose intent-shaped operations for inviting a workspace member, listing pending invitations by user email, and accepting an invitation.
- Invitation role input - should continue to permit inviting users as `admin` or `member`, defaulting to `member` when no valid invite role is supplied.
- Workspace policy errors - should be typed or distinguishable enough for callers to preserve current HTTP semantics for forbidden invite attempts, invalid invitation email, duplicate pending invitations, missing invitations, wrong-email acceptance, and expired invitations.
- Invitation response shapes - should remain compatible with current workspace invitation creation, invitation listing, and invitation acceptance responses.

**Acceptance criteria:**
- [x] Owners and admins can invite users as admin or member through Workspace policy.
- [x] Members cannot invite users, and the existing forbidden HTTP semantics are preserved.
- [x] Duplicate pending invitations for the same workspace and normalized email are rejected with the existing conflict semantics.
- [x] Pending invitations can be listed for a normalized email through Workspace policy.
- [x] Accepting an invitation validates matching email, pending status, and expiry before creating or updating membership.
- [x] Expired invitations are durably marked expired before returning the expiry error.
- [x] Accepted invitations create or update workspace membership with the invited role and mark the invitation accepted.
- [x] Route handlers no longer own invitation membership-role checks, invitation lookup/update SQL, email normalization, duplicate pending invitation detection, or expiry marking.
- [x] Public API response contracts for invitation creation, listing, and acceptance remain compatible.
- [x] Backend typecheck succeeds.

**Out of scope:**
- Changing public route paths, request bodies, response bodies, HTTP status codes, or error codes except where required to preserve existing behavior through Workspace policy.
- Moving workspace user management, owner transfer, deletion eligibility, workspace API key rotation, or new-user workspace bootstrap behind Workspace policy.
- Changing the database schema.
- Introducing a generic persistence layer or generic D1 store abstraction.
