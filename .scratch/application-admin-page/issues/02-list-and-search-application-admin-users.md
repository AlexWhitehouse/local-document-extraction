# List and search Application admin users

Category: enhancement
Status: completed

## Parent

.scratch/application-admin-page/PRD.md

## What to build

Build the first useful Application admin page user listing using Better Auth admin utilities directly. Application admins should be able to load users, see account-level fields, search manually by email or name, clear search, and page through newest accounts first without exposing Workspace data or internal Better Auth user IDs.

## Acceptance criteria

- [x] The Application admin page lists users with email, name, account email verification status, application role, banned status, relevant ban reason, and exact local account creation date/time.
- [x] The list uses fixed page size 25, newest accounts first, previous/next pagination, and total user count inside the page after loading.
- [x] User search uses one input plus an email/name field selector, defaults to email, submits manually, and can be cleared to the first unfiltered page.
- [x] The first listing slice does not show Better Auth user IDs, authentication provider/source, Workspace membership summaries, Workspace data, role filters, or banned-status filters.
- [x] Loading and mutation state for the admin feature is local to the admin feature rather than the app-wide busy flag.
- [x] List loading errors are shown inline and operation outcomes use Action toasts where applicable.
- [x] Focused frontend coverage verifies listing, search, pagination behavior, and that the Admin page remains available during Loading workspace context or Workspace resolution error.

## Agent Brief

**Category:** enhancement
**Summary:** Build the first useful Application admin user listing with search and pagination.

**Current behavior:**
The Application admin foundation exists: Application admin access is based on the persisted Better Auth application role, the authenticated layout can show an Admin page, and the runtime auth client exposes Better Auth admin utilities. The Admin page is still only a shell and does not yet list or search users.

Application admin authority is application-wide and separate from Workspace owner/admin membership. The first admin page must remain account-focused and must not expose Workspace membership summaries, Workspace data, or internal Better Auth user IDs.

**Desired behavior:**
Application admins should be able to load a user list on the Application admin page, inspect account-level fields, manually search by email or name, clear search back to the first unfiltered page, and move through pages of newest accounts first.

The user listing should use Better Auth admin client utilities directly through the existing runtime auth client. Loading and error state for this feature should be local to the Application admin page rather than using the app-wide busy flag. Loading errors should be shown inline, and operation outcomes should use Action toasts where applicable.

The Application admin page should remain available while the frontend is in Loading workspace context or Workspace resolution error because the feature is account-level, not workspace-scoped.

**Key interfaces:**
- Existing runtime auth client — use the already configured Better Auth admin client utilities for user listing and search; do not create custom product `/v1/admin/*` routes for this slice.
- Application admin page state — should own listing, search, pagination, loading, and list-error state locally rather than relying on the app-wide busy flag.
- Application admin page rendering — should show account email, name, account email verification status, application role, banned status, relevant ban reason, and exact local account creation date/time.
- User search controls — should provide one search input plus an email/name selector, default to email, submit manually, and support clearing back to the first unfiltered page.
- Pagination controls — should use a fixed page size of 25, newest accounts first, previous/next navigation, and show the total user count inside the page after loading.

**Acceptance criteria:**
- [x] The Application admin page lists users with email, name, account email verification status, application role, banned status, relevant ban reason, and exact local account creation date/time.
- [x] The list uses fixed page size 25, newest accounts first, previous/next pagination, and shows the total user count inside the page after loading.
- [x] User search uses one input plus an email/name field selector, defaults to email, submits manually, and can be cleared to the first unfiltered page.
- [x] The first listing slice does not show Better Auth user IDs, authentication provider/source, Workspace membership summaries, Workspace data, role filters, or banned-status filters.
- [x] Loading and mutation state for the admin feature is local to the admin feature rather than the app-wide busy flag.
- [x] List loading errors are shown inline and operation outcomes use Action toasts where applicable.
- [x] Focused frontend coverage verifies listing, search, pagination behavior, and that the Application admin page remains available during Loading workspace context or Workspace resolution error.

**Out of scope:**
- Changing Application admin role assignments.
- Banning or unbanning users.
- Starting or stopping impersonation.
- Deleting users, creating users, setting passwords, or manually revoking sessions.
- Showing Better Auth user IDs, authentication provider/source, Workspace membership summaries, or Workspace data.
- Adding role filters, banned-status filters, page-size selection, sortable columns, custom audit logging, custom product admin routes, URL routing, CSS modules, or a new styling system.
