# Start regular-user impersonation safely

Category: enhancement
Status: completed

## Parent

## What to build

Allow Application admins to start impersonating eligible regular users from the Application admin page. Starting impersonation should require confirmation, prevent ineligible targets, clear session-scoped frontend state, refetch the session, and move the SPA into the normal Workspace page experience for the impersonated user.

## Acceptance criteria

- [x] Eligible regular users have an impersonation action that requires confirmation naming the target user and explaining the transition into that user's app experience.
- [x] The acting Application admin cannot impersonate their own account.
- [x] Other Application admins cannot be impersonated.
- [x] Banned users cannot be impersonated until unbanned.
- [x] Successful impersonation clears session-scoped Workspace, Template, and Document UI state, refetches the session, and moves to the Workspace page.
- [x] The admin user list is not reloaded after successful impersonation because the session changes and the admin leaves the page.
- [x] Focused frontend coverage verifies target eligibility guards, confirmation behavior, state clearing, session refetch, and Workspace navigation.

## Agent Brief

**Category:** enhancement
**Summary:** Add safe regular-user impersonation start flow to the Application admin page.

**Current behavior:**
The Application admin page can list, search, and paginate Better Auth users, change single-valued application roles, and ban or unban accounts. The page does not yet let an Application admin start impersonating an eligible regular user.

Application admin authority is application-wide and separate from Workspace owner/admin membership. Impersonation should use Better Auth admin client utilities directly through the existing runtime auth client, not custom product admin routes.

**Desired behavior:**
Application admins should be able to start impersonating eligible regular users from the Application admin page through a deliberate confirmation flow. The confirmation should identify the target user and explain that the admin will leave the Admin page and enter that user's normal app experience.

The acting Application admin must not be able to impersonate their own account. Other Application admins must not be impersonation targets. Banned users must not be impersonation targets until unbanned.

After successful impersonation, the frontend should clear session-scoped Workspace, Template, and Document UI state, refetch the authenticated session, and move to the Workspace page so normal Workspace resolution runs for the impersonated user. The admin user list should not be reloaded after successful impersonation because the session changes and the admin leaves the page.

**Key interfaces:**
- Existing runtime auth client — use Better Auth admin client utilities for starting impersonation; do not add custom `/v1/admin/*` product routes.
- Application admin page state — should own impersonation confirmation, mutation state, eligibility guards, and success/failure feedback locally within the admin feature.
- Application admin user rows — should expose an impersonation action only for eligible regular users, while preventing self-impersonation, admin-to-admin impersonation, and banned-user impersonation.
- Session-scoped UI clearing — should clear Workspace, Template, and Document browser state before moving into the impersonated user's normal Workspace experience.
- Auth session refresh — should refetch the Better Auth session after impersonation so the SPA uses the impersonated session consistently.

**Acceptance criteria:**
- [ ] Eligible regular users have an impersonation action that requires confirmation before calling Better Auth admin utilities.
- [ ] The confirmation names the target user and explains that the admin will leave the Admin page for that user's normal app experience.
- [ ] The acting Application admin cannot impersonate their own account.
- [ ] Other Application admins cannot be impersonated.
- [ ] Banned users cannot be impersonated until unbanned.
- [ ] Successful impersonation clears session-scoped Workspace, Template, and Document UI state.
- [ ] Successful impersonation refetches the authenticated session and moves the SPA to the Workspace page.
- [ ] Successful impersonation does not reload the admin user list.
- [ ] Failed impersonation shows recoverable failure feedback without losing the current admin list state.
- [ ] Focused frontend coverage verifies target eligibility guards, confirmation behavior, state clearing, session refetch, Workspace navigation, and no admin-list reload after success.

**Out of scope:**
- Showing or stopping impersonation mode; that is covered by the follow-up impersonation indicator issue.
- Impersonating other Application admins.
- Impersonating banned users.
- Custom product `/v1/admin/*` routes.
- Custom admin audit logging.
- Workspace membership summaries or Workspace data management.
- Deleting users, creating users, setting passwords, or manually revoking sessions.
