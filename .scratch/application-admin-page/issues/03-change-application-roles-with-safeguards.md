# Change application roles with safeguards

Category: enhancement
Status: completed

## Parent

.scratch/application-admin-page/PRD.md

## What to build

Allow Application admins to change a user's single-valued Better Auth application role between `user` and `admin` from the user list. Role changes should use deliberate per-row actions with confirmation, protect the acting admin from self-demotion, reload the current list after success, and avoid custom session invalidation.

## Acceptance criteria

- [x] Regular users have a per-row `Make admin` action that requires confirmation before calling Better Auth admin utilities.
- [x] Application admins have a per-row `Remove admin` action that uses stronger confirmation language before calling Better Auth admin utilities.
- [x] The acting Application admin cannot demote their own application role.
- [x] Role changes reload the current user list after success and show Action toasts for success/failure.
- [x] Role changes do not trigger custom session invalidation.
- [x] The role UI does not introduce inline dropdown editing or multi-role management.
- [x] Focused frontend coverage verifies confirmation, self-demotion protection, list reload, and toast behavior.

## Agent Brief

**Category:** enhancement
**Summary:** Add safeguarded Application admin role-change actions to the Application admin page.

**Current behavior:**
The Application admin page can list, search, and paginate Better Auth users through the existing runtime auth client. The page shows each user's application role, but Application admins cannot yet change another user's single-valued Better Auth application role from the UI.

Application admin authority is application-wide and separate from Workspace owner/admin membership. Role changes must continue to use Better Auth admin utilities directly rather than custom product admin routes.

**Desired behavior:**
Application admins should be able to promote regular users to Application admin and remove Application admin authority from other admins using deliberate per-row actions. Each action should require confirmation before calling Better Auth admin utilities.

Removing Application admin authority should use stronger confirmation language than promotion because it revokes global account-management access. An acting Application admin must not be able to demote their own application role. Successful role changes should reload the current user list and show an Action toast. Failed role changes should show an Action toast without losing the current list state.

Role changes should not perform custom session invalidation in this slice. The UI should keep single-valued `user` / `admin` semantics and must not introduce inline dropdown role editing or multi-role management.

**Key interfaces:**
- Existing runtime auth client — use Better Auth admin client utilities for role changes; do not add custom `/v1/admin/*` product routes.
- Application admin page state — should own confirmation, mutation, reload, and error/success feedback locally within the admin feature.
- Application admin user rows — should expose per-row `Make admin` for regular users and `Remove admin` for other Application admins, while preventing self-demotion.
- Action toast behavior — should report success and failure outcomes consistently with existing frontend action feedback.

**Acceptance criteria:**
- [ ] Regular users have a per-row `Make admin` action that requires confirmation before calling Better Auth admin utilities.
- [ ] Application admins have a per-row `Remove admin` action that uses stronger confirmation language before calling Better Auth admin utilities.
- [ ] The acting Application admin cannot demote their own application role.
- [ ] Successful role changes reload the current user list and show an Action toast.
- [ ] Failed role changes show an Action toast and preserve recoverable admin page state.
- [ ] Role changes do not trigger custom session invalidation.
- [ ] The role UI does not introduce inline dropdown editing or multi-role management.
- [ ] Focused frontend coverage verifies confirmation, self-demotion protection, list reload, and toast behavior.

**Out of scope:**
- Banning or unbanning users.
- Starting or stopping impersonation.
- Deleting users, creating users, setting passwords, or manually revoking sessions.
- Workspace membership summaries or Workspace data management.
- Custom product `/v1/admin/*` routes.
- Custom admin audit logging.
- Inline role dropdowns or multi-role Better Auth UI.
