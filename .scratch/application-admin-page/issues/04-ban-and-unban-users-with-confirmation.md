# Ban and unban users with confirmation

Category: enhancement
Status: completed

## Parent

.scratch/application-admin-page/PRD.md

## What to build

Allow Application admins to permanently ban users with a required reason and unban users with confirmation. Banning should affect Better Auth account access only, not Workspace memberships or Workspace API keys. Self-ban should be blocked, while banning another Application admin should be possible with explicit confirmation.

- [x] Unbanned users have a ban action that opens a confirmation modal with a required free-text reason field.
- [x] Missing ban reason is handled as recoverable inline validation and does not call Better Auth admin utilities.
- [x] Banned users have an unban action that opens a confirmation modal showing the user's email and existing ban reason.
- [x] The acting Application admin cannot ban their own account.
- [x] Banning another Application admin is allowed only through explicit confirmation.
- [x] Temporary ban duration is not exposed in the first slice.
- [x] Ban and unban operations reload the current user list after success and show Action toasts for success/failure.
- [x] Focused frontend coverage verifies required reason validation, self-ban protection, admin-to-admin confirmation, unban confirmation content, list reload, and toast behavior.

## Agent Brief

**Category:** enhancement
**Summary:** Add permanent ban and unban account actions to the Application admin page.

**Current behavior:**
The Application admin page can list, search, and paginate Better Auth users and can change single-valued application roles with confirmation. The user list already displays each user's banned status and ban reason when available, but Application admins cannot yet ban or unban accounts from the UI.

Application admin authority is application-wide and separate from Workspace owner/admin membership. Banning a user must affect Better Auth account access only; it must not delete Workspace memberships, rotate Workspace API keys, expose Workspace data, or introduce custom product admin routes.

**Desired behavior:**
Application admins should be able to permanently ban unbanned users through a deliberate confirmation flow with a required free-text reason. Missing reasons should be handled as recoverable inline validation before calling Better Auth admin utilities.

Banned users should have an unban action with confirmation that identifies the target user's email and shows the existing ban reason. The acting Application admin must not be able to ban their own account. Banning another Application admin should remain possible, but only after explicit confirmation that makes the elevated target account clear.

Successful ban and unban operations should reload the current user list and show Action toasts. Failed ban and unban operations should show failure Action toasts while preserving recoverable admin page state. Temporary ban duration should not be exposed in this first slice.

**Key interfaces:**
- Existing runtime auth client — use Better Auth admin client utilities for ban and unban operations; do not add custom `/v1/admin/*` product routes.
- Application admin page state — should own confirmation, ban reason input, inline validation, mutation state, reload behavior, and success/failure feedback locally within the admin feature.
- Application admin user rows — should expose ban actions for active users, unban actions for banned users, self-ban protection for the acting admin, and explicit admin-to-admin ban confirmation.
- Action toast behavior — should report ban and unban success/failure consistently with existing frontend action feedback.

**Acceptance criteria:**
- [ ] Unbanned users have a ban action that opens a confirmation modal with a required free-text reason field.
- [ ] Missing ban reason is handled as recoverable inline validation and does not call Better Auth admin utilities.
- [ ] Banned users have an unban action that opens a confirmation modal showing the user's email and existing ban reason.
- [ ] The acting Application admin cannot ban their own account.
- [ ] Banning another Application admin is allowed only through explicit confirmation.
- [ ] Temporary ban duration is not exposed in the first slice.
- [ ] Successful ban and unban operations reload the current user list and show success Action toasts.
- [ ] Failed ban and unban operations show failure Action toasts and preserve recoverable admin page state.
- [ ] Focused frontend coverage verifies required reason validation, self-ban protection, admin-to-admin confirmation, unban confirmation content, list reload, and toast behavior.

**Out of scope:**
- Temporary bans or ban expiry configuration.
- Deleting users, creating users, setting passwords, or manually revoking sessions.
- Workspace membership summaries, Workspace data management, or Workspace API key rotation.
- Custom product `/v1/admin/*` routes.
- Custom admin audit logging.
- Custom banned-user sign-in messages.
- Role changes, impersonation, or stopping impersonation.
