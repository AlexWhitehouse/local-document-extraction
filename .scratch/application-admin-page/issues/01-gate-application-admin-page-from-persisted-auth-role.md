# Gate the Application admin page from persisted auth role

Category: enhancement
Status: completed

## Parent

.scratch/application-admin-page/PRD.md

## What to build

Add the Better Auth admin plugin setup, explicit admin plugin schema migration, safe one-time Application admin role promotion, existing auth-client admin plugin integration, and initial Admin page shell. The Admin page should be visible only to users whose resolved authenticated session has the persisted `admin` application role, while non-admin users see no Admin sidebar item and experience no content layout shift from admin visibility checks.

## Acceptance criteria

- [ ] Better Auth admin plugin fields are added through a forward migration, including safe one-time promotion of the known initial Application admin users when they exist.
- [ ] Better Auth admin plugin is configured without config-based `adminUserIds`, and the existing runtime auth client includes the admin client plugin.
- [ ] The authenticated layout derives Application admin visibility from the resolved session role before rendering the main layout.
- [ ] Application admins see an Admin sidebar item with no count badge; non-admin users do not see the item.
- [ ] A non-admin state that attempts to show the Application admin page returns to the Workspace page rather than rendering an unauthorized admin view.
- [ ] The Application admin page shell preserves the app layout, uses admin-specific context sidebar content, and does not render workspace-specific toolbar content.
- [ ] Backend configuration coverage verifies admin plugin setup and Better Auth synthetic user responses include admin plugin fields.
- [ ] Frontend coverage verifies admin visibility, non-admin fallback, and absence of non-admin layout shift.

## Agent Brief

**Category:** enhancement
**Summary:** Gate the Application admin page from the persisted Better Auth application role and establish the Better Auth admin plugin foundation.

**Current behavior:**
Document Extraction has no Application admin page. The SPA only exposes Workspace, Template, and Document pages. Application-wide account administration is not available, Better Auth's admin plugin fields are not present in the D1 schema, and the runtime auth client does not expose Better Auth admin utilities.

Workspace owner/admin membership already exists, but that role is workspace-scoped and must not grant application-wide account management authority.

**Desired behavior:**
The first Application admin slice should establish the account-admin foundation without exposing full user-management actions yet.

Users whose resolved Better Auth session has application role `admin` should see an Admin sidebar item. Users without that persisted application role should not see the Admin item and should not experience a content layout shift while admin visibility is determined. If frontend state somehow attempts to show the Admin page for a non-admin user, the app should return to the Workspace page rather than rendering an unauthorized admin view.

The Admin page shell should preserve the app's established layout, show admin-specific account-management context in the context sidebar, and avoid workspace-specific toolbar content. It can be a placeholder/shell at this stage; user listing and mutations are handled by later issues.

The backend should configure Better Auth's admin plugin, add the required persisted admin plugin fields through an explicit forward migration, and safely promote the known initial Application admin users to persisted application role `admin` when those users exist. The migration must not fail if either known user ID is absent. Better Auth should not be configured with `adminUserIds`; the source of truth for UI visibility is the persisted user role.

Because email/password auth requires Account email verification, Better Auth synthetic user responses should include the admin plugin fields so synthetic and real user shapes remain aligned.

**Key interfaces:**
- Better Auth configuration should include the admin plugin without config-based admin user IDs.
- Better Auth email/password synthetic user shape should include the admin plugin user fields with defaults for regular users.
- Better Auth user persistence should have admin plugin fields for application role, ban state, ban reason, and ban expiry.
- Better Auth session persistence should have the admin plugin impersonation source field.
- The existing runtime auth client should include the Better Auth admin client plugin while preserving existing base URL and credentials behavior.
- The SPA's authenticated layout should derive Application admin visibility from the resolved session's persisted application role using exact single-role semantics: only `admin` is admin.
- The app navigation model should include an Admin page only for Application admins and should not introduce URL routing in this slice.

**Acceptance criteria:**
- [ ] Better Auth admin plugin fields are added through a forward migration, including safe one-time promotion of the known initial Application admin users when they exist.
- [ ] The migration is safe when either known initial Application admin user ID does not exist.
- [ ] Better Auth admin plugin is configured without config-based `adminUserIds`.
- [ ] Better Auth synthetic user responses include admin plugin fields with regular-user defaults.
- [ ] The existing runtime auth client includes the Better Auth admin client plugin.
- [ ] The authenticated layout derives Application admin visibility from the resolved session role before rendering the main layout.
- [ ] Application admins see an Admin sidebar item with no count badge.
- [ ] Non-admin users do not see the Admin sidebar item and do not experience a content layout shift from admin visibility checks.
- [ ] A non-admin state that attempts to show the Application admin page returns to the Workspace page rather than rendering an unauthorized admin view.
- [ ] The Application admin page shell preserves the app layout, uses admin-specific context sidebar content, and does not render workspace-specific toolbar content.
- [ ] Backend configuration coverage verifies admin plugin setup and Better Auth synthetic user responses include admin plugin fields.
- [ ] Frontend coverage verifies admin visibility, non-admin fallback, and absence of non-admin layout shift.

**Out of scope:**
- User listing, searching, and pagination.
- Application role mutation actions.
- Ban and unban actions.
- Impersonation start/stop behavior.
- Workspace membership summaries or Workspace data management.
- Custom product `/v1/admin/*` routes.
- Custom admin audit logging.
- URL routing for the Admin page.
- Showing Better Auth user IDs in the admin UI.
