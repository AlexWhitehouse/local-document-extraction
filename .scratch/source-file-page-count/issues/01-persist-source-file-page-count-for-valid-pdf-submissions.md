# Persist Source file page count for valid PDF submissions

Category: enhancement
Status: completed

## Parent

.scratch/source-file-page-count/PRD.md

## What to build

Add the first end-to-end path for **Source file page count** on valid PDF Document submissions. A valid PDF should have its page count computed during Document submission, before queued **Extraction job** creation, and that count should be persisted as nullable internal **Source file** metadata in authoritative **Workspace product data**.

Use a small backend PDF page-counting module backed by `pdf-lib`, with a narrow interface that accepts PDF bytes and returns a positive integer page count. The Document submission path should call that module for PDF Source files after reading the submitted bytes, pass the resulting count into queued Extraction job creation, and preserve the existing successful queued response contract.

The Workspace product store should add lazy, idempotent schema support for a nullable page-count column on Source file metadata and persist the count in the same durable operation that creates the queued Extraction job. This slice only needs to prove the valid-PDF path; invalid-PDF rejection and non-PDF boundary hardening are covered by follow-up issues.

## Agent Brief

**Category:** enhancement
**Summary:** Persist internal Source file page count metadata for valid PDF Document submissions.

**Current behavior:**
PDF Document submissions are accepted when they pass the existing request, Template, MIME type, and byte-size checks. The backend reads the submitted Source file bytes, stores the Source file binary, creates a queued Extraction job in authoritative Workspace product data, sends the processing queue message, and returns the existing queued response shape. The durable Source file metadata records key, MIME type, name, creation time, and cleanup state, but it does not record how many pages the PDF contains.

**Desired behavior:**
For valid PDF Source files, Document submission should compute Source file page count after the submitted bytes have been read and before queued Extraction job creation. The computed count should be a positive integer owned by the backend, passed explicitly into queued Extraction job creation as nullable Source file metadata, and persisted with Source file metadata in the same durable operation that creates the queued Extraction job.

The page counting should be implemented behind a small backend module backed by `pdf-lib`. Valid one-page and multi-page PDFs should return the correct page count through that module. This slice only needs to prove the valid-PDF path; invalid-PDF rejection behavior and broader non-PDF boundary hardening are covered by follow-up issues.

The successful queued response, queue message contract, Workflow params, Workspace live update payloads, Workspace product analytics payloads, and public Extraction job list/detail contracts should remain unchanged.

**Key interfaces:**
- PDF page-counting module — accepts PDF bytes and returns a positive integer Source file page count for valid PDFs.
- Queued Extraction job creation input — accepts explicit nullable Source file page count metadata from the submission route.
- `createQueuedExtractionJob()` — persists Source file page count with Source file metadata while creating the queued Extraction job.
- Workspace product store schema migration — adds a nullable Source file page-count column and upgrades existing stores lazily and idempotently.
- Backend dependency manifest and lockfile — include `pdf-lib` for the Worker runtime.
