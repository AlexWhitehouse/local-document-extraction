# Reject uncountable PDF Source files before side effects

Category: enhancement
Status: completed

## Parent

.scratch/source-file-page-count/PRD.md

## What to build

Complete the PDF failure path for **Source file page count**. When a submitted PDF passes the existing upload request checks but the backend cannot determine its page count, Document submission should be rejected as bad input before any durable side effects occur.

The page-counting module should normalize PDF parse/load/library failures into a stable application-level invalid-PDF failure, and the Document submission route should translate that failure into a clear rejected request response. Invalid PDFs must not upload a Source file to R2, create a queued **Extraction job**, send a background processing message, or emit Workspace product analytics.

## Acceptance criteria

- [x] The page-counting module returns or throws a stable invalid-PDF failure for malformed PDF bytes.
- [x] Document submission rejects a PDF when Source file page count cannot be determined.
- [x] The rejected response is a request error suitable for invalid input.
- [x] Invalid PDF submission does not upload the Source file to R2.
- [x] Invalid PDF submission does not create a queued Extraction job.
- [x] Invalid PDF submission does not send a background processing message.
- [x] Invalid PDF submission does not emit Workspace product analytics.
- [x] The implementation does not leak library-specific parse errors into the public response.
- [x] Focused tests cover malformed PDF bytes at the page-counting module boundary and the public Document submission route boundary.
- [x] `npm run typecheck --prefix backend` passes.

## Agent Brief

**Category:** enhancement
**Summary:** Reject uncountable PDF Source files during Document submission before durable side effects occur.

**Current behavior:**
Valid PDF Document submissions already compute Source file page count during submission and pass that metadata into queued Extraction job creation. However, when the backend cannot parse or load a submitted PDF, the page-counting dependency failure is not normalized into a stable application-level invalid-PDF failure. That means malformed PDF bytes can escape through the generic error path instead of producing a clear rejected request response, and the failure contract at the page-counting boundary is not yet durable.

**Desired behavior:**
When a submitted PDF passes the existing request checks but its Source file page count cannot be determined, Document submission should be rejected as invalid input before any durable side effects occur. PDF parse, load, or library failures should be converted into a stable invalid-PDF failure by the page-counting module. The public Document submission route should translate that stable failure into a request error suitable for bad input, without leaking dependency-specific error details.

Malformed PDF submissions must not upload the Source file binary, create a queued Extraction job, send a background processing message, or emit Workspace product analytics. Existing successful behavior for valid PDFs should remain unchanged.

**Key interfaces:**
- `countPdfSourceFilePages()` — should return a positive Source file page count for valid PDFs and expose a stable invalid-PDF failure for malformed or uncountable PDF bytes.
- Invalid-PDF failure shape — should be application-owned, testable, and independent of `pdf-lib` error messages or classes.
- Document submission route — should translate the invalid-PDF failure into a clear invalid-input HTTP response before R2 upload, queued Extraction job creation, queue send, or analytics emission.
- Workspace product analytics emission — should remain successful-submission-only for this failure path.

**Acceptance criteria:**
- [x] Malformed PDF bytes produce the stable invalid-PDF failure at the page-counting module boundary.
- [x] PDF parse, load, and library errors do not leak through public response messages.
- [x] Document submission rejects an uncountable PDF as an invalid-input request error.
- [x] Rejected uncountable PDF submission does not upload the Source file to binary storage.
- [x] Rejected uncountable PDF submission does not create a queued Extraction job.
- [x] Rejected uncountable PDF submission does not send a background processing message.
- [x] Rejected uncountable PDF submission does not emit Workspace product analytics.
- [x] Existing valid PDF submission behavior, including Source file page count persistence and queued response shape, remains unchanged.
- [x] Focused tests cover malformed PDF bytes at the page-counting module boundary and the public Document submission route boundary.
- [x] `npm run typecheck --prefix backend` passes.

**Out of scope:**
- Changing supported Source file MIME types or byte-size validation.
- Changing non-PDF Source file behavior.
- Exposing Source file page count through public API responses, live updates, analytics, queue messages, Workflow params, or frontend UI.
- Enforcing page-based limits, pricing, billing, quota, or reporting.
- Backfilling historical Source file page counts.
- Moving PDF parsing into the Workspace Durable Object.
