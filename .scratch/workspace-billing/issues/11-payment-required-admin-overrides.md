# Payment-Required Admin Overrides

Category: enhancement
Type: AFK
Status: completed

## Parent

.scratch/workspace-billing/PRD.md

## What to build

Allow Application admins to create payment-required Free/Pro/Max Plan overrides. The override should create an owner-visible Stripe invoice, use automatic collection when a default payment method exists or hosted/manual payment otherwise, and activate the target entitlement only after the required invoice is paid.

## Acceptance criteria

- [x] Application admins can create a payment-required Plan override targeting Free, Pro, or Max with start, end, reason, and creating admin.
- [x] A payment-required Plan override creates an owner-visible Stripe invoice for the Workspace.
- [x] Payment-required override invoices use automatic collection by default when the Workspace has a default payment method.
- [x] Payment-required override invoices can be paid manually by the Workspace owner through the billing page when automatic collection is unavailable.
- [x] Application admins can select manual invoice collection when needed.
- [x] Paid override entitlements activate only after the required invoice is paid.
- [x] Unpaid payment-required overrides do not grant paid entitlements or Included Credits.
- [x] Override invoice status appears in owner Billing page and Application admin billing view.
- [x] Stripe invoice items use explicit amounts derived from the override terms.
- [x] Stripe API writes use idempotency keys and webhook events are processed idempotently.
- [x] Application admin billing audit log records override creation and payment state changes.
- [x] Tests cover invoice creation, automatic/manual collection mode, paid activation, unpaid non-activation, owner visibility, admin visibility, duplicate webhook handling, and audit logging.
- [x] `npm run typecheck --prefix backend` and `npm run build --prefix frontend` pass.

## Agent Brief

**Category:** enhancement
**Summary:** Add payment-required Application admin Plan overrides that create owner-visible Stripe invoices and activate only after payment.

**Current behavior:**
Workspace billing already supports the Free/Pro/Max catalog, owner Billing page summaries, Workspace billing authority, Billing ledger credit grants/reservations, Stripe-backed Credit pack purchases, self-service Pro/Max subscription flows, subscription unpaid state, deletion billing guards, no-payment Application admin Plan overrides, No-billing mode, and Application admin billing audit entries.

Application admins can currently create no-payment Plan overrides for Free, Pro, or Max. Those overrides activate immediately and grant Included Credits for covered Billing periods when applicable. There is no payment-required override model, no admin-created override invoice state, no owner-visible payment link for such invoices, and no webhook path that activates an admin-created Plan override from a paid custom invoice.

**Desired behavior:**
Application admins should be able to create a payment-required Plan override for Free, Pro, or Max with start time, end time, reason, creating admin, invoice collection mode, and an explicit tax-exclusive GBP invoice amount. The explicit amount is part of the override's commercial terms; it should be used to create Stripe invoice items rather than creating new Stripe Prices for each override. Payment-required overrides with a non-positive invoice amount should be rejected; zero-cost grants should continue to use the existing no-payment Plan override path.

Creating a payment-required override should create a Stripe Customer for the Workspace if one does not already exist, then create an owner-visible Stripe invoice for the explicit amount. Automatic collection should be the default when the Workspace has a Stripe default payment method. If automatic collection cannot be used because no default payment method exists, the owner should be able to pay via a hosted Stripe invoice payment page. Application admins should also be able to force manual invoice collection when needed.

The target Plan override must not become the Active entitlement and must not grant Included Credits until the required invoice is paid. Unpaid, failed, voided, or otherwise incomplete override invoices should remain visible as invoice state but should not grant paid entitlements, Included Credits, API access, or plan limits. When the invoice is paid, the override should activate for its configured time window, respect the existing Active entitlement precedence, grant target-plan Included Credits idempotently for the covered current Billing period when applicable, and write audit/activity records. If No-billing mode is active, it remains higher precedence; the paid override can be recorded but should only affect the Active entitlement when it is the highest applicable entitlement.

Owner-facing billing surfaces should show payment-required override invoice status, amount, collection mode, and hosted payment URL when payment is needed, without exposing internal admin notes, raw Stripe identifiers, or Application admin audit details. The Application admin billing view should show the pending/paid/failed override invoice state, collection mode, actor, reason, payment status, and audit entries needed for support/commercial follow-up.

Only one pending payment-required Plan override should be allowed per Workspace at a time. If a pending payment-required override invoice already exists, creating another should fail with a clear conflict error rather than silently replacing commercial terms.

**Key interfaces:**
- Workspace billing control data should be able to represent pending and paid payment-required Plan override terms separately from immediately-active no-payment overrides.
- Active entitlement resolution should activate payment-required Plan overrides only after invoice payment and should preserve the established precedence of No-billing mode above Plan overrides, then Enterprise, self-service subscription, and Free.
- Billing period and Included Credit grant behavior should grant target-plan Included Credits only after payment, and should be idempotent for the same Workspace, override, target plan, and Billing period.
- Stripe billing gateway behavior should support creating explicit invoice items, finalizing owner-visible invoices, choosing automatic or manual collection, returning hosted invoice payment URLs when available, and applying Stripe API idempotency keys to every write.
- Stripe billing webhook handling should recognize payment-required override invoices by metadata, process paid/failed/voided events idempotently, and avoid double-activating overrides or double-granting Included Credits on duplicate webhook delivery.
- Owner Billing page contracts should expose customer-facing override invoice status and payment actions without raw Stripe IDs or admin-only notes.
- Application admin billing API and UI contracts should expose creation controls for payment-required overrides, invoice collection mode selection, invoice status, and audit history.
- Application admin billing audit log entries should capture override creation and payment state changes with actor, timestamp, reason, before/after values, Workspace, and invoice status transition.

**Acceptance criteria:**
- [x] Application admins can create a payment-required Plan override targeting Free, Pro, or Max with start time, end time, reason, creating admin, explicit positive tax-exclusive GBP invoice amount, and collection mode.
- [x] Payment-required override creation rejects invalid target plans, invalid date ranges, missing reasons, missing idempotency keys, non-positive invoice amounts, and duplicate pending payment-required overrides for the same Workspace.
- [x] A payment-required Plan override creates an owner-visible Stripe invoice for the Workspace, using explicit invoice items derived from the override's commercial terms.
- [x] Stripe API writes for Customer creation/reuse, invoice item creation, invoice creation/finalization/payment attempts, and any related state changes use stable idempotency keys.
- [x] Automatic invoice collection is used by default when the Workspace has a Stripe default payment method.
- [x] If automatic collection is unavailable because no default payment method exists, the invoice exposes a hosted Stripe payment URL that the Workspace owner can open from the Billing page.
- [x] Application admins can force manual invoice collection even when automatic collection would otherwise be possible.
- [x] Unpaid, failed, voided, or incomplete payment-required override invoices do not activate the target Plan override, do not grant Included Credits, and do not unlock paid/API entitlements.
- [x] Paid payment-required override invoices activate the target Plan override for the configured time window and grant target-plan Included Credits idempotently when applicable.
- [x] Duplicate Stripe webhook delivery for the same override invoice is acknowledged without duplicate audit entries that imply a second transition, duplicate activation, or duplicate Included Credit grants.
- [x] Override invoice status, amount, collection mode, and hosted payment action appear on the owner Billing page without exposing raw Stripe identifiers or admin-only notes.
- [x] Override invoice status, amount, collection mode, actor, reason, and audit history appear in the Application admin billing view.
- [x] Application admin billing audit log records payment-required override creation and invoice payment state changes.
- [x] Tests cover invoice creation, automatic collection, manual/hosted payment collection, paid activation, unpaid non-activation, duplicate pending override rejection, duplicate webhook handling, owner visibility, admin visibility, and audit logging.
- [x] `npm run typecheck --prefix backend` and `npm run build --prefix frontend` pass.

**Out of scope:**
- Enterprise ramp-up, Enterprise annual commitments, Enterprise overage invoices, and Enterprise invoice review mode.
- Billing reconciliation for missed or drifted payment-required override invoices beyond the webhook idempotency needed in this slice.
- Refunding paid override invoices, issuing credit notes, or voiding/canceling pending payment-required override invoices from the application.
- Editing an existing pending payment-required override after invoice creation.
- Changing the code-owned Free/Pro/Max plan catalog, public plan prices, Credit pack catalog, or self-service subscription flows except where payment-required override entitlement precedence must account for them.
- Exposing raw Stripe identifiers, payment method details, internal admin notes, or Application admin audit details on owner-facing billing surfaces.
