## What to build

Add scheduled Billing reconciliation to compare Stripe billing state, D1 billing control data, and Workspace billing ledger summaries. Reconciliation should catch missed webhooks, stale unpaid states, ungranted Included Credits, invoice status drift, and projection drift. It must be idempotent, avoid blindly rewriting ledger history, and record or surface drift for follow-up.

## Agent Brief

**Category:** enhancement
**Summary:** Add idempotent scheduled Billing reconciliation for Stripe, billing control data, and the Billing ledger.

**Current behavior:**
Workspace billing has a Stripe-backed owner and admin billing model with processed Stripe billing event records, idempotent webhook processing, Workspace billing control data, and an append-only Billing ledger. The scheduled Worker entry point is already used for Enterprise invoice generation, but there is no dedicated Billing reconciliation pass.

Missed webhooks, stale unpaid state, mismatched Stripe invoice status, inconsistent processed Stripe billing event records, ungranted paid Credits, and projection drift are not currently detected by a scheduled operational workflow. Application admins also do not have a reconciliation drift/status surface for follow-up.

This issue assumes the earlier billing slices for Credit packs, Pro/Max subscriptions, subscription changes and unpaid state, payment-required overrides, Enterprise ramp-up, and Enterprise annual commitments are already implemented or completed before reconciliation is picked up.

**Desired behavior:**
The backend should run a scheduled, idempotent Billing reconciliation operation that compares Stripe billing state with Workspace billing control records and Billing ledger summaries. It should detect drift across subscription invoices, Credit pack payments, payment-required Plan override invoices, Enterprise ramp-up invoices, Enterprise annual upfront invoices, and Enterprise annual overage invoices.

When reconciliation finds a clearly safe repair, such as a paid Stripe invoice or Checkout payment whose product-side entitlement or Credit grant can be applied with stable Stripe references and existing idempotency keys, it should repair that state without duplicating ledger entries, grants, invoices, or entitlement changes. When reconciliation finds ambiguous drift, such as conflicting invoice metadata, inconsistent processed event records, missing Workspace mapping, or a ledger projection mismatch that cannot be safely repaired, it should record a durable drift/status item for Application admin follow-up rather than rewriting history.

Billing ledger history must remain append-only. Reconciliation may rebuild or compare projections and may add safe compensating or missing entries through existing ledger authority, but it must not mutate or delete historical ledger entries.

**Key interfaces:**
- Scheduled billing operation - should invoke Billing reconciliation alongside existing scheduled billing work and remain safe under duplicate scheduled runs.
- Stripe billing gateway - should support read-only retrieval of relevant invoices, Checkout Sessions, subscriptions, and payment status needed for reconciliation, using Stripe identifiers already stored in billing control data and event records.
- Billing control store - should expose Workspace billing control records, invoice references, subscription references, processed Stripe billing event records, and any new reconciliation drift/status records.
- Processed Stripe billing event records - should be checked for missing, failed, or inconsistent entries where the related Stripe object can be resolved.
- Billing ledger RPC surface - should support idempotent safe grants or repairs using stable Stripe references and should expose enough summary/projection data to compare credit balances and current-period usage without mutating historical entries.
- Active entitlement resolver - should remain the source of entitlement interpretation after reconciliation repairs billing control state.
- Application admin billing view - should expose reconciliation status, drift records, last checked time, severity/actionability, and enough context for operational follow-up without exposing owner-only payment controls in the wrong surface.
