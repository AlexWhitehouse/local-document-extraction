## Agent Brief

**Category:** enhancement
**Summary:** Harden owner-facing and Application admin billing UX after the core Workspace billing paths exist.

**Current behavior:**
Workspace billing has been split into focused backend and frontend slices. The product has Workspace-scoped billing summaries, Active entitlement resolution, Credit balances, Plan page capacity, owner-only billing access, limited Billing operational status for non-owner members, Stripe-hosted payment flows, self-service subscription lifecycle state, Application admin billing controls, Enterprise billing states, and billing reconciliation state.

The owner Billing page, Application admin billing view, blocked-upload affordances, invoice links, Checkout returns, and billing action feedback exist in functional form, but they are still implementation-oriented. States can be dense, uneven, or ambiguous for the people using them. The remaining work is UX hardening and privacy hardening, not new billing policy.

**Desired behavior:**
Workspace owners should have a Billing page that explains the current Active entitlement, scheduled changes, Credit balance, remaining page capacity, Included Credit renewal, current-period usage, invoices, payment setup, Credit pack actions, subscription actions, Enterprise invoice actions when relevant, and Owner billing activity in a clear customer-facing way.

Owner-facing billing surfaces must never reveal internal admin notes, raw Stripe identifiers, reconciliation internals, Application admin billing audit details, or payment method internals. Owner Billing activity should remain customer-facing and should distinguish Credits, invoice/payment events, refunds/corrections, subscription changes, and Enterprise billing events without exposing backend implementation details.

Non-owner Workspace members should not see Billing page navigation or owner-only billing controls. When billing blocks product actions, non-owner members may see only limited Billing operational status that explains the blocked action without invoices, exact paid prices, payment methods, owner controls, internal audit notes, or raw provider identifiers.

Document upload should use advisory billing entitlement summaries to disable obviously blocked submissions before file selection. Final backend billing rejection after exact PDF page count should remain authoritative and should produce actionable inline feedback or Action toasts that help the user understand what happened. Multi-file upload should preserve per-file success and failure states.

Stripe Checkout, subscription changes, portal links, hosted invoice links, and billing refresh after return should have clear loading, success, cancellation, and failure states. Billing actions should use existing Action toast patterns or inline validation consistently. The UI should fit the existing app layout and responsive constraints without adding new billing domain rules.

Application admins should have a coherent billing management view for Plan overrides, No-billing mode, Goodwill Credits, payment-required overrides, Enterprise ramp-up, Enterprise annual commitments, invoice state, collection mode, invoice review mode, audit entries, and reconciliation drift/status. Admin-facing surfaces may expose operational and audit context appropriate to Application admins, but should make owner-facing and admin-facing concepts visually and semantically distinct.

**Key interfaces:**
- Owner Billing summary contract - should expose only customer-facing billing fields needed for entitlement, Credits, page capacity, renewal, invoices, hosted payment actions, subscription actions, and Owner billing activity.
- Billing operational status contract - should stay intentionally limited for non-owner Workspace members and should be safe to show near blocked product actions.
- Document upload flow - should consume advisory billing state before file selection and handle authoritative backend billing rejection after page count without losing per-file queue state.
- Billing action controller - should represent loading, success, cancellation, return-from-Stripe refresh, and failure states for Checkout, subscription, portal, and hosted invoice actions.
- Application admin billing contract - should organize admin-only Workspace billing controls, commercial terms, invoice state, audit information, and reconciliation drift/status without mixing them into owner-facing activity.
- Action toast system - should include billing-specific success, validation, cancellation, and failure messages where inline validation is not the clearer choice.
- Frontend tests - should cover visibility boundaries, blocked upload behavior, owner activity privacy, admin billing controls, invoice/Checkout/Portal states, responsive/error states, and important regression paths.

**Acceptance criteria:**
- [ ] Owner Billing page presents Active entitlement, scheduled changes, available Credits, remaining page capacity, Included Credit renewal, current-period usage, invoices, payment setup, Credit pack actions, subscription actions, Enterprise invoice actions when applicable, and Owner billing activity clearly.
- [ ] Owner Billing page separates available Credits from remaining page capacity and makes the active blocking reason understandable when one exists.
- [ ] Owner Billing page never exposes internal admin notes, raw Stripe identifiers, reconciliation internals, Application admin billing audit details, or payment method internals.
- [ ] Owner Billing activity is customer-facing and does not leak admin-only reasons, audit entries, raw provider IDs, or reconciliation drift details.
- [ ] Non-owner Workspace members never see Billing page navigation or owner-only billing controls.
- [ ] Non-owner blocked-action UI shows only limited Billing operational status and does not expose invoices, payment methods, exact prices paid, hosted payment links, owner controls, admin notes, or raw provider IDs.

**Out of scope:**
