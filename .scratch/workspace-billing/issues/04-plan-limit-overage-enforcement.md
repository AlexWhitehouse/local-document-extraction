# Plan Limit Overage Enforcement

Category: enhancement
Type: AFK
Status: completed

## Parent

## What to build

Enforce Free/Pro/Max plan resource limits without deleting existing over-limit data. The app should detect Template count, Workspace membership count, Template field count, table-shaped field count, table-column count, and API access entitlement, then block only the actions required by the PRD. Existing Templates, members, and API keys should remain visible and manageable.

This slice should make billing enforcement real even before paid subscriptions exist, using Free entitlement and manual Credit grants from prior slices.

## Agent Brief

**Category:** enhancement
**Summary:** Enforce Active entitlement resource limits and API access entitlement without deleting existing over-limit Workspace data.

**Current behavior:**
Workspace billing now has a code-owned Free/Pro/Max catalog, Free Active entitlement fallback, owner-only Billing page, limited Billing operational status, manual Goodwill Credit grants, and prepaid Credit/Plan page capacity enforcement before Document submission side effects. Document submissions reserve Credits and Plan page usage before Source file storage and queued Extraction job creation.

Resource-limit enforcement is still incomplete. Product actions do not consistently evaluate Template count, accepted Workspace membership count, table-shaped Template fields, Template object column count, or Workspace API access entitlement from the Active entitlement. Existing Template create/update behavior may still rely on legacy nullable Workspace limit columns and only simple top-level field counts. Workspace listing Billing operational status only reflects Credit/page-cap blockers. Workspace API key rotation is role-gated but not entitlement-gated, and existing Workspace API keys can authenticate product routes without an API access entitlement check.

**Desired behavior:**
The backend should evaluate Plan limit overage from the Workspace's Active entitlement and existing Workspace resources before accepting new product work. Existing over-limit Templates, Template fields, accepted Workspace memberships, and Workspace API keys must remain visible and manageable; enforcement should block only the actions required by the PRD.

Any Plan limit overage should block new Extraction jobs until the overage is resolved or the Active entitlement changes to limits that cover the Workspace. Too many Templates or too many accepted Workspace memberships should block all new Extraction jobs. Too many Templates should also block new Template creation. Too many accepted Workspace memberships should also block new Workspace invitations. Template-specific overages should block new Extraction jobs for only the over-limit Template. A table-shaped Template field counts as one top-level Template field, and table-shaped field count plus Template object column count must be enforced from the Template schema/metadata contract. Saving an over-limit Template should be allowed only when the saved version brings that Template back within the Active entitlement limits or when the Active entitlement already covers it.

Workspace API key generation/rotation should require active API access entitlement. Existing Workspace API keys should be preserved when API entitlement is inactive. Product API requests authenticated by an existing Workspace API key while API access is inactive should be rejected with a billing/entitlement error rather than an invalid-key error. Session-authenticated and API-key-authenticated product requests should receive the same billing entitlement and Plan limit overage enforcement for product actions, while owner-only billing details remain session-only and owner-only.

The frontend should consume limited Billing operational status to show blocked-action context without exposing owner-only billing details such as invoices, payment methods, exact prices paid, or billing controls. Backend enforcement remains authoritative.

**Key interfaces:**
- Active entitlement and plan catalog resolution — resource-limit checks should read Template, field, table-shaped field, table-column, member, monthly page, Credit, and API access limits from the resolved Active entitlement rather than ad hoc legacy Workspace columns.
- Plan limit overage evaluator — a reusable backend contract should identify Workspace-level blockers and Template-specific blockers for new Extraction jobs, Template creation, Template saving, Workspace invitations, and Workspace API key generation.
- Workspace product data API — Template list/detail/submission validation should expose or compute enough metadata to determine active Template count, top-level field count, table-shaped field count, and Template object column count without relying on deleted or archived data.
- Workspace control data API — accepted Workspace membership count and invitation creation should be checked against the Active entitlement's Plan member limit while preserving existing memberships and pending invitations.
- Product route authentication/authorization — Workspace API key authentication should distinguish "valid key but API access entitlement inactive" from "invalid key", and product routes should apply entitlement errors consistently for session and API-key callers.
- Billing operational status contract — Workspace listing and product surfaces may expose limited blocker labels/reasons, but owner-facing billing details stay confined to owner-authorized billing summary flows.
