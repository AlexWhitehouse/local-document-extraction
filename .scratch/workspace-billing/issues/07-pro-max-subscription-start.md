# Pro/Max Subscription Start

Category: enhancement
Type: AFK

## What to build

Add owner-initiated self-service subscription starts for Pro and Max through Stripe Checkout. A Free Workspace owner should be able to start Pro or Max, pay the first subscription invoice, and have paid entitlements and Included Credits activate only from successful Stripe payment/subscription events. Billing periods should follow Stripe's subscription billing cycle after subscription starts.

## Agent Brief

**Category:** enhancement
**Summary:** Add owner-initiated Pro and Max subscription starts through Stripe Checkout, with paid entitlements activated only after successful Stripe subscription payment events.

**Current behavior:**
Workspace billing has a Free entitlement foundation, a code-owned non-enterprise plan catalog for Free/Pro/Max, owner-only Billing page access, Workspace-scoped Stripe Customer mapping, Credit pack Checkout, signed Stripe webhook processing, processed Stripe billing event records, and Billing ledger support for Included Credit grants. The owner Billing page can show Credits and Credit pack purchase actions, but a Free Workspace owner cannot yet start a Pro or Max subscription. Billing summaries are still Free-entitlement based until subscription state is introduced.

The documented Stripe test-mode catalog and the Credit pack Stripe flow are complete enough for this slice to build against. Subscription starts should reuse those conventions rather than introduce a separate payment integration style.

**Desired behavior:**
A session-authenticated Workspace owner can choose Pro or Max from the owner Billing page and start a Stripe Checkout Session in subscription mode using the configured recurring Stripe Price for the selected plan. Workspace API keys and non-owner Workspace members cannot start subscription Checkout.

Starting Checkout must not activate paid entitlement or grant Included Credits. A Workspace becomes Pro or Max only after the first subscription invoice or payment event proves the subscription period has been paid. At that point the billing control state should record the active self-service subscription entitlement, Stripe subscription/customer references, subscription status, and Billing period anchor from Stripe. The Billing ledger should grant the plan's Included Credits for that paid Billing period exactly once, and those Included Credits should expire at that Billing period end.

Stripe webhook handling must remain signed and idempotent. Duplicate or out-of-order subscription events must not double-grant Included Credits or incorrectly move entitlement ahead of payment. Owner Billing summary responses and the owner Billing page should show the active Pro/Max entitlement, Included Credit renewal/current-period availability, current-period usage/capacity, and subscription status after payment is processed.

**Key interfaces:**
- Non-enterprise plan catalog - Pro and Max definitions provide recurring plan price expectations, Included Credit allowances, plan limits, API access, and monthly page limits.
- Workspace billing control data - should gain the durable Stripe subscription and active self-service subscription fields needed to resolve paid entitlement and Billing periods.
- Stripe Checkout Session creation - should support subscription mode, configured recurring Price IDs, Workspace metadata, automatic tax, Stripe Customer mapping, Stripe API idempotency keys, and no hardcoded `payment_method_types`.
- Stripe billing event processing - should handle subscription Checkout completion and invoice/payment events needed to activate paid entitlement only after payment, using processed event records for idempotency.
- Billing ledger Included Credit grants - should be called with a stable idempotency key derived from Stripe event/subscription/invoice references and the paid Billing period.
- Workspace billing summary API - should resolve active Free/Pro/Max entitlement from billing control state and ledger summaries rather than always returning Free.
- Owner Billing page/controller - should expose Pro and Max subscription start actions and render subscription status after payment.

**Acceptance criteria:**
- [x] Pro and Max subscription starts can be initiated only by the current Workspace owner using session auth.
- [x] Workspace API keys cannot start subscription Checkout or access owner-only subscription controls.
- [x] Subscription Checkout uses configured recurring Stripe Price IDs, the Workspace Stripe Customer, Workspace metadata, automatic tax where supported, Stripe API idempotency keys, and no hardcoded `payment_method_types`.
- [x] Starting Checkout does not activate Pro/Max entitlement or grant Included Credits before successful payment.
- [x] A paid first Pro subscription invoice activates Pro entitlement for the paid Billing period and grants exactly 200 Included Credits for that period.
- [x] A paid first Max subscription invoice activates Max entitlement for the paid Billing period and grants exactly 1,000 Included Credits for that period.
- [x] Paid non-enterprise Billing periods follow the Stripe subscription billing cycle after subscription start.
- [x] Included Credits granted for a subscription period expire at that Billing period end and are not counted in later periods.
- [x] Subscription-related Stripe events are processed idempotently, including duplicate webhook deliveries.
- [x] Owner Billing summary and owner Billing page show active Pro/Max entitlement, Included Credit availability/renewal, current-period usage/capacity, and subscription status after payment.
- [x] Tests cover subscription Checkout authorization, Stripe request shape, invoice-paid entitlement activation, Included Credit grant idempotency, Billing period anchor update, and owner UI state.
- [x] `npm run typecheck --prefix backend` and `npm run build --prefix frontend` pass.

**Out of scope:**
- Pro to Max upgrades, downgrades, cancellation, Customer Portal subscription management, and unpaid billing state beyond the first subscription payment gate.
- Credit pack purchase behavior, except where shared Stripe Customer, webhook, or billing summary code needs to stay compatible.
- Application admin Plan overrides, No-billing mode, Enterprise billing, reconciliation, and Workspace deletion billing guards.
- Creating or changing Stripe Dashboard Products/Prices or committing Stripe secrets.
