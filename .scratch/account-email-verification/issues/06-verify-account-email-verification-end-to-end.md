## Agent Brief

**Category:** enhancement
**Summary:** Verify Account email verification end to end and close integration gaps across Worker configuration, auth, email, Workspace bootstrap, and frontend messaging.

**Current behavior:**
The account email verification implementation has been split across completed slices for Cloudflare Email Sending configuration, generated Worker environment types, reusable transactional email rendering and scheduling, Better Auth verification behavior, post-verification personal **Workspace** bootstrap, and frontend auth messaging. The final integrated behavior still needs to be verified as one flow, and any gaps found while wiring those completed slices together should be fixed within the established scope.

**Desired behavior:**
Account email verification should work end to end for email/password users. Sign-up should send the verification email without granting usable application access or creating a personal **Workspace** too early. Unverified sign-in should be blocked while sending a fresh verification link and showing the agreed frontend message. Successful verification should return the user to the application root, sign them in automatically, and create a personal **Workspace** only when the user has no accepted **Workspace membership**. Verified Google social sign-in should remain a complete onboarding path without sending a separate Document Extraction verification email.

**Key interfaces:**
- Generated Wrangler Worker environment types — should include the `EMAIL` binding and remain the source of truth for platform binding shapes.
- Better Auth email verification configuration — should enforce required verification for email/password access, send verification emails on sign-up and unverified sign-in, return users to the application root, and automatically sign in after successful verification.
- Transactional email rendering and scheduling contracts — should render the agreed **Account email verification** email and schedule sends through Worker scheduling when available without blocking auth responses.
- Personal **Workspace** bootstrap policy — should create a personal **Workspace** only after **Account email verification** grants account access, remain idempotent, and ignore pending **Workspace invitations** when checking accepted access.
- Frontend auth flow — should show the **Account verification prompt** after email/password sign-up, avoid session or Workspace resolution before verification, and show the agreed unverified sign-in message.
- Verification commands — should include backend typecheck, relevant backend tests, relevant frontend tests or build verification, frontend production build, and documented local Cloudflare Email Sending verification status.

**Acceptance criteria:**
- [x] Backend typecheck passes with generated Wrangler Worker types.
- [x] Relevant backend tests pass for email rendering, scheduling, auth verification behavior, Worker configuration, and post-verification **Workspace** bootstrap.
- [x] Relevant frontend tests or build verification pass for the auth flow changes.
- [x] Frontend production build passes.
- [x] Local development behavior for real Cloudflare Email Sending is verified or clearly documented for manual verification.
- [x] Any integration gaps found during verification are fixed without changing the established Account email verification product rules.

**Out of scope:**
- Password reset email sending or forgot-password frontend flow.
- Workspace invitation emails or outbound email for **Workspace invitations**.
- A separate resend verification email button or flow.
- Durable email queueing, retry orchestration, audit tables, provider abstraction, or provider failover.
- Admin-editable email templates, database-backed templates, localization, template previews, or template management UI.
- Marketing or bulk email.
- Retroactive invalidation of existing sessions for users whose email is currently unverified.
- Backfilling existing unverified email/password users as verified.
- New public API endpoints outside Better Auth's built-in verification flow.
- A dedicated verification-success frontend route or page.
