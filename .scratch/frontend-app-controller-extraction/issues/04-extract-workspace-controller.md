# Extract Workspace Controller

Category: enhancement
Status: completed

## Parent

.scratch/frontend-app-controller-extraction/PRD.md

## What to build

Move **Workspace context**, **Workspace selection view**, Workspace resolution, Workspace switching, invitations, users, Workspace API key display state, and forbidden access recovery out of App into a Workspace controller. Preserve the existing session-backed SPA behavior and keep Workspace API helpers independent from the final workspace-aware runtime.

## Acceptance criteria

- [x] App no longer directly owns Workspace ID/name/API key state, user Workspace lists, invitation lists, Workspace resolution status, selected invitation state, Workspace users, Workspace invitation management state, Workspace user action state, or Workspace recovery refs.
- [x] Startup Workspace resolution still chooses an accepted **Workspace context** when available and never auto-selects an **Invited workspace entry**.
- [x] **Loading workspace context** and **Workspace resolution error** behavior are preserved.
- [x] **Stored workspace preference** continues to persist only accepted Workspace ID and display name.
- [x] Switching accepted **Workspace context** still clears visible workspace-scoped data before loading the next Workspace data.
- [x] Selecting an **Invited workspace entry** still opens **Locked invitation state** without workspace API access.
- [x] Accepting, declining, creating, renaming, deleting, leaving, inviting users, canceling invitations, and applying Workspace user actions are preserved.
- [x] **Workspace API key display** generation, rotation confirmation, one-time visible key material, copy behavior, and **Action toast** feedback are preserved.
- [x] Forbidden Workspace access still refreshes Workspaces, switches to another accepted Workspace when available, and shows the existing **Action toast**.
- [x] Workspace API helpers are built from the core runtime and do not depend on the final workspace-aware runtime.
- [x] No user-visible UI changes are introduced.
- [x] `npm run test --prefix frontend` passes.
- [x] `npm run build --prefix frontend` passes.

## Agent Brief

**Category:** enhancement
**Summary:** Extract the frontend Workspace controller from App while preserving Workspace context, Workspace selection view, invitations, user management, Workspace API key display, and forbidden access recovery behavior.

**Current behavior:**
The root App component remains the public frontend root and still directly owns Workspace-oriented state, actions, effects, derived values, and view-model assembly. This includes accepted Workspace context, Workspace selection view search and selection, startup Workspace resolution, Stored workspace preference updates, Workspace switching, pending invitation selection, Workspace invitations, Workspace users, Workspace API key display state, Workspace lifecycle actions, invitation and user-management actions, and forbidden Workspace access recovery. The app runtime core plus Document and Template controllers already exist, but Workspace behavior is still orchestrated directly by App.

**Desired behavior:**
App should delegate cohesive Workspace behavior to a Workspace controller while remaining the public root composer. The controller should own Workspace context, Workspace selection view, Workspace resolution, accepted Workspace switching, invited Workspace entry selection, invitations, users, Workspace API key display state, and forbidden access recovery. User-visible behavior, backend API contracts, storage keys, Stored workspace preference shape, Workspace API key display semantics, and UI structure must remain unchanged.

**Key interfaces:**
- The root App component remains the public bootstrap and composition boundary.
- The Workspace controller public API should expose grouped view models and actions by UI surface rather than requiring App to assemble many individual Workspace props.
- Workspace-owned API helpers should be built from the app runtime core and should not depend on the final workspace-aware request layer, because forbidden Workspace access recovery remains owned by Workspace behavior.
- The final workspace-aware request layer should continue to accept a forbidden Workspace access callback supplied by Workspace behavior.
- Accepted Workspace context selection must remain separate from selected Invited workspace entry behavior; Locked invitation state must not provide workspace API access.
- Stored workspace preference must continue to persist only accepted Workspace ID and display name, never Workspace API key material or invited entry state.
- The controller should continue coordinating with Document and Template controllers when accepted Workspace context changes so visible workspace-scoped data clears before next Workspace data loads.
- App-level integration behavior and existing pure Workspace selection tests remain the primary regression safety net; add controller-specific tests only if independently meaningful pure behavior emerges or a bug is found.

**Acceptance criteria:**
- [ ] App no longer directly owns Workspace ID/name/API key state, user Workspace lists, invitation lists, Workspace resolution status, selected invitation state, Workspace users, Workspace invitation management state, Workspace user action state, or Workspace recovery refs.
- [ ] The controller returns grouped view models and actions for Workspace selection, Workspace pages, Workspace toolbar/API key display, Workspace users, Workspace invitations, and forbidden access recovery.
- [ ] Startup Workspace resolution still chooses an accepted Workspace context when available and never auto-selects an Invited workspace entry.
- [ ] Loading workspace context and Workspace resolution error behavior are preserved.
- [ ] Stored workspace preference continues to persist only accepted Workspace ID and display name.
- [ ] Switching accepted Workspace context still clears visible workspace-scoped data before loading the next Workspace data.
- [ ] Selecting an Invited workspace entry still opens Locked invitation state without workspace API access.
- [ ] Accepting, declining, creating, renaming, deleting, leaving, inviting users, canceling invitations, and applying Workspace user actions are preserved.
- [ ] Workspace API key display generation, rotation confirmation, one-time visible key material, copy behavior, and Action toast feedback are preserved.
- [ ] Forbidden Workspace access still refreshes Workspaces, switches to another accepted Workspace when available, and shows the existing Action toast.
- [ ] Workspace API helpers are built from the core runtime and do not depend on the final workspace-aware runtime.

**Out of scope:**
- Extracting auth or profile controllers in this slice.

- Introducing URL routing, React Context, a global state library, CSS architecture changes, or a broad terminology-only rename.
- Adding controller-specific tests solely to assert internal hook structure.
