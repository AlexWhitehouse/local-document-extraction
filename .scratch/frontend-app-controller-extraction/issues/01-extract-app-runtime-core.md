## Agent Brief

**Category:** enhancement
**Summary:** Extract a small frontend app runtime core so later controllers can share endpoint construction, request behavior, logging, and Action toast helpers without changing user-visible behavior.

**Current behavior:**
The root App component remains the public frontend root and owns shared runtime behavior inline. That includes endpoint construction, request primitives, credentials handling, auth/session checks, Workspace context headers, 204 and JSON response handling, latest response updates, logging, Action toast dispatch, Document upload toast dispatch, and forbidden Workspace access recovery. The same App component also owns feature-specific state and handlers for Documents, Templates, Workspace context, auth, and profile behavior.

**Desired behavior:**
App should delegate the behavior-preserving runtime concerns to a small shared runtime seam while remaining the public root component. The runtime should expose a core layer for endpoint construction, logging, Action toast helpers, and generic request primitives that do not depend on Workspace recovery. A workspace-aware request layer should compose with that core layer and accept a forbidden Workspace access callback, so later feature controllers can make workspace-scoped requests without creating hook-order cycles. Existing user-visible behavior, backend API contracts, storage keys, and UI structure must remain unchanged.

**Key interfaces:**
- The root App component remains the public bootstrap and composition boundary.
- The core runtime interface should provide endpoint construction, logging, notification helpers, and request primitives that are independent of Workspace recovery.
- The workspace-aware request interface should preserve authenticated request behavior, `x-workspace-id` header behavior, `credentials: "include"`, 204 handling, JSON parsing, latest response updates, and existing error message selection.
- Workspace-owned operations should still be able to make auth-required requests that do not require accepted Workspace API access.
- Forbidden Workspace access recovery should remain owned outside the core runtime and be passed into the workspace-aware request layer as a callback.

**Acceptance criteria:**
- [ ] App uses a small core runtime for endpoint construction, logging, Action toast helpers, Document upload toast helpers, and request primitives that do not depend on Workspace recovery.
- [ ] App has a workspace-aware request layer that can accept a forbidden Workspace access callback without creating a hook-order cycle.
- [ ] Existing request headers, credentials behavior, 204 handling, JSON parsing, latest response updates, and error messages are preserved.
- [ ] Workspace operations are still able to make auth-required requests that do not require an accepted Workspace context.
- [ ] No React Context, routing, global state library, backend API changes, storage-key changes, or user-visible UI changes are introduced.
- [ ] Existing App-level behavior tests remain the primary regression safety net and pass with `npm run test --prefix frontend`.
- [ ] The frontend production build succeeds with `npm run build --prefix frontend`.

**Out of scope:**
- Extracting Document, Template, Workspace, auth, or profile controllers in this slice.
- Changing user-visible behavior, labels, Active page semantics, Workspace selection view semantics, Workspace API key display semantics, Template behavior, Document behavior, or Action toast copy.
- Introducing URL routing, React Context, a global state library, CSS architecture changes, backend API changes, storage-key changes, persisted data shape changes, or UI redesign.
- Renaming all legacy internal variables solely for terminology cleanup during this runtime extraction.
