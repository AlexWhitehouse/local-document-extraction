## What to build

Extend Leave Workspace for a non-owner whose departure would remove their final accepted Workspace. Create a **Replacement personal Workspace** using the existing new-user starter-template bootstrap, return it as the next Accepted workspace context without Workspace API key material, and select it in the frontend as part of the same complete action.

The replacement must be created only when required and must not alter the Workspace being left beyond removing the caller's membership.

## Acceptance criteria

- [ ] Leaving the final accepted Workspace creates exactly one Replacement personal Workspace for the departing user.
- [ ] The Replacement personal Workspace has owner membership and the same starter-template bootstrap as a new-user Workspace.
- [ ] The replacement starts with `has_api_key: false` and returns no Workspace API key secret.
- [ ] The Workspace being left, its resources, invitations, API key, and other members remain intact.
- [ ] Pending Workspace invitations do not satisfy the accepted-Workspace invariant and do not suppress replacement creation.
- [ ] The Leave Workspace response identifies the Replacement personal Workspace as the preferred next context.
- [ ] The frontend clears prior Workspace-scoped state and selects the replacement without inventing an ID.
- [ ] Repeated or failed action handling cannot create duplicate personal Workspaces.
- [ ] Contract-oriented tests exercise the full leave-and-replace path through the frontend Adapter and backend Fetch application.
- [ ] Focused Workspace bootstrap, Leave Workspace, frontend context, and build checks pass.

## Agent Brief

**Category:** enhancement
**Summary:** Extend member departure so a final accepted Workspace is replaced atomically with a bootstrapped personal Workspace.

**Current behavior:**
Non-owner departure rejects a user's final accepted Workspace with `last_workspace`. The frontend already understands a replacement response shape, but the authoritative control-data operation cannot produce it.

**Desired behavior:**
When a non-owner's departure would remove their final accepted Workspace, control data removes only that membership and creates exactly one owner-owned Replacement personal Workspace with the new-user starter-template bootstrap. The response names it as both the replacement and preferred next context, contains no API key secret, and leaves the departed Workspace untouched.

**Key interfaces:**
- `LocalWorkspaceControl.leaveWorkspace` — one transaction that validates departure, creates a bootstrap-marked replacement only when needed, deletes the old membership, and returns safe contexts.
- Existing session-only leave route and Workspace request adapter — preserve the established HTTP seam while normalizing the expanded response.
- Workspace selection transition — chooses the server-provided replacement rather than fabricating an ID.

**Acceptance criteria:**
- [ ] A final member departure creates exactly one owner-owned, bootstrap-marked replacement with no API key secret.
- [ ] The original Workspace, resources, invitations, API key, and other members remain unchanged; pending invitations do not count as accepted access.
- [ ] Repeated/failed action handling cannot duplicate replacements, and the response identifies the replacement as the next context.
- [ ] Contract coverage crosses the adapter and Fetch application; focused bootstrap/controller and build checks pass.

**Out of scope:**
- Owner departure, generic membership changes, and Workspace deletion behavior.
- New invitation lifecycle behavior or changes to the underlying leave route shape.

## Completion

Implemented an atomic final-departure transition that creates exactly one bootstrap-marked Replacement personal Workspace before removing the old membership. The response returns only safe replacement/context metadata, and contract tests cover preserved departed resources, pending invitations, repeat calls, and frontend replacement selection. Full backend/frontend tests, lint, backend typecheck, and frontend production build passed.
