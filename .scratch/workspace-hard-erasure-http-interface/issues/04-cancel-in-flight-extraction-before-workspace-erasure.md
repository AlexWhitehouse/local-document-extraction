# Cancel In-Flight Extraction Before Workspace Erasure

Status: completed
Category: bug
Type: AFK
User stories covered: 10, 28-30

## Parent

## What to build

Complete synchronous Workspace deletion when an **Extraction job** is actively processing. Deletion should signal cancellation to in-flight Model gateway work where supported, wait for the active Workspace operation to drain, suppress retry scheduling and late lifecycle persistence, then erase the Workspace and return success.

Keep Model gateway invocation separate from authoritative Extraction job lifecycle changes. Cancellation is execution coordination, not a new durable lifecycle state.

## Acceptance criteria

- [ ] In-flight Extraction processing participates in Workspace-scoped operation coordination.
- [ ] Workspace deletion propagates cancellation to Model gateway work through the existing extraction execution Seam.
- [ ] The deletion response does not report success until active processing has stopped writing Workspace product data.
- [ ] Cancelled processing does not persist completion, failure, or a retry after Workspace deletion has begun.
- [ ] Cancellation does not introduce a new durable Extraction job lifecycle state.
- [ ] Model gateway timeout and retry behavior remains unchanged for active Workspaces not being deleted.
- [ ] Tests use a controllable extraction Adapter to prove cancellation, draining, absence of late writes, and physical erasure through public Interfaces.
- [ ] ADR-0004's separation between Model gateway invocation and persisted lifecycle changes remains intact.
- [ ] Focused runner, Model gateway, Workspace deletion, and backend typecheck checks pass.

## Agent Brief

**Category:** bug
**Summary:** Make synchronous Workspace deletion cancel and drain active extraction execution before hard erasure.

**Current behavior:**
The extraction runner's Model gateway execution is outside Workspace product-operation coordination. Deletion can erase a Workspace while an extraction is still waiting on the model, and the execution seam has no deletion cancellation signal.

**Desired behavior:**
An active extraction holds Workspace participation while it invokes the model. When deletion begins, that participation receives cancellation, deletion waits for it to drain, and the runner exits without persisting completion, failure, or retry work. Active Workspace timeout and retry behavior is unchanged, and cancellation remains execution coordination rather than a durable lifecycle state.

**Key interfaces:**
- `Workspace product operation coordination` — supplies a cancellation signal to active Workspace operations and waits for their release during deletion.
- `Local extraction runner` — participates around claim/model/lifecycle work and passes cancellation into the extraction execution seam.
- Model gateway execution seam — accepts an optional abort signal while retaining its independent timeout behavior and normalized retry errors.
- Runtime composition — shares the same Workspace coordination instance between the Fetch application/deletion Module and Local extraction runner.

**Acceptance criteria:**
- [ ] Deleting a Workspace with active model execution aborts the execution and waits until the runner releases participation before returning success.
- [ ] The runner writes no completion, failure, or retry after deletion begins, and no new durable lifecycle state is introduced.
- [ ] Model cancellation is observable through the extraction seam; normal active-Workspace timeout and retry behavior remains intact.
- [ ] Contract-style tests use a controllable extraction adapter plus the public deletion interface to prove cancellation, drain, and final physical erasure.
- [ ] Focused runner/model/deletion tests and backend typecheck pass.

**Out of scope:**
- Durable deletion intent and restart reconciliation, live browser invalidation, and new user-facing deletion progress.
- Changes to document deletion, profile, Workspace access management, or job-listing features.

## Completion

Implemented shared cancellation-aware Workspace coordination for the runner and Fetch application, propagated the abort signal through the model-gateway seam, and verified in-flight extraction drain without a terminal lifecycle write or retry. Full backend/frontend tests, lint, backend typecheck, and frontend production build passed.
