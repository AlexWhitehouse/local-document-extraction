# Search Extraction Jobs And Report The Authoritative Documents Count

Status: completed
Category: enhancement
Type: AFK
User stories covered: 49, 51-59

## Parent

## What to build

Make Extraction job search and the Documents count executable through authoritative Workspace product data. The backend should interpret the frontend's existing search intent using stable job metadata and return the total number of durable Extraction jobs in the Workspace independently of search and pagination. The frontend should use that authoritative total for the Documents count while rendering the filtered list.

Search must not inspect extracted answers or evidence and must remain scoped to the accepted Workspace context.

## Acceptance criteria

- [ ] Extraction job collection requests accept the existing frontend search input through a plain Document request Adapter.
- [ ] Search matches supported stable metadata: Source-file name, Extraction job ID, Template ID, and lifecycle status.
- [ ] Search is scoped to authoritative Workspace product data for exactly one accepted Workspace context.
- [ ] Search does not inspect or expose Extraction results, evidence, Source-file binary contents, account identity, or Workspace API key material.
- [ ] The collection response includes the authoritative total count of queued, processing, completed, and failed Extraction jobs before filtering and pagination.
- [ ] The frontend Documents count uses the authoritative total rather than the length of the displayed or loaded list.
- [ ] Clearing search restores the unfiltered list without changing total count semantics.
- [ ] Contract-oriented tests run the frontend Document Adapter against the backend Fetch application for matching, non-matching, cross-Workspace isolation, and total-count cases.
- [ ] Existing job list/detail and Completed document cache behavior remains intact.
- [ ] Focused Workspace product store, Document controller, and build checks pass.

## Agent Brief

**Category:** enhancement
**Summary:** Route document search through a plain adapter into authoritative workspace product metadata and return an unfiltered durable total.

**Current behavior:**
The document controller encodes `search` directly in a raw job-list URL, but the backend ignores it and returns no total. UI counts therefore change with filters and with only the currently loaded list.

**Desired behavior:**
The job collection accepts normalized search text through the Document adapter, matches only job ID, Source-file name, Template ID, and lifecycle status within the selected Workspace, and returns `total` for all durable jobs before filtering. The frontend renders the filtered collection while using that authoritative total for Documents count surfaces.

**Key interfaces:**
- `LocalWorkspaceProductStore` — explicit metadata-only filtered list and total-count operations.
- Job collection handler — parses the search query after workspace authorization and returns safe summaries with `total`.
- Document request adapter/controller — own search route construction and map collection totals into presentation state.

**Acceptance criteria:**
- [ ] Search matches only supported stable metadata and isolates exactly one authorized Workspace without inspecting results/evidence/content/identity/key material.
- [ ] Collection responses report the durable unfiltered total before search or pagination.
- [ ] Clearing search restores unfiltered results with the same total; all Documents count surfaces use it.
- [ ] Adapter-to-Fetch contracts cover match/non-match/isolation/totals; focused controller/store/build checks pass.

**Out of scope:**
- Cursor encoding and page windows, delivered by the following pagination issue.
- Full-text extraction-answer search or changes to Completed document cache semantics.

## Completion

Implemented adapter-owned job collection search over safe metadata only, workspace-scoped filtered product-store queries, and an independent durable `total` count. The controller and all Documents count surfaces now use `total` while rendering filters. Contract and controller tests cover matching, isolation, totals, and filtered display; full backend/frontend tests, lint, backend typecheck, and frontend production build passed.
