## What to build

Deliver the first complete Workspace deletion path and use it to establish the executable frontend/backend HTTP Seam. An owner with another accepted Workspace should be able to delete an idle Workspace and receive success only after access is revoked, authoritative Workspace product data is erased, residual Source files are erased, frontend Workspace context moves to a valid replacement, and the real frontend domain request Adapter has crossed the backend Fetch application successfully.

Build a deep Workspace deletion Module rather than extending route choreography. Separate explicit initialization of new Workspace product data from opening existing product data, add Workspace-scoped Source-file erasure behind the storage Interface, preserve existing Workspace policy errors, and add `Workspace deletion` to the backend domain glossary as the complete hard-erasure action.

- [ ] Local product analytics logs are not erased by Workspace deletion.

## Agent Brief

**Category:** bug
**Summary:** Make idle Workspace deletion a complete, observable hard-erasure operation through the frontend/backend HTTP interface.

**Current behavior:**
Workspace deletion removes only Workspace control data. Its authoritative product database and residual Source files remain on disk, and the frontend deletion call constructs the transport request inside React rather than through a domain request interface.

**Desired behavior:**
An owner with another accepted Workspace can delete an idle Workspace through the visible application flow. Success is returned only after policy-approved control access is revoked, pending invitations and API-key access are removed, product data and all Workspace Source files are erased, and the frontend selects a valid remaining Workspace. Existing rejection behavior for non-members, non-owner roles, and a final Workspace remains unchanged.

**Key interfaces:**
- `Workspace deletion` — a small asynchronous operation that owns the complete idle hard-erasure contract instead of route-level choreography.
- `LocalWorkspaceControl` — preserves authorization and last-accepted-Workspace policy while removing control data associated with a deleted Workspace.
- Workspace product-store lifecycle — provides separate explicit initialization of new product data and non-creating access to existing product data, plus erasure of a Workspace database and its SQLite sidecars.
- `LocalSourceFileStore` — exposes idempotent Workspace-scoped Source-file erasure through its storage interface.
- Frontend Workspace request Adapter — owns deletion route construction and response/error interpretation outside React.

**Acceptance criteria:**
- [ ] An owner with another accepted Workspace can delete an idle Workspace through the existing visible flow and compatible success response.
- [ ] Existing public rejection semantics remain for non-members, admins, members, and owners attempting to delete their only accepted Workspace.
- [ ] Successful deletion removes memberships, Workspace API-key access, and pending Workspace invitations.
- [ ] Successful deletion removes the product database, SQLite sidecars, and the complete Workspace Source-file directory before returning success.
- [ ] Source-file erasure is idempotent, and opening missing existing product data never creates a database.
- [ ] The frontend clears deleted Workspace state, selects a remaining Workspace, and retains current action toast behavior.
- [ ] A contract-oriented test drives the plain frontend Adapter against the backend Fetch application for a policy rejection and successful hard erasure.
- [ ] Local product analytics are retained, and focused backend/frontend checks plus backend typecheck pass.

**Out of scope:**
- Preventing concurrent requests, cancelling in-flight extraction, and durable recovery after interruption; those follow-on deletion issues own active-work coordination.
- Live browser invalidation after deletion, profile and membership management routes, document deletion, and extraction-job search or pagination.
