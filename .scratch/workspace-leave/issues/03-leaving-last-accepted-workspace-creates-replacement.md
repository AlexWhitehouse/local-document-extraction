# Leaving the last accepted Workspace creates a replacement

Category: enhancement
Status: ready-for-agent

## What to build

Extend `Leave Workspace` for the last accepted Workspace case. When a signed-in non-owner Workspace member leaves their only accepted Workspace, the system should remove their membership from the left Workspace, create a replacement personal Workspace using the existing starter-template bootstrap behavior, return one-time replacement Workspace API-key material, store that key locally, refresh accepted Workspaces, and select the replacement accepted Workspace context.

## Acceptance criteria

- [ ] Leaving the user's last accepted Workspace succeeds for non-owner Workspace admins and members.
- [ ] The left Workspace is not deleted and remaining members keep their access.
- [ ] A replacement personal Workspace is created for the leaving user using the same starter-template bootstrap behavior as new-user Workspace bootstrap.
- [ ] The leave response includes the replacement Workspace identity and one-time API-key material needed by the frontend.
- [ ] The frontend stores the replacement Workspace API key locally for the replacement Workspace.
- [ ] The frontend selects the replacement accepted Workspace context after the leave succeeds.
- [ ] Workspace policy tests cover last-accepted-Workspace leave and replacement bootstrap behavior.
- [ ] Workspace context tests cover selecting the replacement Workspace when it is returned by leave.
- [ ] Relevant repo checks pass using existing scripts.

## Agent Brief

**Category:** enhancement
**Summary:** Extend `Leave Workspace` so leaving the user's last accepted Workspace creates and selects a replacement personal Workspace.

**Current behavior:**
The main leave path removes a non-owner member's Workspace membership and selects another remaining accepted Workspace when one exists. The last-accepted-Workspace branch is not covered by that main path.

**Desired behavior:**
When a signed-in non-owner Workspace member leaves their only accepted Workspace, the system should remove their membership from the left Workspace, create a replacement personal Workspace for the user, use the same starter-template bootstrap behavior as new-user Workspace bootstrap, return one-time replacement Workspace API-key material, store that key locally, refresh accepted Workspaces, and select the replacement accepted Workspace context.

**Key interfaces:**
- `Workspace policy` leave operation — should detect when leave would remove the user's last accepted Workspace and orchestrate replacement personal Workspace bootstrap.
- New-user Workspace bootstrap behavior — should be reused rather than duplicated so replacement Workspaces receive the same starter-template setup.
- Workspace leave API response — should include replacement Workspace identity and one-time API-key material when a replacement is created.
- Workspace context transition logic — should prefer the returned replacement Workspace over other fallback selection when leave succeeds.
- App/browser adapter behavior — should store the replacement Workspace API key locally and select the replacement Workspace context after refresh.

**Acceptance criteria:**
- [ ] Leaving the user's last accepted Workspace succeeds for non-owner Workspace admins and members.
- [ ] The left Workspace is not deleted and remaining members keep their access.
- [ ] A replacement personal Workspace is created for the leaving user using the same starter-template bootstrap behavior as new-user Workspace bootstrap.
- [ ] The leave response includes the replacement Workspace identity and one-time API-key material needed by the frontend.
- [ ] The frontend stores the replacement Workspace API key locally for the replacement Workspace.
- [ ] The frontend selects the replacement accepted Workspace context after the leave succeeds.
- [ ] Workspace policy tests cover last-accepted-Workspace leave and replacement bootstrap behavior.
- [ ] Workspace context tests cover selecting the replacement Workspace when it is returned by leave.
- [ ] Relevant repo checks pass using existing scripts.

**Out of scope:**
- Implementing the main leave path when other accepted Workspaces exist; that is covered by issue 01.
- Owner, non-member, and Workspace API-key rejection hardening; that is covered by issue 02.
- Changing the starter-template content created by bootstrap.
- Prompting the user for a replacement Workspace name before leaving.
- Allowing a signed-in user to end with zero accepted Workspaces.
