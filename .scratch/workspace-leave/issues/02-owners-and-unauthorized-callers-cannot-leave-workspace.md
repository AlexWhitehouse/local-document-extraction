# Owners and unauthorized callers cannot leave a Workspace

Category: enhancement
Status: complete

## What to build

Harden the role and authentication boundaries around `Leave Workspace`. Owners should continue to use the destructive owner-only Workspace deletion path rather than leaving. Direct owner leave attempts, non-member leave attempts, and Workspace API-key-authenticated leave attempts should be rejected without changing Workspace membership or Workspace context.

## Acceptance criteria

- [x] Workspace owners continue to see `Delete Workspace` rather than `Leave Workspace` in the Workspace action area.
- [x] A direct owner leave request is rejected with messaging that ownership must be transferred or the Workspace deleted instead.
- [x] A direct non-member leave request is rejected without changing Workspace memberships.
- [x] A Workspace API-key-authenticated leave request is rejected because `Leave Workspace` is a signed-in member action.
- [x] Rejected leave attempts do not remove memberships, delete the Workspace, rotate the Workspace API key, or change frontend Workspace context.
- [x] Backend tests cover owner, non-member, and API-key-authenticated rejection behavior.
- [x] Frontend tests cover owner action visibility and failed leave preserving Workspace context.
- [x] Relevant repo checks pass using existing scripts.

- Workspace context transition logic — should preserve current Workspace context on rejected leave attempts.
