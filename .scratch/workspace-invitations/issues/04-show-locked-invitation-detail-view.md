# Show locked invitation detail view

Status: completed
Category: enhancement
Type: AFK

## Parent

## What to build

When an invited workspace entry is selected, show a locked invitation detail view instead of normal workspace settings. Selecting the invitation must not set the active workspace context or trigger workspace API access, and the view should show all invitation details needed before accept/decline.

## Acceptance criteria

- [x] Selected invitation state is tracked separately from active accepted workspace context.
- [x] Selecting an invited workspace does not enable templates, documents, jobs, API key, rename, delete, upload, or user management for that workspace.
- [x] The toolbar/page state communicates that the invitation is pending and no workspace access exists yet.
- [x] The Workspaces page replaces normal settings/cards with an invitation detail view for selected invitations.
- [x] The detail view shows workspace name, invited email, offered role, inviter identity, invited time, and expiry.
- [x] Accept and decline actions appear on the invitation detail view, not directly on the workspace list item.
- [x] Create Workspace remains available while an invitation is selected; Delete Workspace is not shown for the invitation selection.
- [x] Frontend production build succeeds.

## Agent Brief

**Category:** enhancement
**Summary:** Show a locked invitation detail view when an invitee selects an invited workspace entry.

**Current behavior:**
Invited workspace entries can be represented alongside accepted workspaces, but selecting an invitation does not yet have a dedicated locked detail experience. The app must preserve the boundary that a workspace invitation is only an offer and must not become active workspace access before acceptance.

**Desired behavior:**
Selecting an invited workspace entry should track selected invitation state separately from the active accepted workspace context. The Workspaces page should replace normal workspace settings/cards with a locked invitation detail view that shows the workspace name, invited email, offered role, inviter identity, invited time, and expiry. The toolbar/page state should clearly communicate that the invitation is pending and no workspace access exists yet. Accept and decline actions should appear in the detail view, not on the workspace list item, while their implementation can remain delegated to follow-up slices.

**Key interfaces:**
- Workspace selection state should distinguish accepted workspace selection from invited workspace/invitation selection.
- Active workspace context used for authenticated workspace API access must not be set to an invited workspace before acceptance.
- Workspaces page rendering should switch between accepted workspace management and a locked invitation detail view based on the selected item type.
- Invitation detail data should use the invitee-facing invitation summary fields: workspace name, invited email, offered role, inviter identity, invited time, and expiry.
- Global/page actions should hide workspace-only destructive or management actions for invited selections while keeping Create Workspace available.

**Acceptance criteria:**
- [ ] Selected invitation state is tracked separately from active accepted workspace context.
- [ ] Selecting an invited workspace does not enable templates, documents, jobs, API key, rename, delete, upload, or user management for that workspace.
- [ ] The toolbar/page state communicates that the invitation is pending and no workspace access exists yet.
- [ ] The Workspaces page replaces normal settings/cards with an invitation detail view for selected invitations.
- [ ] The detail view shows workspace name, invited email, offered role, inviter identity, invited time, and expiry.
- [ ] Accept and decline actions appear on the invitation detail view, not directly on the workspace list item.
- [ ] Create Workspace remains available while an invitation is selected; Delete Workspace is not shown for the invitation selection.
- [ ] Frontend production build succeeds using the repo's frontend build command.

**Out of scope:**
- Implementing invitation acceptance behavior; that is covered by the follow-up accept slice.
- Implementing invitation decline behavior; that is covered by the follow-up decline slice.
- Adding direct accept/decline controls to workspace list items.
- Granting templates, documents, jobs, API key, workspace rename, delete, upload, or user management access before invitation acceptance.
- Sending invitation emails or building a general notification center.
