## Agent Brief

**Category:** enhancement
**Summary:** Let workspace owners and admins cancel actionable pending workspace invitations.

**Current behavior:**
Workspace owners and admins can see pending workspace invitations after the pending-invitations slice, but there is no completed owner/admin cancellation action for revoking a pending invitation from workspace access management. Pending invitations therefore remain actionable until accepted, expired, or otherwise changed outside this management flow.

**Desired behavior:**
Owners and admins should be able to cancel a pending invitation sent from their workspace. Members should not be able to cancel workspace invitations. Cancellation should use the owner/admin workspace authorization path, set the invitation status to `cancelled`, and make the invitation disappear from actionable pending invitation management. The frontend should ask for confirmation before cancelling someone else's pending invitation and then refresh the pending invitation state after a successful cancellation.

**Key interfaces:**
- `Workspace policy` invitation lifecycle behavior should own owner/admin cancellation authorization and the durable status update to `cancelled`.
- The workspace API should expose a thin workspace-scoped cancellation endpoint for a pending invitation, delegating authorization and status changes to `Workspace policy`.
- Cancellation responses should be minimal and stable, including success, invitation id, and `cancelled` status.
- The workspace access-management UI should provide a cancel action only where owner/admin pending invitation management is available.

**Acceptance criteria:**
- [ ] Owners and admins can cancel pending invitations sent from their workspace.
- [ ] Members cannot cancel pending invitations sent from a workspace.
- [ ] The UI asks for confirmation before an owner/admin cancels someone else's pending invitation.
- [ ] Cancelled invitations receive status `cancelled` and disappear from pending invitation management.
- [ ] Cancellation returns a minimal success response with invitation id and `cancelled` status.
- [ ] Backend policy tests cover owner/admin/member cancellation authorization and status changes.
- [ ] Backend typecheck succeeds using the repo's backend typecheck command.
- [ ] Frontend production build succeeds using the repo's frontend build command.

**Out of scope:**
- Invitee decline; that is a separate detail-view action with different authorization.
- Accepting invitations.
- Adding a separate `declined` status.
- Sending cancellation email notifications.
- Full invitation audit history for non-actionable invitations.
