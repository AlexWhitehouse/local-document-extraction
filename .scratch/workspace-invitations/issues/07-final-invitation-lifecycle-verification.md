## Agent Brief

**Category:** enhancement
**Summary:** Verify the complete workspace invitation lifecycle now that the invite creation, pending management, cancellation, invited workspace display, locked detail view, acceptance, and decline slices are complete.

**Current behavior:**
The workspace invitation feature has been implemented across several vertical slices. Owners/admins can manage pending invitations, invitees can see invited workspace entries, invited selections render a locked invitation detail view, and invitees can accept or decline from that detail view. The remaining work is an end-to-end verification pass to confirm these behaviors work together and do not violate the boundary that a workspace invitation is not workspace access until accepted.

**Desired behavior:**
The full workspace invitation lifecycle should behave consistently from both inviter and invitee perspectives. Owners/admins should be able to invite a user, see the pending invitation separately from current users, and cancel it. Invitees should be able to discover pending invitations in the workspace list, open a locked detail view without gaining workspace API access, accept to join and switch into the workspace, or decline to remove the invitation without a confirmation prompt. Verification should include the repo's supported backend typecheck and frontend production build commands, plus concise manual notes for any behavior that cannot be covered by automated checks.

**Key interfaces:**
- `Workspace policy` invitation lifecycle behavior should remain the durable owner of invitation authorization, expiry handling, membership creation, cancellation, decline, and accepted-role preservation.
- Workspace invitation API behavior should continue to expose separate authorization paths for owner/admin cancellation, invitee decline, invitee acceptance, invitee-facing pending invitation listing, and workspace-scoped pending invitation management.
- Workspace state/selection behavior should continue to distinguish accepted workspace context from selected invited workspace/invitation state.
- Workspaces UI behavior should keep current workspace management separate from locked invitation details, and should not expose workspace-only actions for an unaccepted invitation.

**Acceptance criteria:**
- [ ] A workspace owner/admin can invite a user, see the pending invitation, and cancel it.
- [ ] An invited user can see an orange invited workspace entry, open the locked detail view, and accept the invitation.
- [ ] After accepting, the invited user is switched into the accepted workspace and no longer sees the invitation entry.
- [ ] An invited user can decline an invitation and see it removed without a confirmation prompt.
- [ ] Selecting an invitation never exposes workspace API access, templates, documents, jobs, API keys, workspace rename/delete, upload, or user management before acceptance.
- [ ] Pending invitations remain separate from current workspace users in access management.
- [ ] Backend typecheck succeeds using the repo's backend typecheck command.
- [ ] Frontend production build succeeds using the repo's frontend build command.
- [ ] Manual verification notes are added to the issue comments or implementation summary.

**Out of scope:**
- Sending invitation emails or adding a notification center.
- Adding direct accept/decline controls to workspace list items.
- Introducing a separate declined invitation status.
- Reworking workspace role semantics, invitation audit history, or workspace deletion cascade behavior.
- Implementing unrelated invitation lifecycle features beyond verifying and fixing regressions discovered during this pass.
