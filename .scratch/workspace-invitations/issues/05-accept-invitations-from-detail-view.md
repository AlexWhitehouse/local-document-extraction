## Agent Brief

**Category:** enhancement
**Summary:** Let invitees accept pending workspace invitations from the locked invitation detail view.

**Current behavior:**
Invitees can see pending workspace invitations in the workspaces flow and the invitation detail view now has an Accept Invitation action placeholder, but accepting is not wired through that view. The backend already has an invitation acceptance foundation, but acceptance must be brought into line with the workspace invitation domain rules before this slice is complete.

**Desired behavior:**
An invitee should be able to accept their own pending, unexpired workspace invitation from the locked invitation detail view. Acceptance should authorize by the signed-in user's current normalized account email, create workspace membership with the offered role only when no membership already exists, preserve any existing membership role, mark the invitation accepted, refresh workspace and invitation state, and switch the active workspace context to the accepted workspace. Acceptance must not depend on the inviter still being owner/admin at acceptance time.

**Key interfaces:**
- Workspace invitation acceptance policy should own membership creation, existing-membership preservation, invitation status changes, email matching, expiry handling, and inviter-role independence.
- Invitation acceptance API should expose action-oriented success data including the accepted workspace id and resulting role, while preserving existing HTTP semantics for not found, wrong-email, and expired invitations.
- Workspace selection state should clear selected invitation state after successful acceptance and select the accepted workspace as active workspace context.
- Invitee-facing invitation state should refresh after acceptance so accepted invitations disappear from invited workspace entries.
- Invitation detail UI should enable the Accept Invitation action only when a pending invitation is selected and should surface success/failure feedback through existing app logging patterns.

**Acceptance criteria:**
- [x] Invitees can accept a pending invitation from the invitation detail view.
- [x] Acceptance creates workspace membership with the offered role when no membership exists.
- [x] Acceptance does not overwrite, downgrade, or otherwise change an existing workspace membership role.
- [x] Acceptance rejects wrong-email invitations and expired invitations with the existing HTTP semantics.
- [x] Acceptance does not require the inviter to still be owner/admin at acceptance time.
- [x] After acceptance, the frontend refreshes workspace and invitation state, clears selected invitation state, and selects the accepted workspace.
- [x] Accepted invitations no longer appear as invited workspace entries.
- [x] Backend policy tests cover membership creation, existing-role preservation, wrong-email rejection, expiry rejection, and inviter role changes.
- [x] Backend typecheck succeeds using the repo's backend typecheck command.
- [x] Frontend production build succeeds using the repo's frontend build command.

**Out of scope:**
- Implementing invitee decline behavior; that is covered by the decline slice.
- Adding direct accept controls to workspace list items.
- Sending invitation emails or building a notification center.
- Changing workspace role vocabulary or custom role semantics.
