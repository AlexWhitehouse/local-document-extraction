## Agent Brief

**Category:** enhancement
**Summary:** Make scheduled Workspace billing production-operational with verified execution, per-Workspace failure isolation, and non-secret observability.

**Current behavior:**
Workspace billing already has a Worker `scheduled()` handler that invokes Enterprise ramp-up invoice generation, Enterprise annual overage invoice generation, and Billing reconciliation. The prerequisite Billing reconciliation production-coverage work is complete, including non-destructive drift records, idempotent safe repair paths, and Application admin visibility for reconciliation state.

The remaining production-readiness gap is operational. Production scheduled execution is not yet proven by Worker configuration or an operator-verifiable Cron Trigger runbook. Scheduled billing tasks process multiple Workspaces, but a failure for one Workspace can still throw out of a task or the overall scheduled run, making it possible for unrelated Workspaces to be skipped. Operators also need structured, non-secret visibility into scheduled Billing reconciliation and Enterprise invoice-generation runs so missed execution, partial failure, and retry needs do not stay silent.

**Desired behavior:**
Scheduled Workspace billing should have a clear production execution path. Either the Worker configuration should declare the Cron Trigger cadence directly, or the operator runbook should document the Dashboard-managed Cron Trigger setup and how to verify the Worker's `scheduled()` handler actually runs in production.

Each scheduled billing task should isolate failures by task and by Workspace. Billing reconciliation, Enterprise ramp-up invoice generation, and Enterprise annual overage generation should continue processing unrelated Workspaces after one Workspace fails. A failed Workspace should leave enough non-secret operational evidence for an operator or Application admin to understand the task, Workspace, related Stripe object when known, failure class, timestamp, and retry/manual-review path.

Repeated scheduled runs should remain idempotent. A retry after partial failure must not duplicate Enterprise invoices, Included Credits, Purchased Credits, owner Billing activity, Application admin billing audit entries, or Billing reconciliation drift records. Observability must not log or persist raw Stripe payloads, Stripe API keys, webhook secrets, payment method details, or unnecessary customer PII.

**Key interfaces:**
- Worker `scheduled()` handler - should coordinate scheduled billing tasks, await their completion safely, and make whole-run success or partial failure observable.
- `generateEnterpriseRampUpInvoices()` - should process candidate Workspaces independently and record or log per-Workspace failures without stopping unrelated ramp-up invoice candidates.
- `generateEnterpriseAnnualOverageInvoices()` - should process candidate Workspaces independently and record or log per-Workspace failures without stopping unrelated annual overage invoice candidates.
- `reconcileWorkspaceBilling()` - should process candidate Workspaces independently, preserve existing idempotent repair and drift behavior, and record scheduled reconciliation status or diagnostics when a Workspace cannot be checked.
- Billing reconciliation status, drift records, Application admin billing state, or structured Worker logs - should expose non-secret scheduled-run health, partial failures, last checked state, related Stripe object IDs when known, and actionability.
- Worker configuration and launch/runbook documentation - should prove production Cron Trigger presence or a Dashboard-managed equivalent, including verification steps for the scheduled handler.
- Worker configuration tests and backend scheduled-handler tests - should cover Cron/runbook presence, observability, secret-safety, repeated runs, partial failures, and continued processing of unrelated Workspaces.
