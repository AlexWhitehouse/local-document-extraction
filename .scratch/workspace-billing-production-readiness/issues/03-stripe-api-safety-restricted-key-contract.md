## Agent Brief

**Category:** enhancement
**Summary:** Audit Stripe REST usage and document the least-privilege production restricted-key contract before live Workspace billing launch.

**Current behavior:**
Workspace billing already uses Stripe for Customers, Checkout Sessions, Subscriptions, Invoices, Invoice Items, signed webhooks, and Billing reconciliation reads. Many Stripe REST calls already send a pinned Stripe API version, use idempotency keys for mutating requests, and avoid explicit `payment_method_types` so Stripe dynamic payment methods can remain available.

The production-readiness gap is that this safety contract is not yet enforced as a complete audited surface. The intended outbound Stripe API version is repeated at individual call sites rather than documented as a single production contract, the live webhook payload API-version expectation still needs to be stated for operators, and the minimum Stripe restricted API key permissions have not been documented from the currently observed code paths. Existing tests check several specific Stripe request expectations, but they do not yet guard the full API surface against missing idempotency, API-version drift, or accidental hardcoded payment method types.

**Desired behavior:**
All Stripe REST calls used by Workspace billing, Billing reconciliation, and any Workspace deletion or owner-transfer billing cleanup should follow one documented production Stripe API contract.

Every mutating Stripe API request should send a stable idempotency key when Stripe supports idempotency for that request. Stripe requests should consistently use the intended pinned API version, and operator documentation should explain how the live webhook endpoint's event payload API version is pinned or verified against the fields consumed by the Worker.

Checkout and subscription requests should continue to omit hardcoded `payment_method_types`, preserving Stripe dynamic payment methods. The documentation should list the minimum restricted API key permissions needed for current backend behavior, including Customer, Checkout Session, Subscription, Invoice, Invoice Item, and reconciliation read paths. Operators should be told how to validate that permission set in Stripe test mode using Stripe request logs before creating the equivalent live restricted key.

If a restricted API key cannot be used for a live launch, the exception must be explicit and temporary: it should name the owner, expiry date, reason, and rotation plan.

**Key interfaces:**
- Stripe REST request contract — all outbound Stripe API requests should share the same intended API version and use idempotency keys for retryable mutations.
- Stripe Checkout and Subscription request bodies — must not include hardcoded `payment_method_types` unless a future issue intentionally changes the dynamic payment method policy.
- Stripe webhook operator contract — should document the expected live event payload API version or the verification evidence that the live endpoint payload shape matches the Worker.
- Stripe restricted API key runbook — should document the minimum required permissions for Customers, Checkout Sessions, Subscriptions, Invoices, Invoice Items, and reconciliation reads.
- Worker configuration and backend billing tests — should guard the production safety expectations without storing or printing Stripe secret values.

**Acceptance criteria:**
- [ ] Every mutating Stripe API request used by Workspace billing, Billing reconciliation, and Workspace deletion or owner-transfer billing cleanup has a stable idempotency key where Stripe supports one.
- [ ] Stripe requests consistently send the intended pinned Stripe API version.

- [ ] Backend, configuration, or focused tests guard idempotency, pinned API-version, and no-hardcoded-payment-method expectations across the Stripe API surface.

**Out of scope:**
