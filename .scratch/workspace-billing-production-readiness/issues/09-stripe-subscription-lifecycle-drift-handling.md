# Stripe Subscription Lifecycle Drift Handling

Category: enhancement
Status: completed

## What to build

Handle Stripe subscription lifecycle events that can happen outside the owner-facing app flow. Safe app-owned transitions should update Workspace billing state; dashboard-side creation, plan changes, cancellation reversal, pause/resume, deletion, or incomplete metadata should record Billing reconciliation drift instead of applying unsafe entitlement changes.

## Acceptance criteria

- [x] `customer.subscription.updated` applies safe app-owned changes such as cancel-at-period-end reversal and expected subscription reference/status updates.
- [x] `customer.subscription.deleted` deterministically stops paid entitlement or falls back to the correct Workspace billing state.
- [x] `customer.subscription.paused` and `customer.subscription.resumed` update safe states or record drift according to documented Workspace billing rules.
- [x] `customer.subscription.created` from Stripe Dashboard is treated as drift unless it can be confidently mapped to an app-owned paid invoice flow.
- [x] Subscription events with incomplete or mismatched metadata record Application admin-visible drift rather than granting entitlement.
- [x] Billing reconciliation detects missed or ambiguous subscription lifecycle outcomes.
- [x] Backend and Application admin tests cover safe updates, deletion, pause/resume, cancellation reversal, dashboard-side creation, incomplete metadata, and drift records.

## Agent Brief

**Category:** enhancement
**Summary:** Handle Stripe subscription lifecycle events safely before live Workspace billing launch.

**Current behavior:**
Workspace billing already processes Checkout and invoice Stripe billing events, persists processed/ignored/failed webhook outcomes, exposes failed-event diagnostics to Application admins, and records Billing reconciliation drift for some invoice and ledger mismatches. Self-service paid subscription entitlement is derived from Workspace billing control data, paid invoices activate Pro or Max entitlement, unpaid subscription invoices fall back to Free entitlement while preserving subscription context, and scheduled entitlement records represent owner-initiated cancellation or downgrade timing.

Stripe `customer.subscription.*` lifecycle events are not yet handled as first-class Workspace billing events. Changes made in Stripe outside the owner-facing app flow can therefore be ignored or only indirectly detected. This leaves a production risk that cancellation reversal, deletion, pause/resume, dashboard-side creation, dashboard-side plan change, or incomplete metadata could leave Workspace billing state stale or ambiguous.

**Desired behavior:**
Stripe subscription lifecycle events should be accepted only when they can be safely mapped to the app's Workspace billing model. Safe app-owned transitions should update Workspace billing control state idempotently. Ambiguous Stripe-side transitions should record Application admin-visible Billing reconciliation drift rather than granting or retaining paid entitlement incorrectly.

`customer.subscription.updated` should apply safe expected changes, including cancellation reversal and subscription reference/status/current-period updates when the subscription identity, customer, Workspace metadata, plan metadata, and expected Stripe Price/subscription item data agree with Workspace billing state. Dashboard-side plan changes, mismatched Price IDs, mismatched Workspace/customer metadata, unexpected status transitions, or changes that cannot be proven app-owned should not grant entitlement; they should record drift for manual review.

`customer.subscription.deleted` should deterministically stop paid self-service entitlement or fall back to the correct Workspace billing state. It should not remove historical billing context needed for owner/admin visibility, Billing reconciliation, or deletion-retention records.

`customer.subscription.paused` and `customer.subscription.resumed` should either update a safe state according to existing Workspace billing rules or record drift when the pause/resume semantics are not confidently compatible with Workspace entitlement. Resuming should not grant paid entitlement unless the event and existing state prove the Workspace has a valid paid subscription period or a paid invoice path has already activated it.

`customer.subscription.created` should be treated as drift by default when it originates from Stripe Dashboard or otherwise lacks a confident app-owned paid invoice relationship. A created subscription must not grant entitlement simply because metadata names a Workspace.

Billing reconciliation should detect missed or ambiguous subscription lifecycle outcomes by comparing Stripe-observed subscription state with Workspace billing control data, recording non-destructive drift rather than rewriting ledger or entitlement state unsafely.

**Key interfaces:**
- Stripe billing webhook event routing — should explicitly include the supported `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `customer.subscription.paused`, and `customer.subscription.resumed` lifecycle events.
- Stripe subscription event payload handling — should validate subscription ID, customer ID, metadata, current period, status, items, Price ID, and app-owned billing metadata before applying Workspace billing changes.
- Workspace billing control data — should preserve the self-service subscription plan, status, Stripe subscription ID, subscription item ID, current period, invoice context, and scheduled entitlement state needed for owner/admin summaries.
- Billing reconciliation drift records — should support subscription lifecycle drift types with safe observed/expected details, related Stripe object IDs, severity, actionability, timestamps, and Application admin visibility.
- Application admin billing review response — should expose subscription lifecycle drift and failed/ignored event diagnostics without raw Stripe payloads, API keys, webhook secrets, payment method details, or unnecessary customer PII.

**Acceptance criteria:**
- [ ] `customer.subscription.updated` applies safe app-owned changes such as cancel-at-period-end reversal and expected subscription reference/status/current-period updates.
- [ ] `customer.subscription.updated` records Application admin-visible drift for dashboard-side plan changes, mismatched metadata, mismatched Price IDs, ambiguous status changes, or unsupported lifecycle transitions.
- [ ] `customer.subscription.deleted` deterministically stops paid self-service entitlement or falls back to the correct Workspace billing state without losing historical billing context needed for review.
- [ ] `customer.subscription.paused` and `customer.subscription.resumed` update only safe Workspace billing states and otherwise record drift for manual review.
- [ ] `customer.subscription.created` from Stripe Dashboard or without a confident app-owned paid invoice relationship records drift and does not grant paid entitlement.
- [ ] Subscription events with incomplete or mismatched Workspace/customer/plan metadata record failed diagnostics or reconciliation drift rather than granting entitlement.
- [ ] Billing reconciliation detects missed or ambiguous subscription lifecycle outcomes and records non-destructive drift.
- [ ] Duplicate, delayed, and out-of-order subscription lifecycle events do not duplicate Credits, entitlements, invoice state changes, or admin diagnostics.
- [ ] Backend tests cover safe updates, deletion, pause/resume, cancellation reversal, dashboard-side creation, incomplete metadata, mismatched metadata, drift records, and reconciliation detection.
- [ ] Application admin billing view tests cover visible subscription lifecycle drift without exposing raw Stripe payloads or secrets.
- [ ] Backend typecheck and the relevant frontend production build or focused frontend admin tests pass.

**Out of scope:**
- Changing Free, Pro, Max, Enterprise, Credit pack, Plan override, No-billing, or Workspace billing authority product semantics.
- Adding new Stripe plans, prices, currencies, coupons, trials, refunds, disputes, chargebacks, Customer Portal behavior, or Stripe Connect.
- Rewriting the Billing ledger authority model or mutating ledger history during reconciliation.
- Launching live billing, creating live Stripe Dashboard resources, or entering/printing/documenting production Stripe secrets.
- Storing raw Stripe webhook payload archives or unnecessary customer/payment PII.
