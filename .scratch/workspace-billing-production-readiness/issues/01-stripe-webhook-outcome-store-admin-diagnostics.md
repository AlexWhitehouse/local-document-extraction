# Stripe Webhook Outcome Store and Admin Diagnostics

Category: enhancement
Status: completed

## What to build

Make Stripe billing webhook persistence production-readable by distinguishing processed, ignored, and failed events end to end. Unknown or irrelevant events should be safe to receive without mutating Workspace billing state, failed relevant events should leave durable non-secret diagnostics, and Application admins should be able to see enough context to understand whether a retry, metadata repair, or manual reconciliation is needed.

## Acceptance criteria

- [x] Stripe billing event persistence supports `processed`, `ignored`, and `failed` outcomes without breaking existing processed rows.
- [x] Unknown or irrelevant Stripe billing events return a successful response, do not mutate Workspace billing state, and are not recorded as successfully processed business events.
- [x] Relevant event failures record durable, non-secret diagnostics including event ID, event type, Workspace ID when known, related Stripe object ID when known, failure class, and retry/manual-review guidance.
- [x] Failed-event diagnostics are visible through the Application admin billing review path without exposing raw Stripe payloads, API keys, webhook secrets, payment method details, or unnecessary customer PII.
- [x] Duplicate Stripe deliveries continue to be idempotent for processed events, while failed events remain eligible for Stripe retry or manual repair.
- [x] Backend tests cover processed, ignored, failed, duplicate, and future-unknown event behavior.

## Agent Brief

**Category:** enhancement
**Summary:** Make Stripe billing webhook outcomes durable, diagnosable, and safe for unsupported or failed events before live billing launch.

**Current behavior:**
Stripe billing webhook persistence is oriented around successfully processed business events. The existing Stripe event store only distinguishes processed and failed rows, and unsupported signed Stripe event types can fall through the webhook path without a business mutation but still look like successfully processed events. Failed relevant events do not yet have a complete durable, admin-readable diagnostic contract that separates retryable/fixable failures from ignored non-business events.

Application admin billing review already has a reconciliation and audit surface, but it does not yet expose failed Stripe billing event diagnostics as a first-class production support view. Duplicate processed events are idempotent, but failed-event retry and manual-repair semantics need to remain explicit once failed and ignored outcomes share the same event store.

**Desired behavior:**
Stripe billing webhook persistence should classify every signed, parsed Stripe billing event into one of three durable outcomes: `processed`, `ignored`, or `failed`.

Supported events that successfully apply a Workspace billing business action should be recorded as `processed`. Unsupported, future, or irrelevant event types should return a successful webhook response, avoid all Workspace billing mutations, and be recorded, if recorded at all, as `ignored` rather than as completed business processing. Relevant events that cannot be processed because metadata is incomplete, the referenced Workspace cannot be resolved, Stripe object state is contradictory, or another fixable/runtime error occurs should be recorded as `failed` with non-secret diagnostics and an appropriate retry/manual-review contract.

Failed diagnostics must be useful to Application admins and operators without storing raw Stripe payloads, API keys, webhook secrets, payment method details, or unnecessary customer PII. A duplicate delivery of an already processed event should remain idempotent and should not duplicate Credits, entitlements, invoices, or audit entries. A duplicate delivery of a failed event should remain eligible for Stripe retry or manual repair rather than being hidden as already complete.

**Key interfaces:**
- `workspace_billing_stripe_events` persistence model — must support `processed`, `ignored`, and `failed` outcomes while preserving compatibility with existing processed rows.
- Stripe billing webhook response contract — unsupported or irrelevant events should acknowledge successfully; retryable or fixable relevant failures should preserve the existing error semantics needed for Stripe retry.
- Stripe event diagnostic shape — should include event ID, event type, Workspace ID when known, related Stripe object ID when known, failure class, and retry/manual-review guidance.
- Application admin billing state/review response — should expose failed Stripe billing event diagnostics alongside existing reconciliation or billing review context without leaking sensitive Stripe data.
- Stripe event duplicate handling — should suppress already processed business events while allowing failed events to be retried or repaired safely.

**Acceptance criteria:**
- [ ] Stripe billing event persistence supports `processed`, `ignored`, and `failed` outcomes without breaking existing processed rows.
- [ ] Unknown or irrelevant Stripe billing events return a successful response, do not mutate Workspace billing state, and are not recorded as successfully processed business events.
- [ ] Relevant event failures record durable, non-secret diagnostics including event ID, event type, Workspace ID when known, related Stripe object ID when known, failure class, and retry/manual-review guidance.
- [ ] Failed-event diagnostics are visible through the Application admin billing review path without exposing raw Stripe payloads, API keys, webhook secrets, payment method details, or unnecessary customer PII.
- [ ] Duplicate Stripe deliveries continue to be idempotent for processed events, while failed events remain eligible for Stripe retry or manual repair.
- [ ] Backend tests cover processed, ignored, failed, duplicate, and future-unknown event behavior.

**Out of scope:**
- Adding new Stripe billing product flows or changing Free, Pro, Max, Enterprise, Credit pack, or Workspace billing authority semantics.
- Implementing additional Stripe event types beyond the outcome-store and diagnostics behavior required by this issue.
- Storing raw Stripe webhook payload archives.
- Entering, printing, documenting, or changing production Stripe secrets.
- Changing the authoritative Billing ledger model or Workspace product data storage model.
