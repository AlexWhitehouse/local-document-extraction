Category: enhancement

## What to build

Extend scheduled Billing reconciliation so webhook outages or Stripe-side changes do not permanently hide paid outcomes, terminal unpaid invoices, delayed-payment results, or subscription lifecycle drift. Reconciliation should repair only clearly safe paid outcomes through existing idempotent paths and record non-destructive drift for ambiguous states.

**Summary:** Complete production-grade Billing reconciliation coverage for missed Stripe billing outcomes and manual-review drift.

**Current behavior:**
Workspace billing has a scheduled Billing reconciliation path that compares Stripe billing state with Workspace billing records. The existing implementation already has foundations for scanning Stripe Checkout Sessions, invoices, and subscriptions for Workspaces with Stripe customers; repairing safe paid outcomes through idempotent Credit, subscription, Plan override, and Enterprise paths; persisting reconciliation status; recording drift; and showing reconciliation information in the Application admin billing view.

The prerequisite production-readiness slices are complete: paid Plan downgrade invoice activation, delayed Credit pack Checkout outcomes, self-service subscription negative invoice states, payment-required Plan override invoice lifecycle, Enterprise invoice lifecycle hardening, and Stripe subscription lifecycle drift handling. The remaining work is to make scheduled Billing reconciliation prove full production coverage across those flows as one coherent safety net. Webhook outages, Stripe-side changes, delayed-payment outcomes, terminal unpaid invoice states, missed paid invoices, and ambiguous subscription lifecycle changes must not leave Workspace billing silently stale.

**Desired behavior:**
Billing reconciliation should remain an idempotent scheduled check. It may repair only clearly safe paid outcomes by calling the same idempotent activation or Credit grant contracts used by Stripe billing event handling. It must not rewrite the Billing ledger directly, duplicate Included Credits or Purchased Credits, grant unpaid entitlement, or erase historical billing context.

For paid outcomes, reconciliation should detect missed paid Plan downgrade invoices, delayed Credit pack successes, paid payment-required Plan override invoices, paid self-service subscription invoices, and paid Enterprise annual upfront, Enterprise annual overage, and Enterprise ramp-up invoices. Each repair should converge with later webhook delivery or repeated scheduled runs.

For unpaid, terminal, delayed-failure, ambiguous, or Stripe-side lifecycle outcomes, reconciliation should apply only deterministic non-granting state changes that the existing Workspace billing model can safely prove. Everything else should become Application admin-visible Billing reconciliation drift with non-secret observed/expected details, actionable related Stripe object IDs, severity, actionability, timestamps, and open/resolved status semantics.

The Application admin billing view should give operators enough information to understand when reconciliation last checked a Workspace, what open drift remains, and which Stripe objects need review, without exposing raw Stripe payloads, payment method details, API keys, webhook secrets, or unnecessary PII.

- Scheduled Billing reconciliation contract — should continue running from the Worker scheduled handler and checking every Workspace with a Stripe customer without requiring owner interaction.
- Stripe API observation contract — should list enough Checkout Session, invoice, and subscription state to detect missed paid outcomes, delayed-payment results, terminal invoice states, and subscription lifecycle drift.
- Idempotent paid outcome handlers — should be reused for paid Credit pack, paid subscription invoice, paid Plan downgrade invoice, paid payment-required Plan override invoice, and paid Enterprise invoice repairs.
- Non-granting invoice state handling — should preserve or record payment action required, finalization failed, payment failed, voided, marked uncollectible, and delayed-payment failure states without granting Credits or paid entitlement.
- Billing ledger authority — should remain append-only and authoritative for Credit grants, purchases, spending, refunds, and page usage; reconciliation must not mutate ledger history outside existing idempotent ledger operations.
- Billing reconciliation drift records — should capture non-secret observed and expected state, related Stripe object ID, severity, actionability, first/last seen timestamps, and open/resolved status.
- Application admin billing state — should expose reconciliation last checked time, open drift count, drift records, failed or ignored Stripe event diagnostics, and enough related Stripe object IDs for manual review.
