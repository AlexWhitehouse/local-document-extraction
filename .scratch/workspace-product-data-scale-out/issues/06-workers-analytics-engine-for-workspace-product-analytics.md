# Workers Analytics Engine for Workspace Product Analytics

Category: enhancement
Status: completed

## Parent

.scratch/workspace-product-data-scale-out/PRD.md

## What to build

Add Workers Analytics Engine events for non-sensitive Workspace product analytics without creating a global D1 product-data projection. Product operations should remain authoritative in the Workspace product store; analytics emission happens from Worker or Workflow callers after successful product operations and must not fail the user-facing product operation.

Day-one analytics should cover Document submitted, Extraction completed, Extraction failed, Template created, and Template updated. Events may include stable product identifiers and operational metrics, but must not include extracted answers, evidence text, Source file names, account emails, API keys, Source file binary contents, or Document contents.

## Agent Brief

**Category:** enhancement
**Summary:** Emit non-sensitive Workspace product analytics to Workers Analytics Engine after successful authoritative product operations.

**Current behavior:**
Workspace product operations are now authoritative in the Workspace product store for Template creation/update, Document submission, queued Extraction job creation, and Extraction processor completion/failure. The Worker already keeps Workspace control data in global D1 and routes product mutations through the Workspace product store.

There is not yet a Workers Analytics Engine binding or product analytics emission path. As a result, the application cannot answer aggregate Workspace product analytics questions without querying product stores directly or adding a separate product-data projection, both of which are outside the agreed scale-out boundary.

**Desired behavior:**
The backend should emit Workspace product analytics events to Workers Analytics Engine after successful authoritative product mutations for:

- Template created
- Template updated
- Document submitted
- Extraction completed
- Extraction failed

Analytics emission must happen outside the authoritative Workspace product data mutation. A failed analytics write must be logged or otherwise isolated so it does not fail the user-facing API response, queue processing path, or Workflow lifecycle transition.

Events should include useful stable product identifiers and operational facts where available, such as Workspace ID, Template ID, Extraction job ID, event type, lifecycle status or error code, attempt count, Source file MIME type, Source file byte size, model name, Template field count, and duration. Events must not include extracted answers, evidence text, Source file names, account emails, Workspace API keys, Source file binary contents, or Document contents.

No global D1 projection of Workspace product data should be introduced. Workers Analytics Engine is a non-authoritative analytics sink, not a source of truth for workspace-scoped product APIs.

**Key interfaces:**
- `analytics_engine_datasets` Worker configuration — add a clearly named Workers Analytics Engine binding for Workspace product analytics and keep generated Worker environment types in sync.
- `AnalyticsEngineDataset.writeDataPoint()` — use the Workers Analytics Engine data point contract for indexes, blobs, and doubles without leaking customer content or identity data.
- Workspace product analytics event contract — define a typed representation of the supported event names and allowed non-sensitive fields so future emitters do not invent ad hoc payloads.
- Product API mutation paths — emit Template created, Template updated, and Document submitted events only after the corresponding Workspace product store operation has succeeded.
- Extraction processor lifecycle path — emit Extraction completed and Extraction failed events only after the authoritative lifecycle operation has succeeded for the current attempt.
- Tests for product route and Workflow behavior — verify both the emitted event shape and that analytics write failures do not change public operation outcomes.

**Acceptance criteria:**
- [ ] Workers Analytics Engine configuration adds a Workspace product analytics binding and generated Worker environment types include it.
- [ ] Template creation emits one non-sensitive analytics event after successful authoritative Template creation.
- [ ] Template update emits one non-sensitive analytics event after successful authoritative Template update.
- [ ] Document submission emits one non-sensitive analytics event after successful queued Extraction job creation.
- [ ] Extraction completion emits one non-sensitive analytics event after successful authoritative completion.
- [ ] Extraction failure emits one non-sensitive analytics event after successful authoritative failure.
- [ ] Emitted events include stable product identifiers and relevant operational metrics where available.
- [ ] Emitted events exclude extracted answers, evidence text, Source file names, account emails, Workspace API keys, Source file binary contents, and Document contents.
- [ ] Analytics write failures are isolated from user-facing API responses, queue handling, and Workflow lifecycle transitions.
- [ ] No global D1 product-data projection, cross-Workspace product table, or analytics source-of-truth path is introduced.
- [ ] Tests cover representative successful emissions and analytics failure isolation.
- [ ] `npm run typecheck --prefix backend` passes.

**Out of scope:**
- Building an Application admin analytics dashboard.
- Querying or visualizing Workers Analytics Engine data.
- Exporting analytics events to a warehouse or long-term BI system.
- Treating Workers Analytics Engine as authoritative product data.
- Adding a global D1 projection or any other cross-Workspace product-data read model.
- Emitting extracted answers, evidence text, Source file names, account emails, Workspace API keys, Source file binary contents, or Document contents.
- Changing public product API response shapes.
