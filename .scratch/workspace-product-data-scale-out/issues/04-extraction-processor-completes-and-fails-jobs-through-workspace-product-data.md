# Extraction Processor Completes and Fails Jobs Through Workspace Product Data

Category: enhancement
Status: completed

## Parent

.scratch/workspace-product-data-scale-out/PRD.md

## What to build

Route Cloudflare Workflow processing through the Workspace product store for authoritative Extraction job lifecycle transitions. The Workflow remains the **Extraction processor** and still performs long-running model and R2 work outside the Durable Object. It should load and claim jobs through the Workspace product store, read Source files from R2, run extraction, persist Extraction results through the Workspace product store, and mark jobs completed or failed through domain-specific lifecycle operations.

This slice should preserve durable lifecycle semantics: `queued`, `processing`, `completed`, and `failed`. Stale or duplicate attempts must not overwrite newer or terminal lifecycle state. Completion should persist Extraction results and mark the job completed as one authoritative product-data operation.

## Agent Brief

**Category:** enhancement
**Summary:** Move Extraction processor lifecycle completion, failure, and completed result reads onto authoritative Workspace product data.

**Current behavior:**
Document submission now validates Templates through the Workspace product store, uploads Source file bytes to R2, creates queued Extraction jobs in authoritative Workspace product data, and sends background processing messages with Workspace ID, Extraction job ID, Template ID, Template version, and attempt.

The remaining processing path is still split. Queue/Workflow startup and the Cloudflare Workflow still use legacy global D1 product tables to load Extraction jobs, record Workflow metadata, claim jobs for processing, read Template fields, persist Extraction results, mark jobs completed or failed, and serve completed job result reads. The Workflow already performs expensive Source file reads, model invocation, normalization, and R2 cleanup outside the Durable Object; this must remain true after the storage authority moves.

This split means queued Extraction jobs are authoritative in Workspace product data, but completion/failure/results are still authoritative in the legacy global D1 product tables. It also leaves stale and duplicate Workflow attempt safety outside the Workspace product store boundary.

**Desired behavior:**
The Extraction processor should route all authoritative Extraction job lifecycle operations through the Workspace product store after the queue message identifies the Workspace and Extraction job.

Workflow startup and processing should load and claim Extraction jobs through domain-specific Workspace product store operations. A valid claim should transition an eligible `queued` Extraction job to `processing` for the current attempt. Missing, stale, already-processing, completed, or failed jobs should stop safely without model invocation or Source file reads unless the current attempt is valid.

During processing, expensive work must stay outside the Durable Object. The Workflow may use product store responses to discover Source file metadata and submitted Template field definitions, but R2 object reads, model invocation, result normalization, and R2 deletes must run in the Workflow/Worker environment rather than inside the Durable Object.

Completion should persist normalized Extraction results and mark the Extraction job `completed` through one authoritative Workspace product data operation, only when the current Workflow attempt still owns the `processing` job. Stale or duplicate completion attempts must not write results or overwrite terminal lifecycle state.

Failure should mark the Extraction job `failed` with durable error code/message/attempt information through Workspace product data, only when the current Workflow attempt still owns the `processing` job. Stale or duplicate failure attempts must not overwrite newer or terminal lifecycle state.

Customer-facing Extraction job list/detail responses should read from authoritative Workspace product data. Completed job detail responses should include Extraction results from the Workspace product store, ordered and shaped consistently with the existing public API contract. List/detail responses should expose only durable lifecycle states: `queued`, `processing`, `completed`, and `failed`.

Legacy global D1 product tables may remain for rollback/archive, but they must not receive authoritative completed/failed Extraction job rows or Extraction result writes from this slice.

**Key interfaces:**
- `WorkspaceProductStoreRpc` — add domain operations for loading/claiming Extraction jobs, reading submitted Template field definitions for processing, completing jobs with Extraction results, failing jobs with durable error information, and reading job list/detail data.
- `QueueJobMessage` and `DocumentProcessingWorkflowParams` — keep carrying Workspace ID, Extraction job ID, and attempt so background processing can route to the correct Workspace product store and reject stale attempts.
- `DocumentProcessingWorkflow` — continue to own long-running extraction execution while delegating durable lifecycle state and result persistence to the Workspace product store.
- Extraction job lifecycle contract — preserve `queued`, `processing`, `completed`, and `failed` as the only durable statuses; retry behavior remains Cloudflare Workflow step retry behavior, not a durable retryable status.
- Extraction job API contract — preserve existing list/detail response fields where they are already public, including Source file name, Template ID/version, timestamps, attempt metadata, error details for failed jobs, and completed Extraction results.

**Acceptance criteria:**
- [ ] Workflow startup loads the target Extraction job through the Workspace product store using Workspace ID and Extraction job ID.
- [ ] Workflow claims eligible queued jobs through the Workspace product store before reading Source files or invoking the model.
- [ ] Claiming records `processing` state and current attempt only when the job is eligible for that attempt.
- [ ] Missing, stale, completed, failed, or duplicate attempts stop without expensive model invocation or Source file reads.
- [ ] The Workflow does not perform expensive model invocation, R2 reads, or R2 deletes inside the Durable Object.
- [ ] The Workflow reads submitted Template field definitions needed for extraction from authoritative Workspace product data.
- [ ] Workflow completion persists normalized Extraction results through Workspace product data.
- [ ] Workflow completion marks the Extraction job `completed` only when the current attempt still owns the processing job.
- [ ] Workflow failure marks the Extraction job `failed` with durable error code, message, and attempt information only when the current attempt still owns the processing job.
- [ ] Stale or duplicate completion attempts do not write Extraction results and do not overwrite terminal lifecycle state.
- [ ] Stale or duplicate failure attempts do not overwrite newer processing state or terminal lifecycle state.
- [ ] Completed job detail responses read Extraction results from authoritative Workspace product data.
- [ ] Job list/detail responses expose only `queued`, `processing`, `completed`, and `failed`.
- [ ] Legacy global D1 product tables are not written as authoritative completed/failed job rows or Extraction result rows.
- [ ] Existing Cloudflare Workflow retry behavior continues without introducing a durable retryable status.
- [ ] Tests cover claim, completion, failure, stale attempt rejection, duplicate attempt safety, completed job result reads, and avoidance of legacy D1 authoritative writes.

**Out of scope:**
- Moving Document submission queued job creation; that prerequisite is already complete.
- Adding Workspace live update WebSockets.
- Adding Workers Analytics Engine events.
- Building product deletion, Template deletion cascades, or residual Source file cleanup beyond minimal compatibility needed for existing processing cleanup behavior.
- Removing or destructively changing legacy global D1 product tables.

- Moving Source file binaries out of R2.
