# Workspace Product Store Foundation Through Template Create/List

Category: enhancement
Status: completed

## Parent

.scratch/workspace-product-data-scale-out/PRD.md

## What to build

Create the first vertical slice of the Workspace product data scale-out: a SQLite-backed Durable Object per Workspace that becomes the authoritative store for Template creation and listing. The existing global D1 control plane continues to authenticate and authorize the request, then routes accepted Workspace product operations to the Workspace product store. The slice should prove deterministic Workspace ID routing, lazy schema initialization, domain-specific RPC, and product API responses coming from authoritative Workspace product data rather than legacy global D1 product tables.

This slice should keep the user-visible Template create/list API behavior compatible while moving new authoritative Template writes and reads into the Workspace product store. Legacy global D1 product tables remain present for rollback/archive but are no longer the authority for this path.

## Agent Brief

**Category:** enhancement
**Summary:** Establish the first Workspace product store slice by making Template create/list authoritative in a Workspace-addressed SQLite Durable Object.

**Current behavior:**
Workspace-scoped product routes already authenticate and authorize through Workspace control data for both session-authenticated users and Workspace API key clients. After that authorization boundary, Template creation and listing still read and write the legacy global D1 product tables. That keeps Template product rows under the single global D1 storage ceiling. The Worker configuration does not yet expose a Workspace product Durable Object binding for this product-data authority, and starter Template bootstrap still writes through the legacy global D1 Template adapter.

**Desired behavior:**
Template creation and listing should keep their public API behavior compatible while moving new authoritative Template rows and Template field rows into a SQLite-backed Workspace product store. Each Workspace product store should be addressed deterministically by Workspace ID, initialize or upgrade its own SQLite schema lazily through a versioned and idempotent path, and expose domain-specific Template operations rather than a generic SQL/query interface.

The Worker should continue to use global D1 only for Workspace control data on this path: session lookup, Workspace membership authorization, Workspace API key lookup, Workspace limits, and accepted Workspace routing. Only after that authorization succeeds should the request route to the Workspace product store. New Template create/list responses should come from the Workspace product store, not the legacy global D1 product tables. Legacy global D1 product tables should remain in place for rollback/archive and should not be destructively migrated in this slice.

Starter Template creation for new or repaired Workspaces should stay coherent with the new authority. A newly bootstrapped Workspace should not create its starter Template only in legacy global D1 if Template listing now reads from the Workspace product store.

**Key interfaces:**
- Workspace product Durable Object binding and migration configuration: adds the SQLite-backed per-Workspace product authority.
- Workspace product store RPC surface: should expose domain operations for creating and listing Templates, including Template fields and version metadata, without exposing raw SQL to API handlers.
- Template create/list public API surface: should preserve the response shapes and status codes expected by existing session and Workspace API key callers.
- Workspace control-data authorization boundary: should continue to authorize membership or Workspace API key access before any Workspace product store routing occurs.
- Starter Template adapter/bootstrap contract: should create starter Template product data through the same authoritative Workspace product path used by Template listing.
