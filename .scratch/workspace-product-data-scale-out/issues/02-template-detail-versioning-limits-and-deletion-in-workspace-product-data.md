Category: enhancement
Status: completed

## What to build

Complete the Template product-data path inside the Workspace product store. Template detail, update/versioning, field persistence, product-row-dependent Template limits, and deletion should all use authoritative Workspace product data. Request shape validation can remain outside the Durable Object, but authoritative checks such as Template existence, status, current version, field count, version creation, and deletion belong to the Workspace product store.

The completed slice should let a Workspace member create a Template, retrieve it with fields, update fields to create a new Template version, list updated Templates, and delete a Template without using legacy global D1 product tables as the authority.

## Agent Brief

**Category:** enhancement
**Summary:** Complete the Template authority move by serving Template detail, update/versioning, deletion, and product-row-dependent Template limits from Workspace product data.

**Current behavior:**
Template creation and listing have already moved behind the Workspace product store after Workspace control-data authorization. The remaining Template detail, update, and deletion paths still depend on legacy global D1 product tables as the authority. The Workspace product store currently exposes only Template create/list operations, so it does not yet own Template existence checks, current-version reads, ordered Template field reads, Template version creation, Template deletion visibility, or product-row-dependent Template limit enforcement.

Workspace limit configuration remains Workspace control data, but the counts needed to enforce Template limits now need to come from authoritative Workspace product data. Request shape validation can stay outside the Durable Object; authoritative checks that depend on current product rows should move into the Workspace product store.

**Desired behavior:**
Template detail reads should be served from the Workspace product store and include the current Template version's fields in stable field order. Missing, deleted, or stale Templates should continue to produce the expected public API errors.

Template updates should preserve existing public behavior. Metadata-only updates should keep the current Template version. Updates that replace Template fields should create a new Template version, persist the ordered fields in Workspace product data, and return the new version. The Workspace product store should own the current-version check and the version creation so callers cannot construct inconsistent Template state.

Template deletion should use authoritative Workspace product data and remove or hide the Template from normal list/detail responses without relying on legacy global D1 product tables as the source of truth. Broader job/result and Source file cleanup remains a later cleanup slice, but this issue should leave Template deletion coherent for the product-data authority it owns.

Template creation and update should enforce product-row-dependent limits against authoritative Workspace product data, while continuing to read configured limit values from Workspace control data. Template operations should remain exposed through domain-specific Workspace product store methods rather than a raw SQL/query interface.

**Key interfaces:**
- Workspace product store Template RPC surface: add domain operations for Template detail, Template update/version creation, Template deletion or hiding, and Template count/field-count limit enforcement.
- Template public API surface: preserve existing response shapes and status/error semantics for Template detail, update, and deletion where those routes already exist.
- Workspace control-data limit configuration: continue reading configured `max_templates` and `max_fields_per_template` values from Workspace control data, while evaluating product-row counts inside authoritative Workspace product data.
- Template version contract: field changes create a new Template version; metadata-only changes do not.
- Template field ordering contract: Template fields are stored and returned in deterministic position order for the selected Template version.

**Acceptance criteria:**
- [ ] Template detail reads come from authoritative Workspace product data and include current-version fields in deterministic order.
- [ ] Template updates preserve public behavior for metadata-only changes and field-replacement changes.
- [ ] Updating Template fields creates a new Template version in authoritative Workspace product data.
- [ ] Template fields for each version are persisted in authoritative Workspace product data with stable ordering.
- [ ] Template deletion uses authoritative Workspace product data and removes the Template from normal list/detail responses.
- [ ] Product-row-dependent Template limits are enforced using authoritative Workspace product data counts.
- [ ] Configured Workspace limits remain read from Workspace control data.
- [ ] Template operations are exposed as domain-specific Workspace product store methods, with no generic SQL/query interface for callers.
- [ ] Legacy global D1 product tables are not written as authoritative product rows for Template detail, update, or deletion paths.
- [ ] Tests cover Template detail, ordered fields, update/versioning, deletion visibility, Template limit enforcement, and stale or missing Template errors through external behavior.
