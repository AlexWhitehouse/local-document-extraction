# Legacy D1 Product-Table Cutover Hardening

Category: enhancement
Status: completed

## Parent

.scratch/workspace-product-data-scale-out/PRD.md

## What to build

Harden the completed Workspace product data scale-out by verifying that new authoritative product paths no longer depend on legacy global D1 product tables. This is the final cutover verification slice: preserve global D1 for Workspace control data, preserve legacy product tables for rollback/archive, and ensure customer-facing product APIs, Workflow processing, analytics, cleanup, and live updates all use the Workspace product store as the product-data authority.

This slice should not remove legacy product tables. It should identify and close accidental legacy product-table writes or reads that would undermine the new boundary, update tests where needed, and leave the system ready for a later destructive cleanup migration when rollback/archive is no longer needed.

## Agent Brief

**Category:** enhancement
**Summary:** Harden the final Workspace product data cutover so legacy global D1 product tables are retained only for rollback/archive and are not used as authoritative product data.

**Current behavior:**
The Workspace product data scale-out slices have moved Template operations, Document submission, Extraction job lifecycle, Source file cleanup, Workspace product analytics, and Workspace live updates toward the Workspace product store. Global D1 remains the authority for Workspace control data and still contains legacy product tables from the pre-cutover architecture. Some legacy product-table helpers, tests, or compatibility code may still exist, so the final slice needs to verify and close any accidental authoritative reads or writes through those legacy tables.

**Desired behavior:**
All customer-facing Workspace product APIs and background product workflows should use authoritative Workspace product data. Global D1 should continue to serve only Workspace control-data concerns such as accounts, sessions, Workspaces, Workspace memberships, Workspace invitations, Workspace API key lookup, and configured Workspace limits. Legacy global D1 product tables should remain present for rollback/archive, but new product paths must not create, update, delete, or read authoritative Template, Template field, Template version, Extraction job, Extraction result, or Source file metadata rows from those tables. Workspace API key access to product routes must remain compatible for external clients.

**Key interfaces:**
- Workspace product store RPC interface - remains the domain-specific authority for Template operations, Document submission validation, queued Extraction job creation, lifecycle transitions, result reads, deletion candidates, and residual Source file cleanup.
- Workspace authorization boundary - session and Workspace API key requests must resolve Workspace control data before any Workspace product store routing.
- Product API route behavior - Template routes, Extraction job routes, Document submission, and product deletion should return their established public response shapes while sourcing product records from the Workspace product store.
- Extraction processor behavior - queue and Workflow processing should route by Workspace ID and Extraction job ID, claim and complete/fail through the Workspace product store, and avoid legacy global D1 product writes.
- Workspace product analytics - emitted events should use Workers Analytics Engine and must not introduce a global D1 product-data projection.
- Workspace live updates - lifecycle messages should be emitted only after authoritative Workspace product data has been persisted and should remain session-only for this first implementation.
- Worker configuration and schema boundaries - global D1 migrations keep legacy product tables intact, while Durable Object and analytics bindings remain configured for the authoritative product path.

**Acceptance criteria:**
- [ ] Global D1 remains used for Workspace control data: accounts, sessions, Workspaces, memberships, invitations, Workspace API key lookup, and configured Workspace limits.
- [ ] Template create, list, detail, update, and delete behavior uses authoritative Workspace product data and does not require legacy global D1 Template or Template field rows.
- [ ] Extraction job list, detail, and deletion behavior uses authoritative Workspace product data and Source file storage cleanup rather than legacy global D1 job/result rows.
- [ ] Document submission validates Template existence/status/current version through the Workspace product store, stores Source file metadata there, creates the queued Extraction job there, and does not write authoritative legacy D1 job rows.
- [ ] Queue and Workflow processing claim, complete, fail, and read Extraction results through the Workspace product store.
- [ ] Product deletion and residual Source file cleanup use Workspace product data and remain idempotent.
- [ ] Workspace product analytics use Workers Analytics Engine and do not create or depend on a global D1 product-data projection.
- [ ] Workspace live updates are emitted from persisted Workspace product data lifecycle changes and do not expose Extraction results or customer content.
- [ ] Legacy global D1 product tables remain present in migrations/configuration and are not destructively removed in this slice.
- [ ] Tests or static checks fail when customer-facing product paths perform authoritative reads or writes against legacy global D1 product tables.
- [ ] Workspace API key product-route access continues to work for external clients.
- [ ] Backend typecheck passes.
- [ ] Frontend production build passes.
- [ ] Any documentation touched by the implementation continues to reflect the accepted Workspace control-data versus Workspace product-data boundary.

**Out of scope:**
- Removing legacy global D1 product tables.
- Migrating existing legacy global D1 product rows into Workspace product stores.
- Adding a global D1 projection or cross-Workspace SQL surface for product data.
- Building Application admin analytics dashboards or warehouse export.
- Allowing Workspace API keys to open Workspace live update WebSockets.
- Changing public product terminology or redesigning unrelated Better Auth, Workspace invitation, Leave Workspace, password reset, or Application admin flows.
