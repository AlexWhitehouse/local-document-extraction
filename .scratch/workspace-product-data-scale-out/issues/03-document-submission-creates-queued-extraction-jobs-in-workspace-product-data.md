# Document Submission Creates Queued Extraction Jobs in Workspace Product Data

Category: enhancement
Status: completed

## Parent

.scratch/workspace-product-data-scale-out/PRD.md

## What to build

Move the Document submission path onto authoritative Workspace product data. A valid Document submission should validate the selected Template through the Workspace product store, upload the Source file binary to R2, create a queued Extraction job and Source file metadata in the Workspace product store, and then send the background processing message with Workspace ID, Extraction job ID, Template ID, Template version, and attempt.

The slice should preserve the public `queued` response behavior while ensuring the queued Extraction job is authoritative in the Workspace product store. Failure handling must avoid orphaned Source files: if queued job creation fails after R2 upload, delete the R2 object; if queue send fails synchronously after queued job creation, mark the Extraction job failed and delete the uploaded Source file.

## Agent Brief

**Category:** enhancement
**Summary:** Move Document submission so queued Extraction jobs and Source file metadata are created in authoritative Workspace product data.

**Current behavior:**
Template create/list/detail/update/delete have already moved behind the Workspace product store after Workspace control-data authorization. Document submission still validates the selected Template and creates the queued Extraction job through the legacy global D1 product tables. The Source file binary is uploaded to R2, and the background processing message already carries Workspace and Extraction job identifiers, but the queued Extraction job is not yet authoritative in Workspace product data.

This keeps Document submission tied to the single global D1 product-data ceiling and creates a split authority: Templates are already owned by the Workspace product store, while submitted Documents still depend on legacy product rows.

**Desired behavior:**
Document submission should keep the public queued response compatible while moving the authoritative queued Extraction job path into Workspace product data.

Before uploading a Source file, the request should still validate the Document multipart shape and Source file byte-size limit. The selected Template should be validated through the Workspace product store for existence, active/non-deleted status, current Template version, and at least one Template field. Source file binaries should continue to be stored in R2, not Durable Object storage.

After a successful R2 upload, the Workspace product store should persist Source file metadata and create a queued Extraction job tied to the selected Template version. The background processing message should contain enough identifiers for later processing to route back to the Workspace product store, including Workspace ID, Extraction job ID, Template ID, Template version, and attempt.

Failure handling should avoid orphaned Source files and misleading queued work. If queued Extraction job creation fails after R2 upload, the uploaded R2 object should be deleted before the error is returned. If queue send fails synchronously after the queued Extraction job has been created, the Extraction job should be marked `failed` through Workspace product data and the uploaded Source file should be deleted.

**Key interfaces:**
- Workspace product store RPC surface — add domain operations for validating a Template for Document submission, creating queued Extraction jobs with Source file metadata, and marking a newly queued Extraction job failed when queue send fails.
- Document submission API contract — preserve the existing accepted response shape and error semantics where they are already public, including `job_id`, `status: "queued"`, `source_name`, `template_id`, and `template_version`.
- Source file storage contract — R2 remains the authoritative binary store; Workspace product data stores metadata such as object key, MIME type, Source file name, and cleanup state only.
- Background processing message contract — carry Workspace ID, Extraction job ID, Template ID, Template version, attempt, and enqueue timestamp so the Extraction processor can route follow-up work to Workspace product data.
- Workspace control-data boundary — session and Workspace API key authorization must still complete before routing Document submission to the Workspace product store.

**Acceptance criteria:**

- [ ] Document submission validates Template existence, active status, current Template version, and non-empty Template field count through the Workspace product store.
- [ ] Source file binaries are stored in R2, not Durable Object storage.
- [ ] Source file metadata is stored in authoritative Workspace product data.

- [ ] If queued Extraction job creation fails after R2 upload, the uploaded R2 object is deleted.
- [ ] If queue send fails synchronously after queued Extraction job creation, the Extraction job is marked `failed` through Workspace product data and the uploaded Source file is deleted.
- [ ] Legacy global D1 product tables are not written as authoritative queued Extraction job or Source file metadata rows on the Document submission path.
- [ ] Tests cover successful Document submission through the public API surface.
- [ ] Tests cover Template validation errors coming from Workspace product data.

**Out of scope:**
- Moving Extraction processor claim, completion, failure, Extraction result persistence, or completed Source file cleanup. Those belong to the next processing-lifecycle slice.

- Removing or destructively changing legacy global D1 product tables.
