# 16 — React immediately to OS memory pressure

**What to build:** Let the Local Bun Runtime react to operating-system memory pressure immediately, pausing costly Document work and reclaiming safe idle resources before the existing periodic sampler would notice.

**Blocked by:** 02 — Pin and qualify Bun 1.4.0.

**Category:** enhancement

**Status:** completed

- [x] Exactly one runtime memory-pressure listener is registered and removed through the completion-safe shutdown lifecycle.
- [x] Warning and critical signals immediately reduce or pause Extraction processor permits and prevent new large Document admission according to an explicit policy.
- [x] Critical pressure can evict safe idle Workspace product store owners or caches without closing a resource used by active work.
- [x] Diagnostics record pressure level, policy reason, permit change, eviction outcome, and time to recovery without exposing Workspace product data.
- [x] Recovery occurs only through the existing resource controller's sampled headroom and hysteresis rather than immediately cancelling the OS signal.
- [x] Unit/integration coverage injects pressure events deterministically and proves active durable work is not lost; tests do not attempt to exhaust host memory.
- [x] Large-Document stress measurements record peak RSS, queue latency, pause duration, recovery time, and completed/failed work before and after the policy.

> ## Agent Brief
>
> **Category:** enhancement  
> **Summary:** Connect Bun 1.4's OS `memoryPressure` event to the existing adaptive resource controller, with an immediate explicit warning/critical policy, safe idle-store reclamation, observable hysteretic recovery, and completion-safe listener removal.
>
> **Current behavior:** The resource controller samples process RSS, CPU, event-loop lag, gateway outcomes, and storage every five seconds. A host-level pressure notification between samples has no effect. Submission admission consults only current RSS/disk state, the Workspace product-store registry evicts idle owners only when at capacity, and runtime shutdown owns signal listeners but no memory-pressure listener.
>
> **Desired behavior:** One composition-owned listener forwards `warning`/`critical` into an injectable controller seam. Warning immediately halves processor permits (minimum one) and rejects large submissions; critical pauses processors, rejects all submissions, and evicts every currently idle product-store owner while preserving active leases. The signal triggers sampling but cannot clear itself: three consecutive sampled headroom observations are required before the controller clears the latch and restores the pre-pressure permit level. Diagnostics expose only level, reason, times, permit transition, safe eviction count, and recovery duration. Runtime shutdown unregisters the listener exactly once before durable resources close.
>
> **Key interfaces:** Bun/Node `Process` event emitter; `createLocalResourceController`; `LocalResourceControllerSnapshot`; `canReserveSubmission`; `sampleNow`; extraction queue `setMaxConcurrent`; `LocalWorkspaceProductStoreRegistry`; runtime shutdown recurring-work phase; diagnostics endpoint.
>
> **Acceptance criteria:**
>
> - [x] A listener lifecycle seam registers one `memoryPressure` listener, forwards both supported levels, and removes that same listener idempotently during runtime shutdown.
> - [x] Warning halves current permits with a floor of one and rejects requests at or above the documented large-submission threshold; critical sets permits to zero and rejects every new submission.
> - [x] Critical pressure evicts all idle registry owners and never closes an actively leased store; the active store remains usable and may be evicted after release on a later critical event.
> - [x] Snapshot diagnostics contain no Workspace identifiers or document data and record level, policy reason, signalled/recovered time, permit before/after, evicted owner count, and recovery duration.
> - [x] A pressure latch survives the signal-triggered sample and clears only after three consecutive sampled headroom observations; durable queued/active work is retained throughout.
> - [x] A repeatable injected-pressure large-Document benchmark compares policy-disabled and policy-enabled modes and writes all requested latency, pause, recovery, RSS, completed, and failed measurements.
> - [x] Bun 1.4 focused tests, full unit/typecheck/lint/build, runtime smoke, and Chromium journey remain green.
>
> **Out of scope:** Synthesizing real host OOM conditions, cancelling active extraction/model requests, evicting leased stores, changing durable retry semantics, OS-specific pressure thresholds, or using this event as a replacement for RSS/disk admission limits.

Implemented and verified on Bun 1.4.0. Runtime composition owns one completion-safe listener; the adaptive controller applies the documented warning/critical admission and permit policy, evicts only idle registry owners, emits privacy-safe incident/recovery diagnostics, and requires three headroom samples before restoring the pre-pressure permit level. A real queue integration retained two active jobs plus one durable pending job across a critical pause. The bounded 12-job local comparison recorded 121.52 MiB versus 105.55 MiB peak RSS, 54.83 ms versus 96.86 ms P95 queue latency, 41.68 ms pause, 42.86 ms recovery, and 12 completed/0 failed in both disabled/enabled modes; see `../evidence/16-memory-pressure-backpressure.md`. Root CI passed with 191 backend tests including runtime smoke, 250 frontend tests, coverage and build; the Chromium extraction journey also passed.
