> ## Agent Brief
>
> **Category:** enhancement  
> **Summary:** Add an authenticated, pre-parser Document request-body boundary backed by Bun's server hard cap, derive both from the Source-file and multipart limits, and retain the existing structured `400 source_file_too_large` contract for requests the application can classify.
>
> **Current behavior:** Bun accepts its default 128 MiB request body. The `/v1/extract` handler authenticates and acquires Workspace operations/stores before Busboy begins streaming. Busboy caps the file at the Workspace Source limit and an inner transform caps the whole request at Source bytes plus an unexplained 1 MiB. A known oversized `Content-Length` therefore reaches expensive product setup, while Bun's own hard-limit response would be an empty generic 413 that the application cannot intercept.
>
> **Desired behavior:** Define one shared logical request limit as the configured Source-file bytes plus an envelope allowance derived from the parser's three 8 KiB fields and bounded multipart framing. Measure a maximum-shaped browser `FormData` envelope in a test. After either session or API-key authorization—but before Workspace operation/store acquisition—reject malformed lengths or known lengths above that logical limit using the current structured product error. Reuse the same logical limit in the streaming parser for chunked/lying clients. Configure Bun's emergency `maxRequestBodySize` one envelope beyond the logical limit so normal boundary rejections remain structured while the runtime still has a derived hard stop.
>
> **Key interfaces:** `DEFAULT_MAX_SOURCE_FILE_BYTES`; `Bun.serve.maxRequestBodySize`; `handleLocalDocumentSubmission`; `authorizeLocalProductRequest`; `parseLocalMultipartSubmission`; Busboy limits; `HttpError`; submission admission/body draining; temporary Source promotion and job creation.
>
> **Acceptance criteria:**
>
> - [x] Shared constants/functions explain the multipart envelope calculation and drive application preflight, stream limiting, admission reservation, and Bun's hard request-body cap.
> - [x] Boundary tests prove known lengths one byte below and exactly at the logical request limit proceed, while one byte above returns the established `400` JSON `source_file_too_large` response.
> - [x] A maximum-shaped browser `FormData` measurement fits within the derived allowance, and exact-limit Source files remain eligible while Source-limit-plus-one still fails independently.
> - [x] Session and Workspace API-key requests execute the identical authenticated preflight before product-store acquisition or Source promotion.
> - [x] Chunked/unknown-length, malformed multipart, and aborted oversized streams fail with bounded temporary output and create no job or promoted Source file.
> - [x] Existing MIME, PDF, field-name/part-count, and concurrent resource-admission tests stay green as independent defenses.
> - [x] A repeatable real-server oversized-body stress lane records request count, response latency, peak RSS growth, connection settlement, and temporary/promoted/job outcomes without exhausting host memory.
> - [x] Bun 1.4 focused tests, full typecheck/lint/unit/build/runtime smoke, and Chromium journey remain green.
>
> **Out of scope:** Changing the public Source-file limit, changing the established product error status/code, buffering multipart bodies, trusting `Content-Length` as the only defense, or promising a structured response after Bun itself terminates an arbitrarily larger malicious body at the emergency cap.

Implemented and verified on Bun 1.4.0. One 32 KiB envelope allowance is derived from three 8 KiB parser fields plus 8 KiB of framing; the maximum-shaped browser fixture measured 25,378 bytes. Authenticated known-length preflight, unknown/chunked stream limiting, admission reservation, and Bun's emergency cap now share that calculation. The exact Source maximum is accepted after correcting Busboy's limit sentinel to maximum-plus-one. Session and API-key oversize requests both returned the established structured `400 source_file_too_large` response without creating a Workspace store or job. The real-server stress run produced 24/24 structured responses at 16.84 ms P95, 34.47 MiB peak RSS growth, four settled aborted connections, and zero pending handlers, temporary files, promoted Sources, or jobs; see `../evidence/17-document-body-limit-stress.md`. Root CI passed with 200 backend tests including runtime smoke, 250 frontend tests, coverage and build; the Chromium journey also passed.
