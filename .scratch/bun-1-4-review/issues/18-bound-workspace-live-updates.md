# 18 — Bound Workspace live-update idle and backpressure behaviour

**What to build:** Keep legitimate Workspace live update connections stable when quiet, bound the cost of slow or abusive clients, and expose enough diagnostics to distinguish a delivered, delayed, dropped, or reconnected update.

**Blocked by:** 02 — Pin and qualify Bun 1.4.0.

**Category:** enhancement

**Status:** completed

- [x] The Local Bun Runtime has an intentional idle policy that keeps a normal receive-only browser connected beyond the previous default timeout without unnecessary re-authentication or Extraction job reloads.
- [x] Incoming WebSocket payload size is tightly bounded because product clients do not send application messages.
- [x] Outgoing send status and backpressure are handled explicitly; a thrown call is not the only signal used to classify delivery.
- [x] Slow-client buffering has a documented limit and close/drop policy that cannot create unbounded process memory.
- [x] Aggregate diagnostics expose open/pending connections and Workspace subscriber counts without revealing Workspace identifiers or message content.
- [x] Tests cover an idle browser lasting more than two minutes, a stalled receiver, connection cleanup, Workspace authorization isolation, and frontend reconnection after genuine loss.
- [x] A fanout benchmark records the current Local live update hub cost before any separate native topic pub/sub migration is proposed.

> ## Agent Brief
>
> **Category:** enhancement  
> **Summary:** Give Workspace live updates an explicit five-minute idle policy, tiny receive-only payload allowance, per-socket backpressure cap, send-status classification, privacy-safe aggregate diagnostics, and a baseline fanout benchmark.
>
> **Current behavior:** Bun's default 120-second idle timeout applies to quiet receive-only browsers, incoming messages are ignored under the default 16 MiB payload cap, and each socket may buffer up to Bun's default 16 MiB without automatic closure. The hub treats only thrown `send()` calls as failure even though Bun returns `>0`, `-1`, or `0` for delivered, backpressured, or dropped sends. Diagnostics do not expose live-connection state or delivery outcomes.
>
> **Desired behavior:** Configure a 300-second idle timeout with automatic pings, a 64-byte incoming payload cap, a 64 KiB per-socket backpressure limit, and close-on-limit. Close any supported-size client message with policy code 1008 because the channel is receive-only; Bun terminates larger payloads at the native limit (observed by Bun 1.4 clients as abnormal close 1006 rather than a 1009 frame). Teach the hub to classify send results, mark `-1` sockets pending until `drain`, and remove/close sockets returning `0` or throwing. Expose only aggregate open/pending/workspace subscriber and lifetime/delivery counters. Keep the existing authorized in-memory Workspace map until benchmark evidence justifies a separate native-topic migration.
>
> **Key interfaces:** Bun `WebSocketHandler` options; `ServerWebSocket.send()` status; `drain`; `getBufferedAmount`; `Server.pendingWebSockets`; `LocalLiveUpdateHub`; runtime diagnostics; `upgradeLocalLiveUpdate`; frontend reconnect/list refresh effect.
>
> **Acceptance criteria:**
>
> - [x] A shared WebSocket policy configures `idleTimeout: 300`, `sendPings: true`, `maxPayloadLength: 64`, `backpressureLimit: 65536`, and `closeOnBackpressureLimit: true` in runtime and real-server tests.
> - [x] A normal receive-only connection remains eligible beyond 120 seconds; a supported-size inbound message closes at 1008 and a payload above 64 bytes is terminated by Bun's native limit with its observed client close semantics recorded.
> - [x] Hub tests classify positive sends as delivered, `-1` as backpressured/pending until drain, `0` as dropped and closed, and exceptions as failed and closed.
> - [x] The 64 KiB Bun buffer cap is the only per-client outbound queue; the JavaScript hub never retains message payloads for retry.
> - [x] Diagnostics report current open/pending/workspace totals, subscriber distribution, lifetime opened/closed, and delivery counts without Workspace IDs, message content, job IDs, or account data.
> - [x] Existing real authorization isolation and forced cleanup tests pass, and the frontend genuine-loss test proves one delayed reconnect plus HTTP job revalidation.
> - [x] A repeatable current-hub fanout benchmark records subscribers, events, attempted sends, wall time, per-send cost, throughput, and RSS before proposing native topics.
> - [x] Bun 1.4 focused tests, full typecheck/lint/unit/build/runtime smoke, and Chromium journey remain green.
>
> **Out of scope:** Migrating to Bun native pub/sub, cross-process fanout, guaranteed delivery/replay, application messages from browsers, changing upgrade authorization, or storing Workspace IDs/message bodies in diagnostics.

Implemented and verified on Bun 1.4.0. Runtime and real-server tests share the five-minute/automatic-ping, 64-byte inbound, and 64 KiB close-on-backpressure policy. A real supported client message closed at 1008; Bun terminated 65 bytes at its native limit and the Bun client observed 1006. Hub send results are now classified as delivered/backpressured/dropped/failed, `drain` clears pending state, and no JavaScript retry queue exists. Runtime smoke proved aggregate open/pending/subscriber diagnostics while excluding the Workspace ID; authorization isolation, forced cleanup, and frontend delayed reconnect plus HTTP revalidation remain green. The synthetic current-hub baseline covered 1–1,000 subscribers and up to 500,000 attempted sends (2.42 ms wall, 0.005 µs/callback at 1,000 in this local optimized run); see `../evidence/18-live-update-fanout.md` and its explicit non-network scope. Root CI passed with 203 backend tests including runtime smoke, 250 frontend tests, coverage and build; the Chromium journey and frozen install also passed.
