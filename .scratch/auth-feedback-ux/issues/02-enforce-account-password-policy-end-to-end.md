# Enforce Account Password Policy End-To-End

Category: enhancement
Status: complete

## Parent

## What to build

Enforce the **Account password policy** consistently before account creation. The policy should be encapsulated behind a small testable interface and applied on the backend before Better Auth processes email/password sign-up, returning a stable safe failure when the policy is not met.

## Acceptance criteria

- [x] The Account password policy is represented by a small testable module/interface.
- [x] The policy requires at least 8 characters, one ASCII uppercase letter, one ASCII number, and one special character.
- [x] Special character means any non-alphanumeric character.
- [x] Better Auth remains configured with a minimum password length of 8.
- [x] Backend email/password sign-up rejects weak passwords before account creation.
- [x] Backend password-policy failures return a stable error code such as `password_policy_not_met` and a safe user-facing message.
- [x] Strong passwords proceed to the normal auth handling path.
- [x] Password-policy tests assert external behavior of valid and invalid passwords, not implementation details.
- [x] Backend request validation is covered where feasible through request/response behavior.
- [x] Backend typecheck passes.

## Agent Brief

**Category:** enhancement
**Summary:** Enforce the Account password policy consistently before email/password account creation.

**Current behavior:**
The backend enables Better Auth email/password authentication, but the full **Account password policy** is not enforced before account creation. Better Auth supports a minimum password length option, but the agreed policy also requires one ASCII uppercase letter, one ASCII number, and one special character.

**Desired behavior:**
The **Account password policy** should be represented behind a small, testable interface and enforced on the backend before Better Auth processes email/password sign-up. Weak passwords should be rejected before account creation with a stable safe error code such as `password_policy_not_met` and a user-facing safe message. Strong passwords should proceed to normal auth handling.

**Key interfaces:**
- The Account password policy interface should answer whether a password satisfies the policy and expose enough information for tests and UI callers to understand unmet requirements.
- The backend auth request handling path should reject weak email/password sign-up requests before account creation.
- Better Auth email/password configuration should continue to use minimum password length 8, with additional complexity checks enforced by the app-owned policy gate.

**Acceptance criteria:**
- [ ] The Account password policy is represented by a small testable module/interface.
- [ ] The policy requires at least 8 characters, one ASCII uppercase letter, one ASCII number, and one special character.
- [ ] Special character means any non-alphanumeric character.
- [ ] Better Auth remains configured with a minimum password length of 8.
- [ ] Backend email/password sign-up rejects weak passwords before account creation.
- [ ] Backend password-policy failures return a stable error code such as `password_policy_not_met` and a safe user-facing message.
- [ ] Strong passwords proceed to the normal auth handling path.
- [ ] Password-policy tests assert external behavior of valid and invalid passwords, not implementation details.
- [ ] Backend request validation is covered where feasible through request/response behavior.
- [ ] Backend typecheck passes.

**Out of scope:**
- Frontend live password-policy checklist behavior.
- Confirm Password behavior.
- Sign-in failure toast behavior.
- Password reset flows.
- Email verification flows.
- Database schema changes.
