# Add Workspace Access Management Toasts

Category: enhancement
Status: completed

## Parent

## What to build

Add toast feedback to workspace access-management actions: creating and cancelling **Workspace invitations**, accepting and declining **Workspace invitations**, and applying **Workspace member actions**. The copy should use resolved domain vocabulary and avoid implying outbound email delivery for invitations.

This slice should cover member removal, admin promotion, and workspace ownership transfer with precise membership wording. Existing confirmation-cancel behavior should remain quiet, and activity-log detail should remain available.

- [x] Creating a **Workspace invitation** shows success, validation-blocker, and friendly failure toasts.
- [x] Invitation creation success copy uses “Successfully invited {email}”.

- [x] Accepting a **Workspace invitation** shows success and failure toasts.

- [x] **Workspace member action** failures show friendly error toasts.
- [x] Cancelling existing confirmations produces no toast.
- [x] Background access-management listing/refresh remains toast-free.

## Agent Brief

**Category:** enhancement
**Summary:** Add toast feedback for Workspace invitations and Workspace member actions.

**Current behavior:**
Workspace invitation and access-management actions primarily update state and write activity-log messages. Users do not consistently receive immediate visible feedback when creating, cancelling, accepting, or declining Workspace invitations, or when applying Workspace member actions such as removal, admin promotion, or ownership transfer. The shared notification module already contains the resolved domain vocabulary for these actions.

**Desired behavior:**
Workspace invitation actions and Workspace member actions should use centralized Sonner toast feedback for success, validation blockers, and friendly failures. Toast copy should use the resolved domain terms: Workspace invitation, Invitation cancelled, Invitation declined, Workspace member action, Removed {member} from workspace, Made {member} an admin, and Workspace ownership transferred to {member}. Invitation creation success should say Successfully invited {email} without implying outbound email delivery. Existing confirmation-cancel behavior should remain quiet, background access-management listing or refresh should stay toast-free, and activity-log detail should remain available.

**Key interfaces:**

- Toast notification module - should supply Workspace invitation and Workspace member action notification message/severity for handlers.
- Workspace invitation transition helpers - should remain the source of request, validation, success, failure, refresh, and context transition decisions.
- Workspace member action transition helper - should remain the source of member action request and transition decisions.
- Access-management action handlers - should emit toasts only for explicit user-initiated outcomes, not passive listing or refresh.

**Acceptance criteria:**

- [ ] Creating a Workspace invitation shows success, validation-blocker, and friendly failure toasts.
- [ ] Invitation creation success copy uses “Successfully invited {email}”.
- [ ] Cancelling a pending Workspace invitation shows success/failure toasts and uses “Invitation cancelled” copy.
- [ ] Accepting a Workspace invitation shows success and failure toasts.
- [ ] Declining a Workspace invitation shows success and failure toasts, with success copy using “Invitation declined”.
- [ ] Removing a member uses “Removed {member} from workspace” success copy.
- [ ] Making a member an admin uses “Made {member} an admin” success copy.
- [ ] Transferring ownership uses “Workspace ownership transferred to {member}” success copy.
- [ ] Workspace member action failures show friendly error toasts.
- [ ] Cancelling existing confirmations produces no toast.
- [ ] Background access-management listing and refresh remain toast-free.
- [ ] Existing activity-log detail remains available.
- [ ] Focused frontend verification passes for the changed notification behavior.

**Out of scope:**

- Changing outbound email behavior for Workspace invitations.
- Changing invitation or member-management API contracts.
- Changing Workspace permission policy.
- Changing Sonner global configuration, placement, duration, theme, or styling.
