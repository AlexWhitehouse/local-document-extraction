## Agent Brief

**Category:** enhancement

**Summary:** Rename workspace source-size limits from legacy image byte terminology to **Source file** byte terminology across persistence, policy interfaces, validation, configuration, docs, and tests.

**Current behavior:**
Workspace source-size limits still use legacy image-oriented names in application-owned schema, workspace policy/listing interfaces, document submission validation inputs, environment/configuration names, and tests. The runtime behavior already enforces a workspace-specific byte limit when present and otherwise falls back to a default configured byte limit.

**Desired behavior:**
Workspace source-size limits should use **Source file** terminology wherever the application owns the name. Existing limit behavior must be preserved: workspace-specific limits override the default, and the default applies when the workspace has no custom limit. This should be done through a new forward migration; historical migrations must remain immutable.

Configuration should use **Source file** terminology for the default source-size limit. Any authored docs that describe the default source-size limit should use the renamed configuration and domain language. Standards-level MIME strings and generated/platform-owned vocabulary may retain `image` only where required by external contracts.

**Key interfaces:**
- Workspace persistence schema — the workspace source-size limit column should be renamed with **Source file** terminology through a forward migration.
- Workspace policy/listing return shapes — accepted workspace context/listing data should expose the byte limit using the renamed application-owned field.
- Document submission validation boundary — extraction request validation should receive and enforce the renamed **Source file** byte limit while preserving the existing too-large error behavior.
- Environment/configuration shape — the default source-size limit variable should use **Source file** terminology.
- Tests and authored docs — workspace-specific and default source-size limit behavior should be verified and documented with the new terminology.

**Acceptance criteria:**
- [x] A new forward migration renames the workspace source-size limit to **Source file** byte terminology without editing historical migration files.
- [x] Workspace policy/listing flows expose the source-size limit using the new application-owned name.
- [x] Document submission validation enforces the renamed **Source file** byte limit for both workspace-specific and default limits.
- [x] Environment/configuration names use **Source file** terminology for the default source-size limit.
- [x] Authored documentation references the renamed source-size limit configuration.
- [x] Tests verify workspace-specific and default source-size limits still apply.
- [x] Backend typecheck succeeds.

**Out of scope:**
- Changing the supported Document source formats.
- Changing the `document` multipart submission-field contract.
- Renaming Extraction job source metadata already covered by the completed dependency issue.
- Renaming R2 bindings, physical buckets, queues, workflows, or broader Cloudflare resources.
- Redesigning Workspace policy beyond terminology and interface shape required for source byte limits.
- Rewriting historical migration files.
- Hand-editing generated Cloudflare platform types or built frontend assets.
- Removing standards-level MIME strings such as `image/png`.
