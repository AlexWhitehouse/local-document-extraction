# Rename Cloudflare resources to Document Extraction naming

Status: completed
Category: enhancement
Type: AFK
User stories covered: 23, 25, 26, 27, 43, 48, 49

## Parent

`.scratch/document-extraction-terminology/PRD.md`

## What to build

Move Cloudflare resource naming away from legacy image terminology for application-owned infrastructure: Worker service name, D1 database name, R2 **Source file** bucket name, queue name, workflow name/binding/class, runtime bindings, cleanup paths, and deployment documentation. This slice should preserve runtime behaviour while coordinating any operator-owned provisioning or data migration required for renamed Cloudflare resources.

## Acceptance criteria

- [x] Worker service naming uses **Document Extraction** terminology instead of legacy image terminology.
- [x] D1 database naming uses **Document Extraction** terminology instead of legacy image terminology.
- [x] Queue naming uses **Document Extraction** or **Extraction job** terminology instead of legacy image terminology.
- [x] Workflow resource naming uses `documentProcessingWorkflow` / **Document** terminology instead of legacy image terminology.
- [x] Worker storage binding names use **Source file** terminology.
- [x] Document submission writes **Source files** through the renamed binding.
- [x] Workflow processing reads and deletes **Source files** through the renamed binding.
- [x] Cascade deletion deletes **Source files** through the renamed binding.
- [x] Deployment/support docs name the non-legacy Cloudflare resources, including D1 database, R2 bucket, queue, Worker, and workflow where applicable.
- [x] Any required operator action for provisioning, rebinding, or migrating physical Cloudflare resources is explicitly documented.
- [x] Tests verify storage read/write/delete behaviour still works through the new naming.
- [x] Backend typecheck succeeds.

## Ready-For-Human Brief

**Category:** enhancement

**Summary:** Move application-owned Cloudflare resource names and source-file storage bindings from legacy image terminology to Document Extraction terminology.

**Current behavior:**
Application-owned Cloudflare resource names still use legacy image-oriented vocabulary for the Worker service, D1 database, R2 Source file bucket, queue, workflow resource, workflow binding, workflow class/type names, runtime bindings, storage cleanup paths, and deployment documentation. Document submission, workflow processing, and cascade deletion already rely on the same storage behavior, but the names do not match the resolved **Document Extraction**, **Document**, **Source file**, and **Extraction job** glossary.

**Desired behavior:**
Application-owned Cloudflare resource names should use non-legacy **Document Extraction**, **Document**, **Source file**, or **Extraction job** terminology while preserving runtime behavior. Document submission should write **Source files** through the renamed storage binding. Workflow processing should read and delete **Source files** through the renamed binding. Cascade deletion should continue deleting stored **Source files** through the renamed binding. Authored deployment/support docs should name the new Cloudflare resources and clearly document any required operator action for provisioning, rebinding, data migration, rollout sequencing, or cleanup of old resources.

This is marked `ready-for-human` because the code change is specified, but physical Cloudflare resource naming can require operator-owned provisioning, data migration, deployment sequencing, and production verification decisions that should not be delegated blindly to an AFK agent.

**Key interfaces:**
- Worker configuration resource names — Worker service, D1 database, R2 bucket, queue, and workflow resources should use non-legacy Document Extraction terminology where the application owns the name.
- Worker environment bindings — storage, queue, and workflow bindings should use **Source file**, **Extraction job**, or **Document processing** terminology rather than legacy image terminology.
- Workflow class and payload types — application-owned workflow names should move toward `documentProcessingWorkflow` / **Document** terminology while preserving the existing processing behavior.
- Document submission storage boundary — submitted **Documents** should still write the original binary as a **Source file** with unchanged metadata and cleanup behavior.
- Workflow processing and cascade deletion boundaries — stored **Source files** should still be read and deleted reliably through the renamed binding.
- Deployment/support documentation — operator-owned resource creation, rebinding, migration, and rollout requirements must be explicit.

**Acceptance criteria:**
- [x] Worker service naming uses **Document Extraction** terminology instead of legacy image terminology.
- [x] D1 database naming uses **Document Extraction** terminology instead of legacy image terminology.
- [x] Queue naming uses **Document Extraction** or **Extraction job** terminology instead of legacy image terminology.
- [x] Workflow resource naming uses `documentProcessingWorkflow` / **Document** terminology instead of legacy image terminology.
- [x] Worker storage binding names use **Source file** terminology.
- [x] Document submission writes **Source files** through the renamed binding.
- [x] Workflow processing reads and deletes **Source files** through the renamed binding.
- [x] Cascade deletion deletes **Source files** through the renamed binding.
- [x] Deployment/support docs name the non-legacy Cloudflare resources, including D1 database, R2 bucket, queue, Worker, and workflow where applicable.
- [x] Any required operator action for provisioning, rebinding, migrating existing data, deployment sequencing, or retiring old resources is explicitly documented.
- [x] Tests verify storage read/write/delete behavior still works through the new naming.
- [x] Backend typecheck succeeds.

**Out of scope:**
- Changing supported Document source formats.
- Changing the `document` multipart submission-field contract.
- Reintroducing legacy `image` or generic `file` compatibility aliases.
- Rewriting historical D1 migration files.
- Hand-editing generated Cloudflare platform types or built frontend assets.
- Removing standards-level MIME strings such as `image/png`.
- Changing Cloudflare platform API option keys that require image vocabulary.
- Redesigning the Extraction job lifecycle state model.
- Migrating existing R2 object contents beyond the naming/configuration work required to use the new bucket.
- Changing the repository folder name, package names, or local machine path unless a maintainer explicitly decides those are part of the operator-owned rename.
