# Document Billing Usage Invalidation

Category: enhancement
Status: completed

## Parent

## What to build

Emit billing-usage Workspace context invalidation after accepted Document submission and after effective Credit refund mutations. The accepted submission invalidation should happen only after the API has reached the accepted queueing point it reports to the caller, not immediately after a temporary Credit reservation that later acceptance steps can still refund.

Connected frontends should use the throttled selected Workspace context refresh path to update remaining Credits, remaining Plan page capacity, **Billing operational status**, and upload-blocking state.

## Agent Brief

**Category:** enhancement
**Summary:** Emit billing-usage Workspace context invalidation after accepted Document submission and effective Credit refunds.

**Current behavior:**
The backend reserves Credits or records billing usage before a Document submission is fully accepted, and it refunds prepaid Credit reservations in failure compensation paths. The Workspace live update protocol already supports Workspace context invalidation events, and connected frontends already know how to refresh the selected accepted **Workspace context** when an invalidation arrives. However, Document submission and submission-compensation paths do not yet reliably emit `billing_usage` invalidations at the points where remaining Credits, remaining Plan page capacity, **Billing operational status**, or upload-blocking state may have changed.

**Desired behavior:**
Accepted Document submissions should emit a `workspace_context_invalidated` event with reason `billing_usage` only after the submission reaches the accepted queueing point reported to the caller. Temporary Credit reservation alone must not emit the accepted-submission invalidation, because later acceptance steps may still fail and refund the reservation before the caller receives an accepted response.

When a submission failure path performs an effective Credit refund or confirms an already-effective refund for the same reservation, it should emit `billing_usage` invalidation after the refund result is known. Compensation calls that find no refundable reservation or otherwise perform no effective refund should not emit unnecessary billing-usage invalidation.

Connected frontends should continue using the existing throttled selected **Workspace context** refresh path. The live payload must remain a freshness hint and must not include computed **Billing operational status**, remaining Credits, remaining Plan page capacity, invoice details, payment details, account identity, API keys, or owner-only billing state.

**Key interfaces:**
- Document submission acceptance flow — should publish billing-usage invalidation after the durable billing mutation, Source file persistence, queued **Extraction job** creation, and queue acceptance have all succeeded enough for the API to return an accepted submission.
- Credit refund/compensation flow — should inspect the refund result and publish billing-usage invalidation only when the refund call returns an effective refund result rather than a no-op.
- Billing ledger refund contract — should preserve a distinguishable result for effective refunds, already-effective idempotent refunds, and no refundable reservation.
- Workspace live update invalidation event — should use the existing `workspace_context_invalidated` event shape with reason `billing_usage` and an occurrence timestamp, without embedding billing or identity data.
- Frontend live invalidation refresh path — should refresh the selected accepted **Workspace context** and render remaining Credits, remaining Plan page capacity, upload-blocking state, and **Billing operational status** from the refreshed backend response.

**Acceptance criteria:**
- [x] Accepted Document submission emits billing-usage invalidation after the Document has reached the accepted queueing point.
- [x] Temporary Credit reservation alone does not emit accepted-submission invalidation when later acceptance steps can still fail.
- [x] Submission failure paths that reserve and then refund Credits do not emit accepted-submission invalidation before failure.
- [x] Effective Credit refund mutations emit billing-usage invalidation when they change or confirm Workspace capacity.
- [x] Compensation calls that find no refundable reservation do not create unnecessary billing-usage invalidation.
- [x] Connected frontends update remaining Credits, remaining Plan page capacity, and upload-blocking badges from selected Workspace context refresh.
- [x] Focused backend coverage verifies accepted submission invalidation, failed-submission refund invalidation, and no-op compensation behavior.
- [x] Focused frontend coverage verifies live billing-usage invalidation refreshes selected Workspace context without full Workspace-list refresh.

**Out of scope:**
- Changing Document submission billing rules, Credit pricing, Plan limits, Billable Document page counting, or final backend enforcement.
- Emitting billing-entitlement invalidation for owner-facing billing changes, Application admin billing changes, or Stripe billing events; those are separate issues.
- Emitting Template-limit, member-limit, or Workspace-access invalidation; those are separate issues.
- Sending computed billing summaries, badge strings, invoices, payments, account identity, API keys, or owner-only billing state over Workspace live updates.
- Replacing HTTP Workspace context refresh with websocket-sourced state.
