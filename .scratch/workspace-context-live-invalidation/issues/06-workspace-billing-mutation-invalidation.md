# Workspace Billing Mutation Invalidation

Category: enhancement
Status: completed

## Parent

.scratch/workspace-context-live-invalidation/PRD.md

## What to build

Emit billing Workspace context invalidation after owner-facing and Application admin Workspace billing mutations that change Workspace billing state, remaining Credits, Plan limits, or submission-blocking state. Connected frontends should become eventually fresh through the selected Workspace context refresh path without exposing billing details in live update payloads.

This slice covers direct app/API billing mutations, not Stripe webhook event processing.

## Acceptance criteria

- [x] Goodwill Credit grants and effective revocations emit billing invalidation after successful mutation.
- [x] Plan changes and scheduled billing-change cancellations emit billing entitlement invalidation after successful mutation.
- [x] Subscription cancellation actions emit billing entitlement invalidation after successful mutation.
- [x] No-billing mode changes emit billing entitlement invalidation after successful mutation.
- [x] Plan overrides and Enterprise deal term changes emit billing entitlement invalidation after successful mutation.
- [x] Failed billing mutations do not emit invalidation when no durable state changed.
- [x] Live update payloads for these invalidations contain only reason and occurrence metadata, not billing details.
- [x] Connected frontends refresh selected Workspace context and update operational badges from backend recomputation.
- [x] Focused backend billing coverage verifies invalidation emission for successful mutations and no-emission failure cases.
- [x] Focused frontend coverage verifies billing invalidation uses selected Workspace context refresh and bounded throttle behavior.

## Agent Brief

**Category:** enhancement
**Summary:** Emit Workspace billing mutation invalidation after direct owner-facing and Application admin Workspace billing changes.

**Current behavior:**
The selected **Workspace context** refresh path and `workspace_context_invalidated` live update event already exist. Document submission, Template mutation, and Workspace membership/access slices already use the invalidation protocol. Direct owner-facing and Application admin **Workspace billing** mutations can still change remaining Credits, entitlement, **Billing operational status**, Plan limits, or submission-blocking state without reliably notifying connected frontends that the accepted **Workspace context** may be stale.

**Desired behavior:**
After a successful direct Workspace billing mutation that changes **Workspace billing** state, remaining Credits, entitlement, Plan limits, or submission-blocking state, the backend should publish a `workspace_context_invalidated` event for the affected Workspace. Goodwill Credit grants and effective Goodwill Credit revocations should use `billing_usage`. Plan entitlement, scheduled change, subscription cancellation, Plan override, Enterprise deal term, and No-billing mode changes should use `billing_entitlement`.

Invalidation must happen only after the durable mutation succeeds. Failed validation, authorization failures, missing Workspace or ledger failures before durable state changes, duplicate/conflict failures, Stripe API failures before local state is stored, and other no-op failures must not emit invalidation. The live update payload must remain a freshness hint with reason and occurrence metadata only; it must not include computed **Billing operational status**, Credit balances, Plan page capacity, invoice details, payment details, account identity, API keys, or owner-only billing details.

Connected frontends should continue using the existing throttled selected **Workspace context** refresh path and should render operational badges from backend recomputation, not websocket payload contents.

**Key interfaces:**
- Workspace context invalidation transport — reuse the existing `workspace_context_invalidated` event shape and `broadcastWorkspaceContextInvalidation`-style backend interface.
- Direct owner-facing billing mutation handlers — subscription cancellation, scheduled billing-change cancellation, and subscription change paths should emit `billing_entitlement` only when they durably change local Workspace billing state.
- Application admin billing mutation handlers — Goodwill Credit grant/revocation, no-payment Plan override, payment-required Plan override creation, Enterprise ramp-up assignment, Enterprise annual commitment creation, and No-billing mode update should emit the appropriate billing invalidation only after successful state changes.
- Billing ledger mutation outcomes — Goodwill Credit grant and effective revocation should be distinguishable from failures or no-ops so `billing_usage` invalidation is emitted only when capacity may have changed.
- Existing frontend live invalidation handling — should refresh selected accepted **Workspace context** through the throttled path and update badges from the refreshed backend response.

**Acceptance criteria:**
- [ ] Successful Goodwill Credit grants emit `billing_usage` Workspace context invalidation after the grant is durably recorded.
- [ ] Effective Goodwill Credit revocations emit `billing_usage` Workspace context invalidation after the revocation is durably recorded.
- [ ] Successful owner-facing scheduled billing-change cancellation emits `billing_entitlement` invalidation after local scheduled entitlement state is cleared.
- [ ] Successful owner-facing subscription cancellation or paid-to-Free scheduling emits `billing_entitlement` invalidation after local scheduled entitlement state is recorded.
- [ ] Successful Application admin no-payment Plan overrides emit `billing_entitlement` invalidation after override state is recorded.
- [ ] Successful Application admin payment-required Plan override creation emits `billing_entitlement` invalidation after pending override state is recorded.
- [ ] Successful Application admin Enterprise ramp-up and Enterprise annual commitment creation emit `billing_entitlement` invalidation after deal term state is recorded.
- [ ] Successful Application admin No-billing mode changes emit `billing_entitlement` invalidation after No-billing mode state is recorded.
- [ ] Failed or rejected billing mutations do not emit invalidation when no durable Workspace billing state changed.
- [ ] Live update payloads for these invalidations contain only reason and occurrence metadata, not billing details, account identity, API keys, or owner-only state.
- [ ] Focused backend coverage verifies invalidation emission for successful mutations and no-emission failure cases.
- [ ] Existing frontend selected-refresh/live-invalidation coverage continues to prove connected frontends refresh selected **Workspace context** and update operational badges from backend recomputation.

**Out of scope:**
- Stripe webhook, Stripe invoice, delayed checkout, and scheduled billing reconciliation invalidation; those belong to the Stripe billing event invalidation follow-on.
- Document submission, Credit refund compensation, Template mutation, Workspace membership, and Workspace access invalidation; those are covered by separate slices.
- Changing **Workspace billing** product rules, Plan limits, Credit pricing, subscription semantics, Enterprise commercial terms, or final backend enforcement.
- Sending computed billing summaries, badge strings, invoices, payments, account identity, API keys, or owner-only billing state over Workspace live updates.
- Replacing HTTP Workspace context refresh with websocket-sourced state.
