# Template Limit Invalidation

Category: enhancement
Status: completed

## Parent

## What to build

Emit Workspace context invalidation after committed Template mutations that may affect Template count or Template schema Plan limit overage. Connected frontends should refresh the selected accepted Workspace context through the throttled live invalidation path so “Template limit overage” and “Template schema limit overage” badges become fresh without a browser reload.

Local draft edits, Template selection, Template list loading, and Template detail loading should not emit invalidation. Pure Template rename or description-only updates may emit invalidation for implementation simplicity, but schema-impacting changes must be covered.

## Agent Brief

**Category:** enhancement
**Summary:** Emit Template-limit Workspace context invalidation after committed Template mutations.

**Current behavior:**
Template create, update, and delete actions durably change **Workspace product data** and refresh Template data, but they do not reliably signal that the accepted **Workspace context** may be stale. As a result, connected frontends can continue showing stale **Billing operational status** badges for Template count or Template schema **Plan limit overage** until some unrelated Workspace context refresh occurs.

**Desired behavior:**
Successful Template mutations that may change Template count or Template schema limits should emit a `workspace_context_invalidated` event with the `template_limits` reason after the durable mutation succeeds. Connected frontends should use the existing throttled live invalidation path to refresh the selected accepted **Workspace context**, and any Template overage badges should come from recomputed backend **Billing operational status**, not from websocket payload contents.

Failed Template mutations must not emit invalidation when no durable state changed. Local browser draft edits, Template selection, Template list loading, and Template detail loading must not emit invalidation. Pure rename or description-only updates may emit `template_limits` invalidation for implementation simplicity, but field/schema updates must be covered.

**Key interfaces:**
- Template mutation API handlers — should emit Template-limit Workspace context invalidation only after successful create, delete, and schema-impacting update mutations have committed.
- Workspace live update invalidation event — should use the existing `workspace_context_invalidated` event shape with reason `template_limits` and an occurrence timestamp, without embedding computed billing or owner-only state.
- Frontend live invalidation refresh path — should refresh selected accepted **Workspace context** through the throttled scheduler and render Template overage badges from refreshed **Billing operational status**.

**Acceptance criteria:**
- [x] Successful Template creation emits a Template-limit Workspace context invalidation after durable mutation.
- [x] Successful Template deletion emits a Template-limit Workspace context invalidation after durable mutation.
- [x] Successful Template field/schema updates emit a Template-limit Workspace context invalidation after durable mutation.
- [x] Failed Template mutations do not emit invalidation when no durable state changed.
- [x] Local browser draft edits, Template selection, Template list loading, and Template detail loading do not emit invalidation.
- [x] Connected frontends refresh selected Workspace context through the throttled invalidation path and update Template overage badges from recomputed **Billing operational status**.
- [x] Focused backend coverage verifies Template mutation invalidation emission and no-emission failure cases.
- [x] Focused frontend coverage verifies refreshed Template overage badge presentation comes from selected Workspace context refresh, not from websocket payload contents.

**Out of scope:**
- Adding new billing rules, changing Plan limits, or changing final backend enforcement for Document submission and Template limits.
- Sending computed **Billing operational status**, Credit balances, Plan page capacity, invoice details, payment details, account identity, API keys, or owner-only billing state over Workspace live updates.
- Emitting invalidation for Document submission, Workspace billing, Stripe billing events, Workspace membership changes, or Workspace access revalidation; those are separate follow-on issues.
- Replacing HTTP Workspace context refresh with websocket-sourced state.
