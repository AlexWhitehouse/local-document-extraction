## What to build

Handle Workspace access and Plan member limit freshness for connected live update clients. The live update transport should have enough backend-only session identity metadata to close known affected sockets after member-removal or Leave Workspace mutations when possible. When exact socket closure is not possible, emit Workspace access revalidation invalidation so the frontend immediately revalidates the selected accepted Workspace context before applying further useful live update effects.

Member-count-affecting mutations should also emit member-limit invalidation so Plan member limit overage badges become fresh for connected Workspace members.

## Agent Brief

**Category:** enhancement
**Summary:** Refresh or revoke live Workspace access after membership changes, and keep Plan member limit overage fresh.

**Current behavior:**
Workspace live updates are session-only and Workspace API keys are rejected before a socket is opened. The existing live update protocol can publish `workspace_context_invalidated` events, and the frontend can refresh the selected accepted **Workspace context** after ordinary invalidations. However, live update sockets do not yet carry enough backend-only session identity metadata for targeted access-change handling. If a user loses **Workspace membership** while a socket is open, the transport cannot reliably close that user's socket or force immediate access revalidation before additional useful live update effects are applied.

Accepted **Workspace membership** count changes also do not yet consistently publish `member_limits` invalidation, so connected frontends can keep stale **Plan member limit** overage badges until another Workspace context refresh happens.

**Desired behavior:**
Live update connections should store backend-only session identity metadata sufficient to identify known sockets for a signed-in user in an accepted **Workspace context**. That identity must remain connection metadata only and must never appear in websocket message payloads.

After member removal or **Leave Workspace**, the backend should close known affected live update sockets when identity metadata is available. When exact closure is not possible, or when broader access revalidation is safer, the backend should publish a `workspace_access` Workspace context invalidation. The frontend should treat `workspace_access` as urgent: immediately revalidate the selected accepted **Workspace context**, and block further useful effects from that socket until revalidation succeeds. If revalidation fails because access is gone, the existing full Workspace-list/access-recovery flow should take over.

After mutations that change accepted **Workspace membership** count, including invitation acceptance, member removal, and **Leave Workspace**, the backend should publish `member_limits` invalidation after the durable mutation succeeds. Connected frontends should refresh selected **Workspace context** and render **Plan member limit** overage from recomputed backend **Billing operational status**, not from websocket payload contents.

**Key interfaces:**
- Workspace live update connection metadata — should carry backend-only session identity needed for targeted access-change handling without exposing it in payloads.
- Workspace live update access-change operation — should close sockets for known affected session identities and support `workspace_access` invalidation when closure is unavailable or insufficient.
- Workspace context invalidation event — should use existing reason-code payloads such as `workspace_access` and `member_limits`, with occurrence metadata only.
- Workspace membership mutation outcomes — should leave callers enough information after successful mutation to emit access-change and member-limit invalidation only after durable state changes.
- Frontend live update handling — should distinguish urgent Workspace access invalidation from ordinary throttled context invalidation and suppress useful socket effects until access revalidation succeeds.

**Acceptance criteria:**
- [ ] Live update sockets store enough backend-only session identity metadata to support access-change handling.
- [ ] Session identity metadata is not included in websocket message payloads.
- [ ] Member-removal and **Leave Workspace** mutations close known affected sockets when the live update transport has enough identity metadata.
- [ ] `workspace_access` invalidation is emitted when exact affected-socket closure is not available or when broader access revalidation is needed.
- [ ] Frontend Workspace access invalidation causes immediate selected accepted **Workspace context** revalidation.
- [ ] The frontend ignores further useful live update effects for a socket until Workspace access revalidation succeeds.
- [ ] Accepted **Workspace membership** count changes emit `member_limits` invalidation after successful mutation.
- [ ] `member_limits` invalidation refreshes selected **Workspace context** and updates **Plan member limit** overage badges from recomputed **Billing operational status**.
- [ ] Workspace API keys still cannot open Workspace live update sockets.
- [ ] Focused backend coverage verifies socket metadata privacy, affected-socket closure, access revalidation invalidation, member-limit invalidation, and Workspace API key rejection.
- [ ] Focused frontend coverage verifies immediate access revalidation and live update effect blocking until revalidation succeeds.

**Out of scope:**
- Changing **Workspace billing** product rules, Plan member limits, or final backend enforcement.
- Sending account identity, session identity, computed **Billing operational status**, member counts, invoices, payment data, API keys, or owner-only billing details over Workspace live updates.
- Making Workspace live updates durable history or replacing HTTP Workspace context revalidation.
- Implementing billing mutation or Stripe event invalidation; those are separate issues.
