# Workspace-owned Source storage

Issue 99 lets a **Workspace** keep its retained originals in its own S3-compatible bucket. This replaces one decision in [Retained Source Files](0013-retained-source-files.md): a Workspace can now have separate storage. Retention rules, delivery, deletion intents and the key layout from ADR-0013 and [Saved Evaluation Document Originals](0014-saved-evaluation-document-originals.md) are unchanged.

## Decision

- **Default and override.** The installation's storage (`none`, `local` or `s3`) stays the default. A Workspace owner or admin can save a Workspace bucket, which takes precedence for that Workspace's new uploads, packet originals and library saves. `local` remains installation-only. `SOURCE_STORAGE_WORKSPACE_OVERRIDES_ENABLED` (default `true`) lets the operator turn overrides off. With overrides off, saved buckets take no new originals but keep serving existing ones.
- **Retention.** `SOURCE_ORIGINAL_RETENTION_ENABLED` now defaults to `true` when the installation has a store or overrides are enabled. A Workspace with its own bucket retains new originals under that switch and its own opt-out.
- **Destinations.** The control database stores each Workspace bucket in `source_storage_destinations`: endpoint, region, bucket, prefix, addressing style, encrypted credentials, revision and `retired_at`. A destination's location never changes. Saving a different endpoint, bucket, prefix or addressing style retires the current destination and creates another. Saving the same location with a new region or new credentials updates it in place; the region only signs requests. Clearing the override retires the destination.
- **Recorded per object.** Each `source_object_manifest` entry records `destination_id`. Existing rows migrate to `installation`. Reads, recovery and deletion use the recorded destination, never the Workspace's current settings. An upload attempt resolves its destination once and records it before its PUT, so a settings change during an upload cannot split the object from its record. A packet's children use the packet original's destination. Product rows still store only the object key. The manifest entry exists for an object's whole life, from before upload until deletion is confirmed.
- **Installation guard.** `assertDestination` now counts only `installation` entries. Objects in Workspace buckets never block a change to the installation's bucket. The same applies to `storage configure`.
- **Lifetime.** Workspace erasure retires the Workspace's destinations and marks their objects for deletion. Retired destinations, with their credentials, stay until no manifest entry references them, and for at least 15 minutes after retirement. Background cleanup then removes them. Deleting the Workspace therefore never strands objects.
- **Credentials.** Credentials are encrypted with the existing machine key (`secrets/model-gateway.key`) under a separate purpose, bound to the destination ID. The API never returns them. It shows only the last four characters of the access key ID. If the key cannot decrypt them, reads from that bucket are unavailable and a save needs new keys.
- **Saving.** `GET|PUT|DELETE /v1/workspaces/:id/source-storage` and `POST …/source-storage/test` are session-only and limited to owners and admins. Changes need `If-Match`, or `If-None-Match: *` when creating. Every save first writes, reads back and deletes a synthetic object. Nothing is saved if a step fails. Saving needs confirmation that the bucket uses neither versioning nor Object Lock. The app cannot check this.
- **Endpoints.** Endpoints are HTTP(S) origins. Saves and tests reject link-local addresses, cloud metadata hostnames and addresses, and `0.0.0.0/8`. The check covers literal addresses and every address the hostname resolves to. Private networks stay allowed, as for the Model gateway. A hostname that later resolves elsewhere is not re-checked.
- **Isolation.** Clients are cached per destination and rebuilt when its revision changes. Remote read slots (8) are per destination. Cleanup groups due deletions by destination and sweeps the groups concurrently. A group stops at its first failure in a sweep, so an unreachable Workspace bucket costs one timed-out request per sweep.

## Consequences

- Tenants control their own buckets, so the no-versioning and no-Object-Lock rule is the Workspace admin's responsibility. Erasure guarantees depend on their bucket settings. If a tenant revokes access, cleanup retries indefinitely, as for the installation bucket.
- Moving originals between buckets is still unsupported. A changed location affects only new uploads. Earlier locations stay readable until their objects are deleted.
- Workspace admins can make the server send signed requests to private network hosts they choose. Give the role only to trusted people, as for the Model gateway.
- Upload admission still shares `SUBMISSION_MAX_CONCURRENCY` and `SUBMISSION_MAX_RESERVED_BYTES` across Workspaces. A slow tenant bucket holds those reservations while its PUT runs. There is no per-destination upload limit yet.
- Workspace buckets are not part of application-state backups. Restoring control data needs the matching machine key to read their credentials.
